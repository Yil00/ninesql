# Architecture

## Crates
```
crates/
├── ninesql-ui/          # binary `ninesql`: GPUI app, windows, docks, dialogs, actions
├── ninesql-grid/        # virtualized Arrow-backed results grid (GPUI element)
├── ninesql-editor/      # SQL editor integration (gpui-component editor + tree-sitter + completion)
├── ninesql-core/        # app state, connection model, services, driver runtime bridge
├── ninesql-storage/     # XDG workspace files, schema versions, migrations, history.sqlite
├── ninesql-secrets/     # Secret Service backend, encrypted vault, secret handles
├── ninesql-ssh/         # russh tunnels, jump hosts, known_hosts
├── ninesql-transfer/    # streamed export formats, export file, CSV reader and import conversion (P5-C)
├── ninesql-dbeaver/     # DBeaver workspace import / export
├── ninesql-driver-api/  # driver traits, capabilities, dialect, result types
└── drivers/             # one crate per family (ADR-0003), added from P1-B
    ├── ninesql-driver-pgwire/
    ├── ninesql-driver-mysqlwire/
    ├── ninesql-driver-sqlite/
    └── …
```

Dependency direction (no cycles, enforced by the crate graph):
```
ninesql-ui ──► ninesql-grid, ninesql-editor ──► ninesql-core ──► ninesql-driver-api ◄── drivers/*
                                                  │
                                                  ├──► ninesql-storage
                                                  ├──► ninesql-secrets
                                                  ├──► ninesql-ssh
                                                  ├──► ninesql-transfer
                                                  └──► ninesql-dbeaver
```
- UI crates never use a driver crate directly: `ninesql-core` registers drivers and exposes services. The one exception is the `ninesql` binary (`crates/ninesql-ui/src/main.rs`), which registers the drivers it ships (pgwire for PostgreSQL, TimescaleDB, YugabyteDB and QuestDB; mysqlwire for MySQL, MariaDB and TiDB; sqlite) in the `DriverRegistry` at startup; Cargo has no binary-only dependencies, so they are listed in `ninesql-ui`'s manifest, but the library never names them.
- Drivers depend only on `ninesql-driver-api` (and their client crates). They never read workspace files or secrets; they receive resolved parameters.
- `ninesql-dbeaver` does not depend on `ninesql-core` (the core depends on it). It outputs a **mirror** of the core connection model, with the decrypted secrets in zeroized buffers; `ninesql-core` converts that model, runs its own validation, persists the connections and moves the secrets to `ninesql-secrets` (P2-C).

## Threads and data flow
```
GPUI foreground (UI)                Tokio runtime (driver I/O)                 Database
────────────────────                ─────────────────────────                 ────────
user runs a query ──► core service ──► spawn: session.execute() ──────────────► server
                                        │   batches (Arrow / documents)
grid entity  ◄── channel ◄─────────────┘   stop at fetch_size / max_bytes
 renders visible rows only                  cancel token ──► server-side cancel
```
- The foreground never awaits I/O (I6). Services return handles; results arrive through channels polled by GPUI.
- Each result keeps its batches in an `Arc` shared with the grid. Every stream stops at its own `FetchBudget::max_bytes`; on top of it the grid keeps one memory account **per execution** (one editor tab, every result set of a script together) and stops accepting batches at that budget ("retain, never evict", [below](#sql-editor-and-results-grid-p3-a-p3-b)).
- SSH tunnels are tasks on the same runtime; a session holds its tunnel alive and closing the session closes it.

## Startup (`CoreServices`)
The application starts the core with `CoreServices::start(CoreConfig)` (`services` module of `ninesql-core`), which runs on a background thread and answers through a `Reply` (I6). It:
1. opens the project's `Workspace` (directories, workspace lock, `project.json`);
2. selects the secret backend, **keyring → vault → ask every time**, never plaintext: a `SecretServiceStore` when a Secret Service answers (feature `secret-service`, off by default), the vault always registered (opened locked) when it can be opened, and the "ask every time" `SessionSecretCache`. `secret_backend()` says where new secrets go (`Keyring`, `Vault` or `AskEveryTime`);
3. registers the vault and the cache in one `LockHooks`, together with a hook that emits `CoreEvent::SecretsLocked`;
4. starts the `SessionManager` with the `DriverRegistry` the application filled (the application registers the drivers it ships; the UI never depends on a driver crate);
5. starts `DesktopLockWatcher` (feature `desktop-lock`, **on by default**); failing to start it (no system bus) is not an error, `lock_watcher_status()` reports it;
6. runs the idle timer on the driver runtime: `Vault::lock_if_idle` and `SessionSecretCache::purge_expired` every 30 s (vault idle timeout 15 min by default, both in `CoreConfig`).

The UI keeps the `CoreServices` (cheap to clone) and uses `sessions()`, `take_events()`, `validate_connection()`, `unlock_vault()` / `create_vault()` / `vault_status()` / `lock_now()` (all on the blocking pool, answered through a `Reply`) and `lock_watcher_status()`. `shutdown(timeout)` at exit locks the secrets, stops the watcher and the timer and closes every session.

**Vault unlock flow.** When a saved secret of the connection being opened is in the locked vault, `SessionManager::open` answers `OpenOutcome::NeedsVaultUnlock { connection, slot }` before anything is dialled. The UI asks for the master password into a `SecretString`, calls `CoreServices::unlock_vault` (the password is moved to the blocking pool and zeroized right after the key derivation) and opens again, giving prompted secrets again. The unlock is asked for before any "ask every time" prompt. A lock that arrives between the `unlock_vault` call and the end of the unlock wins (lock generation in `LockHooks`): the vault is locked again and the call answers `VaultError::Locked`.

## Driver runtime and session manager (P1-D)
The API lives in `ninesql-core` (`runtime`, `registry`, `session`, `connect` modules); the rustdoc is the reference.
- **`DriverRuntime`**: one multi-thread Tokio runtime owned by the core (4 workers by default, at most 16), for sessions, SSH tunnels and, on its blocking pool, secret-store calls and `known_hosts` I/O. The UI never runs on it.
- **`DriverRegistry`**: engine id → driver. It answers capabilities and dialects without a session, and `validate_connection` is **the** validation entry point of the save (P1-C) and import (P2-C) flows: the model rules, then every driver rule (reserved and unknown properties, authentication kind, password-exchange policy, TLS mode against `Capabilities::tls` — a driver without TLS accepts only `disable` on network endpoints —, the `verify-ca` CA file, client certificates). `Workspace::save_connections_checked` and `create_connection_checked` call it for every connection (disabled connections of engines without a driver get the model rules only); the connect flow calls it again.
- **`SessionManager::open`** runs the connect flow on the runtime and answers through a `Reply` with an `OpenOutcome`: `Opened(SessionHandle)`, `NeedsSecrets` (fields set to "ask every time"; nothing reached the network), `NeedsVaultUnlock` (a saved secret is in the locked vault; nothing reached the network), `HostKeyNeedsConfirmation` (unknown key under the strict policy; no credential sent to that hop) or `InitSqlNeedsConfirmation`. The UI answers and calls `open` again.
- **Sessions**: each session is owned by one task, driven through a bounded command channel. `SessionHandle::execute` returns an `Execution` whose `ExecEvent`s carry the result items one by one through a small bounded channel, so a slow consumer slows the fetch instead of filling memory (I6). The terminal event goes through a slot reserved when the statement starts, and every send gives up when the statement is cancelled or the `Execution` dropped, so a consumer that stopped reading never blocks the session.
- **Cancel**: `Execution::cancel` triggers the driver's execution-scoped server-side cancel. The session stays busy until the server confirms the end; a statement sent meanwhile reports `WaitingForPreviousCancel` and waits up to `ManagerConfig::busy_wait`, then fails with `StillCancelling`.
- **Events**: session-level events (opened, closed, tunnel lost) and `SecretsLocked` (sleep, screen lock, idle, requested) go to one bounded `CoreEvents` channel, taken once with `take_events`. When it is full, events are dropped and counted (`dropped_events`), so the runtime never waits on the UI; `SessionClosed` is never dropped. The UI takes the receiver at startup and resynchronizes when the counter grows (P1-C).
- `Reply` and `Execution` are executor-agnostic: GPUI awaits them on its own executor or polls them with `try_take` / `try_next`.

## Connection lifecycle
1. The user opens a connection → `SessionManager::open`. The core validates it against its driver and, for init SQL that needs confirmation under the connection type or that was imported and not confirmed yet (`init_sql_needs_confirmation`, below), answers `InitSqlNeedsConfirmation` before anything else happens.
2. Saved secrets are read from `ninesql-secrets` on the blocking pool; fields set to "ask every time" come from the UI (`NeedsSecrets`). Secrets travel as zeroizing values and are moved into the SSH hops and the driver parameters; nothing is kept once the driver connected.
3. If SSH is configured, `ninesql-ssh` opens the tunnel hop by hop under each hop's host-key policy (`connections.json` schema 2) and returns a local `127.0.0.1:<port>`. TLS `server_name` is set to the real database host, so `verify-full` still checks the right name behind the tunnel.
4. The driver connects with TLS settings (ADR-0011), the connection's password-exchange policy (`password_exchange`, `connections.json` schema 3) and read-only taken from the connection type's policy (ADR-0007), applies init SQL, and returns a `Session` with its `Capabilities` for that server version. If the policy asks for read-only and the session does not report it, the core closes the session (`ReadOnlyNotEnforced`, I3). A file inside a DBeaver workspace (below) is also asked for as a read-only session, whatever the type, and refused the same way when the driver does not report one (P1-E review, L2): a file driver that ignored `inside_dbeaver_workspace` could otherwise write to it.
5. The UI enables actions from the capabilities (I8).

For a file endpoint, the core sets `ConnectParams::inside_dbeaver_workspace` (I4) from `ManagerConfig::dbeaver_roots` (`DbeaverRoots`), on the blocking pool: after resolving symbolic links, a file is inside when it lies under the `DBeaverData` directory of a known install location (native, Flatpak, Snap) or under a folder added with `DbeaverRoots::add` (a workspace picked for an import, at runtime through `SessionManager::dbeaver_roots()`), when a component of its path is `DBeaverData`, or when an ancestor below the home directory holds `.metadata/dbeaver-workspace.properties` or a `.dbeaver` directory with a DBeaver project file (`$HOME`, its ancestors and `/` are never taken for one). Every check is read-only and fails closed (an unresolvable path or an unreadable marker counts as inside). The driver receives the canonical path that was checked (`DbeaverRoots::check` → `FileCheck`), and `SessionInfo::inside_dbeaver_workspace` tells the UI the file was opened read-only for that reason. A dangling symbolic link (to a file or folder not created yet) is followed to its target, at most 40 links deep, since a creating open would write there. `DbeaverRoots::from_env`, and with it `ManagerConfig::new` and `CoreConfig::new`, canonicalizes `$HOME`: build the configuration off the UI thread. File drivers then open the file read-only.

## Connections UI (P1-C)
In `crates/ninesql-ui/src/connections/`; the rustdoc is the reference.
- **Hub**: one GPUI entity shared by every window, holding the started `CoreServices` and what the UI reads from it (workspace, `SessionManager`, registry, `secret_stores()`, `secret_backend()`), the saved connections and types and the open sessions. It is installed empty at launch; `CoreConfig::new`, `CoreServices::start` (awaited on GPUI's executor) and the first load of `connections.json` run off the UI thread, and the hub fills in when they are done (the UI never opens the workspace itself). Saves go through `Workspace::save_connections_checked`; workspace writes and secret-store calls run on the driver runtime's blocking pool, connects through `SessionManager::open` (I6). It takes `CoreEvents`, rebuilds its open sessions from `sessions_of` when `dropped_events` grows, shows `SecretsLocked` as a notice and a status-bar label, lists a lock watcher that is not running among the connection problems, and calls `CoreServices::shutdown` at quit. "Lock secrets now" (`ctrl-alt-l`) calls `lock_now`.
- **Dialog**: the view model (`form`) offers only what the driver declares (engines from the registry, TLS modes from `Capabilities::tls`, auth kinds and property keys from `ConnectCapabilities`), flags weakened TLS / SSH settings and `verify-ca` without a CA file, and validates with `DriverRegistry::validate_connection` before saving. Credentials show "Saved in keyring" / "Saved in vault" / "Not saved" / "Asked at every connect", never a value; secret inputs are masked with no reveal toggle, use the password content type (no copy, not exposed to accessibility clients), are read into zeroized buffers and cleared on every exit. Each saved secret gets a fresh id (`<connection>:<slot>:<random>`); it is written before `connections.json`, the reference is swapped only once the file is saved (otherwise the new secret is deleted), and every secret no connection references any more is deleted afterwards. URLs only fill fields; a URL with a password or any credential-like parameter is refused.
- **Connect flow** (per window): answers every `OpenOutcome` (secret prompt, host key with fingerprint and `other_key_types`, init SQL with flagged statements, `NeedsVaultUnlock` with the master-password prompt, then a new open) and shows the session's security warnings, including a file opened read-only because it is inside a DBeaver workspace (`SessionInfo::inside_dbeaver_workspace`). Saving a password to a vault that is locked or not created yet opens the same prompt (unlock, or create with a confirmed master password) before saving.
- **DBeaver import** (P2-B, `crates/ninesql-ui/src/import/`): "Import from DBeaver" (`ctrl-k ctrl-i`), "Import from DBeaver: choose folder" (`ctrl-k ctrl-shift-i`, the desktop folder picker or a typed path) and a first-run offer shown while the project is empty and a workspace is found in the known locations (the hub lists them with `ninesql_core::dbeaver::detect_workspaces` on the blocking pool: folders only, nothing decrypted; dismissed for good with `[import] first_run_prompt = false` in `settings.toml`). The preview (`CoreServices::preview_import`) becomes a view model (`import::model`): per project and connection what is created, updated (the `UpdateDiff`, TLS kept at the saved setting with a per-connection "Accept the imported TLS settings" toggle that fills `accept_tls_changes`, reset by every new preview; secrets dropped), imported disabled (the `DisabledReason`) or not imported; secrets as counts and fields only (I1) with the target store; types created or tightened, a tightened type used by saved connections highlighted; imported init SQL marked "will ask for confirmation on first connect". "Test" runs `ImportPreview::connection_for_test` (every credential asked) through the window's connect flow under `ImportPreview::types_after`. The apply goes through `ConnectionHub::apply_import`, which blocks saves while it runs and replaces the hub's list with `ImportOutcome::connections` and reloads the types (no stale list, review L-d); `VaultNotCreated` / `VaultLocked` open the vault prompt and apply the same preview again, `SourceChanged` previews again with a notice. The outcome shows the counts, the report file and the ADR-0006 §4 advice. Disabled connections show their reason in the navigator; "Enable connection" (`ctrl-k ctrl-shift-e`) calls `Workspace::enable_connection` through `ConnectionHub::enable`, passing `route_fixed = true` only for a `Route` reason and only after the user ticked the explicit confirmation; a refusal is shown in the dialog. Connect on a disabled connection says why and does not start.
- **Visuals** (ADR-0007 §4): type color stripe and badges in the navigator, type and read-only badges in the status bar, and a frame in the type color around the editor area while the window's active connection is production. With a session open, production, read-only and the security-warning count come from the session (`SessionInfo`), not from settings saved since; edits apply on reconnect, and the UI says so.

## Confirmations (ADR-0007, ADR-0011)
Everything the user must confirm goes through a single-use token issued by the core, bound to what was shown, expiring after ten minutes:
| Token | Issued with | Bound to |
|---|---|---|
| `ConfirmationToken` | `ExecEvent::NeedsConfirmation` (destructive statement, or any write when the type confirms writes; always on production) | The session, the exact statement text, its language and its parameters |
| `InitSqlToken` | `OpenOutcome::InitSqlNeedsConfirmation` | The connection and its exact init statements |
| `HostKeyToken` | `OpenOutcome::HostKeyNeedsConfirmation` | The key the core kept: the UI cannot get a different key trusted |

Init SQL is classified with the engine's dialect before anything is dialled. Entries the classifier cannot vouch for are flagged too: an entry holding several statements, an entry that changes how the following statements are lexed (for example `sql_mode`, `standard_conforming_strings`), and every entry after the first session-level, access-mode or unrecognised one. Init SQL runs after the read-only mechanism is applied. Saving such init SQL stays allowed (DBeaver imports carry bootstrap queries); it is confirmed when it would run.

Imported init SQL is confirmed once whatever the connection type, because a crafted DBeaver workspace can type its connection "dev" to skip the type's confirmation. A connection carries `init_sql_needs_confirmation` (`connections.json` schema 4; `false` when absent, written only when `true`), which the P2-C import sets and the UI never sets. Since P2-C, `Workspace::save_connections_checked` and `update_connection` read the file under the write guard and keep the marker of a connection whose init SQL is unchanged even when the caller's copy lost it (one more confirmation, never one less).
- **Asked:** while it is set, every init statement is flagged (`ConfirmReason::Imported`, unless the type's own rule flags it first) and `InitSqlConfirmation::imported` is `true`. The core does not trust the request's marker alone: when it has a workspace (`SessionManager::set_workspace`, done by `CoreServices`) and the request carries init SQL without the marker, it reads `connections.json` on the blocking pool (`Workspace::init_sql_marked_on_disk`). A saved connection that carries the marker, or holds other init SQL than the request, counts as marked; so does a failed read. A connection not saved yet uses the request's marker.
- **Token:** the `InitSqlToken` is bound to the connection, its exact statements and whether it was issued with the imported notice, so a token issued without it neither opens a marked connection nor clears the marker.
- **Cleared at confirmation:** when the token is redeemed, before the driver connects, the core calls `Workspace::clear_init_sql_marker`. It clears the marker only when the init SQL on disk is still the confirmed one, under a process-wide guard of the file's writes shared by every `Workspace` of the project. The user approved these exact statements, so a connect that then fails (wrong password, server down) does not ask again; moving the clear after a successful connect would ask again for statements already shown and accepted, without adding a check.
- **Event:** the core then emits `CoreEvent::ImportedInitSqlConfirmed { connection, statements, cleared }`. `cleared` is `Some(true)` when the file now holds those statements without the marker, `Some(false)` when the init SQL on disk changed (a re-import), the connection is not on disk or the write failed, and `None` without a workspace. The hub clears its copy only when its init SQL equals `statements` and `cleared` is not `Some(false)`, so after a failed write or a re-import the next open asks again.
- **Load issues** found by that read-modify-write are removed from the file and logged, as on every load; they are not returned (they can only come from an edit made outside NineSQL since the UI loaded the file).
- An older NineSQL refuses a schema 4 file instead of dropping the marker.

The classifier lexes init SQL with the engine's **default** lexical rules: it does not know the server's `sql_mode` (`ANSI_QUOTES`, `NO_BACKSLASH_ESCAPES`) or `standard_conforming_strings`, which a server or a role can set before the first statement. An entry could therefore be read differently by the server than by the classifier. Mitigations: entries that change the lexical mode, entries holding several statements and every entry after a session statement are flagged; the drivers split init SQL with the session's dialect, send one statement per call, apply the read-only mechanism before the first entry and re-assert or verify it after every statement (docs/05, "Read-only sessions"). A second classification with the session's dialect is not done: init SQL runs inside the driver's connect, before the core holds the session, and the dialect the core has before connecting is the same one.

## Running statements (P3-C)
The `execution` module of `ninesql-core` is the reference (rustdoc); [ADR-0024](adr/0024-phase-3-execution-history-and-preferences-decisions.md) (accepted) records its decisions.
- **`ExecutionService::run(&session, RunRequest)`** returns a `Run` at once and works on the driver runtime. A request is a statement (`RunRequest::statement`: exactly one statement, with its bind parameters), a selection (`RunRequest::selection`, with its offset in the buffer) or a script (`RunRequest::script`). It sits on `SessionHandle::execute`, so every session rule still applies to each statement: classification and confirmation (ADR-0007), read-only refusal, the bounded result channel and the fetch budget (I6), the cancel path, query text logged only at `trace` level when the type allows it.
- **Scripts** are split lazily with the session dialect's `split_script_ahead`, the `ScriptState` (the MySQL `DELIMITER` in force) carried item by item, so the work stays linear ([docs/08](08-engine-capabilities.md#script-splitting-and-classification-p3-d-f-sql-18)). Client directives are applied and never sent. A refused piece (`COPY … FROM STDIN`, a psql meta-command, a mysql client command, an invalid `DELIMITER`) refuses the whole run before anything is sent; one revealed only by a re-split stops the run before its next statement. Each statement is classified with the session's dialect just before it runs; after every statement the dialect's `lexical_rules()` are compared with those the pending items were split with, and the rest is split again from that point when they differ. A `ScriptState` passed back by the caller is validated first (an invalid delimiter refuses the run).
- **Events.** `RunEvent::Started`, then per statement `StatementStarted`, its driver items unchanged (`RunEvent::Item`: result-set headers, row batches, documents, update counts, notices, `Truncated`) and one end (`StatementFinished`, `StatementClosed`, `StatementFailed` with an `ErrorPosition`, `StatementCancelled`, `StatementTimedOut` or `NeedsConfirmation`), and exactly one `Done(RunSummary)`, never dropped: a run task that panics still sends it, from a drop guard. Events go through a small bounded channel (back-pressure on the fetch).
- **Confirmations.** A statement that needs confirmation is not sent; the run ends with `RunEnd::NeedsConfirmation`, and `RunEvent::NeedsConfirmation` carries the statement's absolute span and the `ScriptState` at it. The UI shows the dialog and runs the same text again with `resume_from(span.start)`, `with_script_state(state)` and `confirmed(token)`: statements before the offset are not run again, and the token goes only to the statement that starts exactly there. Resuming is by byte offset, never by index (indexes depend on the lexical modes in force when the text was split).
- **Paging.** With `RunRequest::with_paging`, the first page of each result set is delivered unprompted, then the result pauses (`PageEnd`) with its stream open until `RunControl::fetch` (a page, or all of it under the budget) or `RunControl::release` (closed early: a server-side cancel, `StatementClosed`). Only statements the dialect classifies as reads pause or are released; any other statement streams to its end under the budget. In a script, every read but the last is released after its first page. A paused result keeps the session busy. A paused read left idle for `[execution] paused_result_idle_secs` (default 240 s, 30 to 280 s) is released by the core and reported with `RunEvent::ResultClosedIdle { index, rows, after }` just before its `StatementClosed` (not after a cancel, so it never takes the slot of the terminal event), before pgwire and mysqlwire reach their own 300 s limit, which would close the session too. `paused_result_idle_limit` clamps the preference to `MIN_PAUSED_RESULT_IDLE`..=`MAX_PAUSED_RESULT_IDLE` (30 to 280 s); a lower limit declared by the driver would win, but the driver API has no such field yet, so a shorter server-side setting can still end the session first (P3 review M1, closing PR; [ADR-0024](adr/0024-phase-3-execution-history-and-preferences-decisions.md) §5 note). The rows received stay, the session and any open transaction stay open; reading further means running the statement again. `RunControl` requests are coalesced in constant space.
- **Timeouts.** `TimeoutChoice::Default` takes the connection's own timeout from the preferences (`[execution.connection_timeouts]`), else the global `query_timeout_secs` (none by default, ADR-0004); a request may ask for another one or none. A timeout covers each statement, fetch included.
- **Errors in scripts** follow `on_error` (`stop` by default, or `continue`); after a release or a cancel, only `DriverError::Cancelled` or SQLSTATE `57014` counts as cancelled, any other engine error is kept as a failure.
- **Transactions.** After each statement the session's `TransactionState` is cached on the handle and `CoreEvent::TransactionChanged` is emitted when it changes. `SessionHandle::set_auto_commit(true)` over an open transaction is refused with `CoreError::PendingTransaction` (the user commits or rolls back first). `SessionHandle::close_with(Commit | Rollback)` ends the transaction and closes; it answers `Busy` at once while a statement runs, a paused result included. `SessionManager::sessions_with_open_transaction` and `ConfirmationPreferences::asks_on_close(production)` drive the close confirmation (always asked for production, ADR-0007 §5).
- **Keep-alive.** An idle session is pinged every `keep_alive_secs` (off by default; `SessionManager::set_keep_alive`, applied by the execution service from the preferences); a failed ping reports the session lost.
- **Reconnect** (F-CON-10). `SessionManager::reconnect(OpenRequest, ReconnectPolicy)` is a fresh `open`, retried with exponential backoff on transient failures only (server or hop unreachable, connect timeout); every other outcome (secrets to ask, locked vault, host key, authentication, TLS) ends it at once. It never re-runs a statement, an open transaction is lost, init SQL is confirmed again under its rules. The policy is clamped (1 to 20 attempts, delays up to 60 s) and one reconnect lasts at most 5 minutes. Prompted secrets stay in memory only while it lasts; every secrets lock (`SessionManager::notify_secrets_locked`: lock now, sleep, screen lock, idle) ends it at once with `NeedsSecrets` and drops them. The UI does not start a reconnect yet.

## Query history (P3-C)
`history.sqlite` lives in `$XDG_STATE_HOME/ninesql/` (ADR-0008 §1). The file layer is `ninesql_storage::history::HistoryDb` (`rusqlite`, the bundled SQLite of the workspace); the rules are in `ninesql_core::history`.
- **File.** Created `0600` by NineSQL, opened without following symbolic links and refused when not owned by the user, versioned by `user_version` (a newer file is refused), `secure_delete` on, `journal_size_limit = 0`, and `wal_checkpoint(TRUNCATE)` after every delete, clear, connection delete or pruning that removed entries, so deleted text does not stay in the write-ahead log. A history that cannot be opened is reported by `CoreServices::history_error`; it is not a startup error.
- **What is recorded** (`history::may_record`, then the text check): only when history is enabled, the connection's effective type allows query text in logs (`log_query_text`) and the connection is not production; and never a statement whose text holds a credential word or a URI with credentials (`ninesql_driver_api::hygiene`, the rule the drivers apply to their statement logs, [docs/08](08-engine-capabilities.md#capability-model)). Otherwise nothing at all is stored: no redacted entry, no timing. An entry holds the text as sent, connection, project and engine ids, start time, duration, rows, update count, status, the stable error kind and engine error code (never the engine message), and the **number** of bind parameters, never their values (I1). Statements sent through `SessionHandle::execute` directly are not recorded.
- **Writer.** One thread (`ninesql-history`) owns the database; executions hand it entries through a bounded queue without waiting (a full queue drops and counts, `History::dropped`, as do failed writes). Retention (`max_entries_per_connection`, `max_age_days`) is applied at start, every 500 entries and when it changes; a change is applied after the inserts queued before it, so none of them is written past the new limit.

## Preferences (P3-C)
`ninesql_core::preferences` reads the `[execution]`, `[history]` and `[confirmations]` sections of `settings.toml` (ADR-0008 §1); the keys are listed in the [Run SQL tutorial](tutorials/run-sql.md#10-preferences-in-settingstoml). The load is lenient (a missing or invalid key keeps its default and is reported without echoing a string value; unknown keys are ignored), the save strict: `CoreServices::save_preferences` validates each `PreferenceChange`, edits only the changed keys with `toml_edit` (comments and other sections kept) and writes atomically; a file with a newer `schema_version` or invalid TOML is never overwritten. Whether statements are confirmed is a property of the connection type, never a preference (ADR-0007). `[execution] paused_result_idle_secs` (default 240, 30 to 280) sets how long a paused read may wait for the next fetch before the core releases it (see "Paging" above); its upper bound keeps it below the drivers' 300 s limit. The core and the UI's settings writer take one process-wide lock (`preferences::settings_write_lock`), so their read-modify-writes never interleave. No preferences page exists yet.

## SQL editor and results grid (P3-A, P3-B)
The UI crates talk to the core through narrow adapters, so `ninesql-editor` and `ninesql-grid` never depend on each other, and the core depends on neither:
- **Editor** (`ninesql-editor`): `SqlEditor` on gpui-component's code editor (rope, tree-sitter highlighting with the MIT `tree-sitter-sequel` grammar, search, multi-cursor, folding, completion menu, diagnostics), never Zed's GPL editor (I7). `EditorSetup` comes from the session: `split::DialectSplitter` over `Dialect::split_script` and `code_tokens`, `ParameterStyle::for_engine`, `KeywordSet::for_engine` and the dialect's identifier quoting; completion objects come from a `MetadataProvider` (since P4-B, the core's completion snapshot: [Navigator UI](#navigator-ui-p4-b)). An execution request (statement, selection or script, with its bind parameters and the count of bidirectional controls) goes out through the `ExecutionSink` trait and is never awaited. Text is cleaned on its way in (typed, IME, paste, load): C0 / C1 controls and DEL removed, line ends normalised to `\n`, bidirectional controls kept and flagged. The parameters prompt keeps values in zeroized buffers, consumed on submit; named placeholders are rewritten to the dialect's positional ones and values are always bound.
- **Grid** (`ninesql-grid`): GPUI-free models (cell formatting, one result set over Arrow batches, selection, bounded TSV / CSV copy, `ExecutionResults`) under a `ResultsView` over gpui-component's `DataTable` that builds only the visible rows and columns. It knows the driver-API result types only; `ResultSource` (`fetch`, `release`) and `ExecutionEvent` are its adapter. One **memory budget per execution** (one editor tab: every result set, notice and error of the run, `GridBudget::from_fetch_budget`), "retain, never evict": at the budget the batch is not kept, the result shows "Truncated: memory budget reached" and the stream is released. "Fetch all" can never load more than the budget. Each result-set header is charged `RESULT_SET_OVERHEAD_BYTES` (1 KiB) plus its schema, each update count `UPDATE_COUNT_BYTES` (16 bytes) and each notice its text plus `NOTICE_OVERHEAD_BYTES`, so empty result sets are not free, and one execution keeps at most `MAX_RESULT_TABS` (1 000, a constant) result tabs. A result set past the cap or the budget is counted, not kept, and its stream released; an update count past the budget is counted and not kept (a write's stream is never released); the execution banner starts with "Results limit reached:". A result closed by the core for idleness keeps its rows, shows "closed after idle" and offers no further fetch (P3 review M2, closing PR; [ADR-0024](adr/0024-phase-3-execution-history-and-preferences-decisions.md) §4 note). Details: [`crates/ninesql-grid/README.md`](../crates/ninesql-grid/README.md).
- **Editor tab** (`ninesql-ui`, `editor_tab`): an `SqlEditorTab` holds the editor above the grid in a split, on one open session chosen with the connection picker. Its `TabSink` builds a `RunRequest` (paged, under the preferences' budget) and calls `ExecutionService::run`; each `RunEvent` is awaited on GPUI's background executor and applied on the foreground thread as an `ExecutionEvent` for the grid (I6), one at a time, so back-pressure is kept. A run is bound to the `SessionHandle` it started on: resumes after a confirmation go there only, the picker is disabled and a session change is refused while it lasts, and a closed session ends it. A confirmation dialog that goes away without an answer ends the run and drops its bind values; the bind values the tab holds for a run (its request and the core request kept for a resume) are zeroized when the run ends, whichever way (best effort: the text input's rope and the core's own copies are not). The confirmation shows the statement's line and byte counts in a bounded, scrollable box; a statement over 64 KiB shows its first and last 24 KiB around a marker of the bytes not shown, and the end of the last line is repeated under the box when the end may be out of sight. The cancel button says "Cancel" only for a driver that declares `CancelSupport::ServerSide`, "Stop fetching" otherwise (I8). Commit and roll back are refused during a run. A script request snapshots the text of its range; the run is refused if any byte of it changed.

## Metadata service (P4-B)
The `metadata` module of `ninesql-core` (`crates/ninesql-core/src/metadata/`) is the reference (rustdoc); [ADR-0026](adr/0026-phase-4-metadata-navigator-and-wire-engine-decisions.md) (accepted) records its decisions. `CoreServices::metadata()` returns the `MetadataService`, built at startup with the project's navigator filters.
- **Nodes.** A node (`NodeKey`) is "the objects of one kind under one parent", the unit a driver lists with `Metadata::list`. `child_kinds` says which kinds an object has, from the kinds the session declares (I8): a kind it does not declare, or DDL for a kind outside `MetadataCapabilities::ddl`, fails with `Unsupported` / `DdlUnsupported` before any driver call.
- **Session binding.** Requests name a connection; the service binds it to the connection's **oldest open session** and keeps one cache per connection, tied to that session. When the session ends, the cache is cleared, requests in flight fail with `SessionClosed` and `MetadataEvent::Invalidated` tells the UI; the next request binds another open session of the connection, if any. Metadata calls share the session's connection: a navigator call while a result streams on the same session fails with `Busy` ([docs/08](08-engine-capabilities.md#capability-model)).
- **Loading.** Every call runs on the driver runtime (I6) and answers through a `MetadataRequest` (awaited on any executor) and an event. One request in flight per node and per DDL object (single flight; later callers share it). Dropping the last `MetadataRequest` of a node drops the driver call, which the drivers cancel on the server where the engine can. Defaults (`MetadataConfig`): 30 s per load (every page of it) or DDL fetch; pages of 1 000 objects (`PageRequest::DEFAULT_LIMIT`, clamped to 1..=10 000); at most 10 pages per load, after which the node is reported incomplete and `load_more` continues; at most 4 driver calls at once per connection.
- **Cache.** At most 4 096 entries (nodes and DDL texts) and 64 MiB of estimated bytes per connection, least recently used evicted first. `refresh` reloads a node; `invalidate` drops a subtree. A result larger than the budget is still returned to its requester, not cached.
- **Filters** (F-NAV-04). Include / exclude glob patterns (`*`, `?`, whole-name match) per connection and per kind, case-insensitive unless the filter is case-sensitive; at most 64 patterns per list, 1 to 256 bytes each, no control character; errors never echo a pattern. Applied client-side on every page. Sent to the driver (as a bound substring, `PageRequest::filter`) only for a case-sensitive filter with a single include pattern, its longest literal run; the client-side match then keeps the exact set. `set_filters` saves them and invalidates the connection's tree (`InvalidationReason::FiltersChanged`).
- **`navigator.json`** (schema 1), one per project, next to `connections.json`: filters by connection id, then by kind name. Machine-owned, written atomically under a process-wide writer lock; no secret, no object data. A missing file means no filter; entries with an unknown kind or an invalid pattern are dropped at load and reported (`CoreServices` lists them); a file that cannot be read (from a newer NineSQL, invalid) is reported and never overwritten: the service then keeps filters in memory only. Recorded in [ADR-0026](adr/0026-phase-4-metadata-navigator-and-wire-engine-decisions.md) §1 (not a `connections.json` schema change).
- **Search** (F-NAV-05). `search(SearchRequest)` reads the cache only and never loads: fuzzy on names (exact, prefix, word, substring, then fuzzy ranking), optionally a case-insensitive substring in comments (first 4 KiB) and loaded DDL (first 256 KiB); queries cut to 128 characters; at most 1 000 results (100 by default), 500 000 candidates and 250 ms per search.
- **Prefetch.** `prefetch(connection, root, PrefetchLimits)` loads, in the background, at most `max_nodes` nodes (up to 2 048) to `max_depth` levels (up to 6), and stops when its handle is dropped; `warm_schema` is a prefetch of one schema with the default limits (256 nodes, depth 2: the objects, then their columns). Nothing prefetches by default.
- **Completion.** `completion_snapshot(connection)` builds, from cached nodes only, the schemas, objects (at most 250 000) and columns completion can offer, and is rebuilt only when the cache changed. Foreign keys are listed without their target (`ForeignKeyRef::target` is `None`), so the editor does not complete joins yet ([Phase 4 follow-ups](ROADMAP.md#phase-4-follow-ups)).
- **Events.** `take_events()` gives the bounded `MetadataEvents` channel: `NodeLoaded` (items shown, `complete`, `hidden_by_filter`, `cached`), `NodeFailed`, `DdlLoaded`, `DdlFailed`, `Invalidated` (`Requested`, `Refresh`, `FiltersChanged`, `SessionClosed`). Events that do not fit are dropped and counted (`dropped_events`); the UI then re-reads what it shows from the cache.
- **Hygiene.** Metadata holds object names, comments, types and DDL, never a credential. Errors carry the engine's message to the UI (`MetadataError::Driver`); logs carry connection ids, kind names, counts and stable error kinds (`MetadataError::kind`) only, never object names or engine messages.

## Navigator UI (P4-B)
`crates/ninesql-ui/src/navigator.rs` and `crates/ninesql-ui/src/browse/`; the steps are in the [Browse a database tutorial](tutorials/browse-database.md). Everything reads the `MetadataService` through the hub; each call returns at once and its answer is awaited in a GPUI task that only waits on channels filled by the driver runtime (I6). Dropping a task drops its request, which cancels the driver call when no one else waits for that node.
- **Tree** (`browse::tree`, no GPUI): folders and connections, then under an open connection the kinds its driver declares as groups ("Tables"), the objects of a loaded group, and so on down. Expanding a group loads it; collapsing a loading group cancels its request; expanding a closed connection starts the connect flow (vault unlock, prompts, host keys included). Loaded objects stay in the core's shared `NodeChildren`; rows only point into them, and the view builds only the visible rows (`uniform_list`). Rows say "Loading…", "Load more", "N hidden by filter", "(empty)", or the error ("… (Enter to retry)"). The tree follows `MetadataEvent::Invalidated`, and a closed session clears that connection's subtree. Keyboard navigation uses the shared list actions of gpui-kit (`gpui_kit::base::actions`: `SelectUp`, `SelectDown`, `SelectLeft`, `SelectRight`, `SelectFirst`, `SelectLast`, `SelectPageUp`, `SelectPageDown`, `Confirm`) bound in the navigator's key context; rows have a context menu with the actions that apply to them.
- **Filters dialog**, **"Find object"** (`browse::search`: search over the cache across the open connections, a bounded "Load metadata" prefetch of 256 nodes to depth 4 cancelled when the dialog closes, results revealed in the tree by expanding the path lazily) and the **object editor** (`browse::object_editor`: lists loaded per tab with `children` for the kinds the driver lists under the object, virtualized; "Not available for this engine." for a kind it does not list; a read-only DDL tab only when `supports_ddl`; lists reloaded when the metadata under the object is invalidated).
- **Generate SQL** (`browse::generate`): templates quoted with the session dialect's `quote_identifier`, opened in a new SQL editor and never run; values and conditions are `<placeholders>` that no engine accepts, and `UPDATE` / `DELETE` always carry a `WHERE` line. Placeholders keep only `[A-Za-z0-9_]` (32 characters at most, `<value_N>` when nothing is left), so a name can never add a statement, a comment or a line; a template is refused when a name would be changed by the editor's text hygiene; the key condition comes from the primary-key constraint, or from column flags only when the column node is complete and nothing is filtered, otherwise `WHERE <condition>` with a comment; `INSERT` / `UPDATE` / `DELETE` are not offered on read-only sessions. Running an edited template goes through the normal execution flow and its production confirmation (I3).
- **Completion** (`browse::completion`): a `MetadataProvider` over `completion_snapshot`; when an editor tab binds to a connection, the default schema (the connection's `default_schema` when listed, otherwise the first schema the driver lists, or the first catalog on engines without schemas) is resolved and warmed with `warm_schema`. Names the editor would change are not offered.
- **Labels**: names, comments and engine messages are shown through one display function: control, bidirectional, zero-width and other `Default_Ignorable_Code_Point` characters as `U+FFFD`, space characters other than the ASCII space as `U+2423`, leading or trailing ASCII spaces as `U+2420`; names capped at 200 characters, engine messages at 400. A label is never SQL.

## Session leases (P5-C)
A transfer or a grid save needs its session to itself. `SessionHandle::lease()` returns a `SessionLease` only when the session is idle: no statement running or queued (a paused grid result counts as running), counted by a pending-command counter raised before each send and lowered when the session task has finished the command, so a command the task already took is never missed. While the lease lives, every other statement and transaction command on the session fails with `CoreError::SessionLeased` (the keep-alive ping and `close` still work), metadata loads refuse it (`MetadataError::SessionLeased`), and `SessionHandle::is_leased()` lets the UI disable what would fail. The transfer and edit services wait up to 2 s for a session that is just finishing a statement, then answer `SessionBusy`. A lease dropped while its export, import or save holds a transaction queues a `ROLLBACK` before it is released, so nothing of a half-done job is committed by a later statement. Recorded in [ADR-0027](adr/0027-phase-5-editing-transfer-and-export-decisions.md) §3 (accepted).

## Data transfer (P5-C)
`TransferService` (`crates/ninesql-core/src/transfer.rs`, `CoreServices::transfer()`) runs exports and CSV imports on a session, on the driver runtime (I6), with progress, cancel and a summary; the formats, the export file and the CSV reader are in `ninesql-transfer`. The rustdoc is the reference; the UI steps are in the [export and import tutorial](tutorials/export-import.md).
- **Export** (F-XFER-01): the source is a statement (the active result's, run again) or a table (`SELECT * FROM <table>` quoted by the dialect). It must classify as `Read` with the session's dialect (`TransferJobError::NotARead`). When the session is not read-only, has transactions and none is open, the export runs inside an engine-side read-only transaction (PostgreSQL family `BEGIN READ ONLY`, MySQL and MariaDB `START TRANSACTION READ ONLY`), rolled back before the summary; if it cannot be opened, the export fails on production and confirm-every-write connections and runs without it elsewhere, with a warning. TiDB has no read-only transaction (its read-only transaction forms are no-ops, refused with error 1235 unless `tidb_enable_noop_functions` is on), so none is sent: on a session that is not read-only, a TiDB export has the classifier check only, is refused on production and confirm-every-write connections (`TransferJobError::NoReadOnlyTransaction`; export from a read-only TiDB connection, enforced engine-side by the driver) and carries `ExportWarning::NoReadOnlyTransaction` elsewhere (P5-E M3). A transaction already open: refused on production and confirm-every-write connections, otherwise the export reads inside it, with a warning ([ADR-0007 amendment](adr/0007-production-safety-model.md#amendment-phase-5-2026-11-16), accepted). Batches go through a queue of `WRITER_QUEUE` (2) batches to a writer on the blocking pool that keeps one row of text and a 64 KiB buffer: an export holds at most `(WRITER_QUEUE + 2) × max_batch_bytes` plus the session's own queue, and reports its measured peak (`ExportSummary::peak_buffered_bytes`). Formats: CSV, TSV, JSON (array), JSON Lines, SQL `INSERT` (rendered by the P5-B DML renderer, `dml::insert_preview`), Markdown, HTML (a Content-Security-Policy that forbids scripts). Only the first tabular result set is exported; a value cut by the driver fails a SQL export and is reported per column elsewhere.
- **Export file**: `TransferService::check_export_path` resolves the directory and refuses a relative path, a path inside a DBeaver workspace (`DbeaverRoots`, fail-closed), inside NineSQL's configuration, data or state directories, or inside `~/.ssh` (compared by resolved prefix and by `(device, inode)` of the directory and each ancestor, resolved at every check). `OutputFile` writes a temporary `.<name>.<random>.ninesql-part` in the same directory (`O_CREAT | O_EXCL | O_NOFOLLOW | O_CLOEXEC`, mode `0600`), `fsync`s it and moves it into place with `renameat2(RENAME_NOREPLACE)` (a hard link, then a check and `rename`, only where unsupported), or a plain `rename` when the user confirmed the overwrite; on error or cancel the temporary file is removed ([docs/05](05-security.md#export-and-import-files-p5-c)).
- **CSV import** (F-XFER-03): `preview_csv` reads the first rows (100 by default) and checks them against the target columns; `import_csv` refuses before anything is sent a read-only session, a driver without bind parameters, an open transaction, an all-or-nothing import on an engine without transactions or into a table that cannot roll back (`TransferJobError::NonTransactionalTable`; on the MySQL family also when the storage engine is unknown, `TableStorageUnknown`), an invalid mapping, a file that is not a regular file, over 8 GiB (`CsvLimits::max_file_bytes`) or inside NineSQL's own storage. The file is opened once (`O_NOFOLLOW | O_NONBLOCK`), checked with `fstat` and read through that handle only. Rows go as bound multi-row `INSERT`s (at most 1 000 rows, 30 000 parameters and 4 MiB of parameters each); values are converted from the target column types, never spliced into the text. `ImportTransaction::AllOrNothing` (default) runs one transaction rolled back on error or cancel; `CommitEvery(n)` commits every n rows. The import commits its own rows even on a session in manual-commit mode, unlike a grid save, so the session's "Roll back" cannot undo it (`ImportConfirmation::session_manual_commit`; [ADR-0007 amendment](adr/0007-production-safety-model.md#amendment-phase-5-2026-11-16), note of 2026-11-18). **Target table** (P5-E M1, ADR-0027 §1.6): before its lease the import reads the table's `TableInfo::transactional` through the metadata service (from `ImportRequest::table_path`, or found from the name parts; a complete cached listing that lacks the table is refreshed once and searched again, so a table created after its schema was cached is found (fix of 2026-11-18); a table still not found counts as unknown), and `TransferService::import_target` gives the UI the same `ImportTarget` beforehand (`rows_can_be_rolled_back`, `all_or_nothing_allowed`, `all_or_nothing_refusal`, `table_transactional`). On a MyISAM / MEMORY / ARCHIVE / Aria table, or an unknown storage engine on the MySQL family, only "commit every N rows" runs: every row the database accepted stays whatever the end, `ImportSummary::transactional` is `false` and `rows_committed` counts those rows (a failed multi-row `INSERT` may have written part of its rows too). An invalid row stops the import unless `skip_invalid_rows`; the summary keeps the first 100 issues (line, column, reason, never a value).
- **Confirmation**: on a production or confirm-every-write connection the first call ends with `ImportEvent::NeedsConfirmation` and a single-use `ImportToken`, valid 10 minutes, bound to the session, the canonical file and its identity (device, inode, length, modification time), the table, the columns, the mapping, the transaction mode, `skip_invalid_rows`, the CSV syntax (delimiter, quote, header) and value options (NULL text, empty fields, trimming) and the `ImportTarget` shown; the confirmation also carries the transaction mode, the `ImportTarget` and whether the session is in manual-commit mode (`ImportConfirmation::transaction`, `target`, `non_transactional`, `session_manual_commit`); the UI calls again with `ImportRequest::confirmed`. The service then answers the session's per-statement confirmations only for the byte-identical `INSERT` it just sent, classified `Write` ([ADR-0007 amendment](adr/0007-production-safety-model.md#amendment-phase-5-2026-11-16)).
- **Formatter and snippets**: `format_sql` (F-SQL-09, `crates/ninesql-core/src/sql_format.rs`) changes only keyword case (words reserved in every dialect) and whitespace between tokens, on the dialect lexer; tokens and comments are kept byte for byte, checked by property tests. `SnippetStore` (F-SQL-10, `crates/ninesql-core/src/snippets.rs`) keeps snippets in the project's `snippets.json` ([Storage](#storage)).
- **Run summary** (F-SQL-16): `RunSummary::outcomes` lists each statement's status, span, rows, update count and duration (at most 10 000, the rest counted), and `first_error` the first failure with its stable kind; not shown in the UI yet.

## Data editing (P5-A)
`EditService` (`crates/ninesql-core/src/edit/`, `CoreServices::edit()`) edits rows of one table, builds the server-side sort and filter queries and the foreign-key navigation queries. The rustdoc is the reference; the UI steps are in the [edit data tutorial](tutorials/edit-data.md).
- **Key**: `describe_table` reads the table through the metadata service and picks the row key from the driver's index flags only (`KeyCandidate::from_index`: invalid, deferrable, partial and expression indexes never count) and SQLite's `INTEGER PRIMARY KEY`: the primary key, then the smallest non-null unique key, then the smallest nullable one. Editing is unavailable, with a `NotEditable` reason the UI shows, on a read-only session, without editing capabilities, transactions or bind parameters, without a key, on a non-transactional storage engine (`TableInfo::transactional == Some(false)`) or an unknown one on the MySQL family, or when the table is missing from its schema's listing.
- **Provenance**: only a result of the core's own table query can be edited. `table_query`, `build_table_query` and the foreign-key queries return a `BuiltQuery` whose `QuerySource` names the table and the selected columns; `PendingEdits::new` refuses a result whose columns are not exactly those (name, order, number) with `NotEditable::ResultNotFromTable`. A statement the user typed is never editable.
- **Pending changes and preview**: `PendingEdits` holds cell edits and inserted, duplicated and deleted rows; `plan` renders them with `dml::generate_batch` into the bound statements and the DML preview script; `UPDATE` and `DELETE` carry the original values of the edited columns (columns without reliable equality are listed as unchecked).
- **Save**: never on a read-only session; the session is leased; at most 10 000 changes (`MAX_CHANGES_PER_SAVE`); every statement must classify as a filtered `Write` and runs in its bound form, and must change exactly one row (`check_affected`). Auto-commit session: a `BEGIN` … `COMMIT` of its own (an open transaction is refused). Manual-commit session: inside the session's transaction (opened when none is), under a savepoint `ninesql_edit_save_<random>`, released on success with the transaction left open for the user to commit (`SaveSummary::committed == false`); on failure `ROLLBACK TO SAVEPOINT`, and when that fails the whole transaction is rolled back and the save fails with `EditError::TransactionRolledBack` (`UndoFailed` if even that fails). A driver without savepoints refuses saves in manual-commit mode (`NoSavepoints`).
- **Confirmation**: on a production or confirm-every-write connection the first call ends with `SaveEvent::NeedsConfirmation`: one confirmation for the whole save, showing the preview script, with a single-use `SaveToken`, valid 10 minutes, bound to the session, the table and a SHA-256 digest of the exact statements and values. Once confirmed, the service answers the session's per-statement confirmations only for those statements.
- **Sort and filter** (F-DATA-03): client-side over the loaded rows in the grid; server-side, `build_table_query` re-runs a single-table `SELECT` with names quoted by the dialect, values bound and a raw `WHERE` (at most 16 KiB) accepted only when it stays a read inside its parentheses (balanced, no `;`, no placeholder, none of `UNION`, `ORDER`, `LIMIT`, `INTO`, `FOR`, `UPDATE`, `DELETE`… outside strings, and the whole statement one statement classified `Read`). `record_filter` keeps a per-connection history in memory (50 entries per connection, never on disk) under the history rules: on production and non-logging types only the shape (columns, comparisons, order), never a value or the raw text.
- **Foreign keys** (F-DATA-07): `referenced_rows_query` and `referencing_rows_query` build the bound `SELECT` of the rows a row points to or that point to it, from the metadata service's foreign keys; `referencing_foreign_keys` scans the tables of the same schema (at most 512, 60 s).
- Nothing here logs a value: logs carry counts, kinds and session ids. Decisions in [ADR-0027](adr/0027-phase-5-editing-transfer-and-export-decisions.md) §2 (accepted).

## Export to DBeaver (P5-D)
`CoreServices::export_dbeaver(ids, target)` (`crates/ninesql-core/src/dbeaver_export.rs`) converts the chosen connections and **all** the project's connection types into the input of `ninesql_dbeaver::export_connections` (no secret value: a password, passphrase or token is only a "saved" flag, used for the report), generates the file and writes it with `write_export` to a new `data-sources.json` or a new DBeaver project folder, on the blocking pool. A target inside a DBeaver location is refused (the crate's markers and the session's `DbeaverRoots`, I4). When a path changes while the file is written, nothing is exported (`DbeaverExportError::Changed`) and the UI asks for the target again. What is written, skipped and warned is in [docs/06](06-dbeaver-interop.md#export-to-dbeaver-p5-d); decisions in [ADR-0027](adr/0027-phase-5-editing-transfer-and-export-decisions.md) §5 (accepted).

## DBeaver import (P2-C)
The core side of the import lives in `ninesql-core` (`import` module); the rustdoc is the reference. `ninesql-dbeaver` reads the DBeaver files read-only and returns a mirror of the connection model; the core never reads a DBeaver file itself.
- **API for the UI** (P2-B): `CoreServices::preview_import(ImportSource) -> Reply<Result<ImportPreview, ImportError>>` and `CoreServices::apply_import(ImportPreview, ImportChoices) -> Reply<Result<ImportOutcome, ImportError>>`, both on the driver runtime's blocking pool (I6). `ImportSource::Detect(SearchRoots)` (or `ImportSource::detect_from_env()`) looks in the known locations; `ImportSource::Folder(path)` takes a workspace or project folder the user picked. `CoreServices::importer()` gives the blocking `Importer` for tests and tools.
- **Preview**: the connection types of every project folded together (`ImportPreview::connection_types`: a type id defined in several projects or detected workspaces keeps the stricter rules of each; `TypeAction::Create` / `Tighten` / `Keep` against the project's types, built-ins included), and per DBeaver project the folders (`used`: NineSQL folders exist through their connections, so empty ones are listed and reported, not created), and one `ConnectionPlan` per DBeaver connection: `ImportStatus` (imported, imported disabled, failed), `PlanAction` (`Create`, `Update { existing, diff }` with a field-level `UpdateDiff` — engine, endpoint, user name, TLS, SSH route, driver properties, init SQL, connection type, saved secrets kept / replaced / dropped —, `NotImported { reason }`), the converted `Connection` as it will be written, the secrets to move (`SecretToMove { slot, kind }`, never a value) and the report entries. The preview holds no secret value (I1). The source workspace is added to the session's `DbeaverRoots` at preview time, so its database files open read-only, a test-before-save included.
- **Conversion**: mirror → `Connection`; driver properties come already mapped to NineSQL names by `ninesql-dbeaver` (what it dropped is in `ImportedConnection::dropped_properties` and its report entries); the core re-checks each remaining key against the registered driver and drops a refused one with a report entry unless the parser already reported it (pgjdbc and Connector/J properties without an equivalent never reach a driver); `sanitize()` removes secret-bearing data with an entry; a file endpoint inside a DBeaver workspace (`DbeaverRoots::check`) gets `read_only = Some(true)`; init SQL gets `init_sql_needs_confirmation = true` (never taken from the file); the DBeaver bootstrap default schema / catalog and auto-commit go to `default_schema`, `default_catalog` and `auto_commit` (schema 5; kept, not applied by the drivers yet: the driver API has no default-schema field). Then `DriverRegistry::validate_connection`: a connection its driver refuses, or whose engine has no driver, is imported **disabled** with a persisted `DisabledReason` (`NoDriver`, `Invalid`); the parser's route reasons (network profile, unknown handler, SSH forwarding target) become `Route`. A connection that breaks a model rule is not imported.
- **Apply**: reads the source again and refuses with `ImportError::SourceChanged` if the preview it computes differs (DBeaver files or saved connections changed: preview again). Then `ImportError::NoStore` / `VaultLocked` / `VaultNotCreated` are checked before anything is written. Each selected secret is saved under a fresh reference `<connection id>:<slot>:<uuid>` in the chosen store (`ImportChoices::store`; `None` leaves the fields on "ask every time"), the imported values being dropped (zeroized) right after; types are saved (an existing type, built-ins included, is only ever made stricter, name and color kept), then every connection is written in one checked bulk write under the `connections.json` guard (`Workspace::save_imported`), which refuses (`SourceChanged`) when a connection to update is no longer on disk as planned. Only after that write are the references the connections no longer use deleted; a failure deletes only the new references, so no saved secret is lost. The report is saved as `imports/dbeaver-<YYYYMMDDTHHMMSSZ>.json` in the project (`ImportReportFile`, schema 1): statuses, actions, reasons, secret counts and report entries, no secret value. The report is written last and is best effort (P2-D review, L1): when it cannot be saved (an `imports` path that is not a private directory, a full disk…), the apply still returns its `ImportOutcome`, with `report_file: None`, `report_error: Some("report not saved: <reason>")` and the written connections, and logs a warning without any secret; failing there would leave the UI with a stale list whose next save drops the imported connections.
- **Re-import** (F-CON-14): a connection is updated in place only when its `origin` matches the DBeaver id, the DBeaver project **and** the canonical source workspace (`Origin::Dbeaver::source_workspace`, schema 5). A match on the id alone (another workspace or project, or a connection imported before schema 5) is reported and imported as a new connection. Kept from the saved copy: id, name, description, folder, password-exchange policy, per-hop host-key policies of the same hop behind the same route (a non-strict policy is never carried across a route change: the hop is strict again, reported), a stricter read-only or manual-commit override, a stricter TLS mode and the saved CA file (unless `ImportChoices::accept_tls_changes` lists the connection: the imported settings then apply if the driver accepts them), the saved type unless the imported one is at least as strict on every rule, and a "disabled by the user" state. A secret saved in NineSQL for a field DBeaver has no value for is kept only while everything it authenticates against is unchanged (database: engine, host, port, user, TLS mode and CA file, SSH route; SSH slot: the hop's host, port, user and key file, and the jump hosts in front of it; client key: certificate and key files and host); otherwise it is dropped, reported and deleted after the write. With no store chosen, a saved secret is kept under the same rule instead of being replaced. `ImportPreview::connection_for_test` puts every credential field on "ask", so a test-before-save never sends a saved secret to settings not yet accepted. The init SQL marker is set again on every re-import with init SQL.
- **Disabled reasons**: while `disabled_reason` is set, `enabled` must be `false` (`Connection::validate`). `save_connections_checked` and `update_connection` refuse any change of the reason the file holds (dropped, added, other kind or message); only `Workspace::enable_connection(…, route_fixed, registry)` clears it, through `Connection::try_enable`: the driver must accept the connection, and a `Route` reason also needs `route_fixed = true`, passed by the UI only after the user confirmed the route was set up again.
- **Properties without a driver**: a connection whose engine has no driver keeps its driver properties (they reach no driver while it is disabled); `try_enable` checks them against the driver's allowlist before enabling.
- **Not done**: copying DBeaver SQL scripts (the `Scripts/` format is not verified, docs/06); applying the default schema / catalog at connect (when a driver does, the value must be bound or quoted as an identifier with the dialect, never interpolated: it comes from an imported file).
- **Duplicate** (UI): a copy of a disabled connection keeps its `enabled` flag and its reason.

## Secrets (ADR-0005, P1-D)
`ninesql-secrets` offers three ways to hold a secret, never plaintext on disk (I1):
- **Secret Service** (`SecretServiceStore`, feature `secret-service`, **off by default** until the desktop round trip of ADR-0012 passes): items scoped by the project UUID. The startup probe (`detect_secret_service`) is bounded to 5 s and every D-Bus method call to 25 s; an unlock prompt is not a method call and can wait indefinitely, so the core bounds secret resolution itself: all store calls of one open get `ManagerConfig::secret_timeout` together (default 60 s), after which the field fails with `SecretError::Unavailable`, as does a panicking store task. An open whose `Reply` is dropped stops at once; a store call already running on a blocking thread still ends on the store's own limits, and its value is dropped unused.
- **Vault** (`Vault`, `VaultStore`): `$XDG_DATA_HOME/ninesql/vault.bin`, `0600`, written atomically under the workspace lock. Argon2id (default m = 64 MiB, t = 3, p = 1, stored in the header) and XChaCha20-Poly1305 over the whole entry list with the header as associated data; a key-check tag tells a wrong master password from a damaged file; the payload is padded to 256-byte steps; limits of 10 000 entries, 64 KiB per secret and 16 MiB per file. It starts locked, locks again after an idle time measured on `CLOCK_BOOTTIME` (suspended time counts), slows repeated failed unlocks within the process (`UnlockBackoff`), and can change its master password. Reading never writes. Format v1 is specified in the rustdoc of `ninesql_secrets::vault`.
- **Ask every time** (`SessionSecretCache`): the answer to a prompt stays in memory only, for the session or for a set duration, and is zeroized when removed or expired.

Sleep and screen lock: the vault and the "ask every time" cache are `LockHook`s. Registered in one `LockHooks` (by `CoreServices` at startup), they are locked (vault) and cleared (cache) together through `DesktopLockWatcher` (feature `desktop-lock`, on by default and implied by `secret-service`: zbus 6 only, its own system-bus connection):
- on logind's `PrepareForSleep(true)`. The watcher holds a logind sleep **delay inhibitor**, so the suspend waits (up to logind's `InhibitDelayMaxSec`) until the hook ran; it is released right after and taken again on resume, and dropped when logind leaves the bus and taken again from the new logind when it (re)appears;
- when the current logind session locks: its `Lock` signal, or its `LockedHint` property turning true (what GNOME and KDE lockers set). The session is found by PID, then `$XDG_SESSION_ID`, then the user's display session (`GetUser` → `Display`, for applications in an `app-*.scope`).

The watcher only calls logind (session lookup, `Inhibit`) and the bus (`GetNameOwner`). Match rules alone do not filter senders (a signal addressed to the watcher by name is delivered whatever the rules say), so each signal is checked on receipt: no destination header, and the sender must be the current unique owner of `org.freedesktop.login1`, followed through `NameOwnerChanged`, whose stream is polled before the others so a restarted logind's first signal is not dropped. A forged signal therefore cannot release the sleep delay or force a lock. A panicking hook is logged and the watcher goes on; if the bus connection is lost, it locks once and stops (`is_running()`; it is not restarted). `CoreServices` starts it at startup; without the feature, or without a system bus, the idle timers still apply and `CoreServices::lock_now` locks on demand.

Backend selection at startup: the keyring if a Secret Service answers, otherwise the vault (created on first use with a master password); with neither, only "ask every time". Saved references keep resolving in the vault whatever the keyring does, and there is no silent fallback at runtime: if the keyring fails, the user decides whether to move the secret to the vault. Store calls are blocking and run on the runtime's blocking pool, never on the GPUI thread.

## Storage
See [ADR-0008](adr/0008-workspace-and-config-storage.md): settings in `$XDG_CONFIG_HOME/ninesql`, projects in `$XDG_DATA_HOME/ninesql/workspace`, history and logs in `$XDG_STATE_HOME/ninesql`. No secrets in any of them. Amended by [ADR-0017](adr/0017-workspace-lock-rewrite-on-load-and-project-identity.md):
- **Single writer**: an open workspace holds an exclusive lock on `$XDG_DATA_HOME/ninesql/ninesql.lock`, released by the kernel when the process ends. A second NineSQL process is refused; a file system without locks is refused with an explanation. Writes to NineSQL's `known_hosts` take the same lock behind a process-wide writer mutex and re-read both `known_hosts` files under it, so concurrent writers never drop each other's entries and a key revoked meanwhile is honoured. A lock held by another process is waited for at most 2 s: that only helps against brief holders (a writer without an open workspace); another NineSQL with an open workspace holds the lock for its lifetime, so the write fails.
- **Rewrite on load**: a secret-looking value found in a workspace file is removed and the file is rewritten at once, atomically; migration backups (`.bak`) are built from the scrubbed content.
- **Settings**: `settings.toml` is outside the workspace lock. Its writes are serialized within one process only (the UI writer and the core's preferences writer share `preferences::settings_write_lock`); with two NineSQL processes the last write wins (each write atomic, no secrets in the file). Since P3-C it also holds the execution preferences, per-connection timeouts included ([Preferences](#preferences-p3-c)).
- **History**: `history.sqlite` in `$XDG_STATE_HOME/ninesql/` ([Query history](#query-history-p3-c)); `ninesql-storage` depends on `rusqlite` for it.
- **Project id**: `project.json` (schema version 2) carries a stable UUID, which scopes the project's Secret Service items, so renaming a project keeps its secrets.
- **`connections.json` schema 5** (P2-C): adds the optional `default_schema`, `default_catalog`, `auto_commit` (per-connection override; on a production type it can only turn auto-commit off), `disabled_reason` (`{ "kind": "no-driver" | "route" | "invalid", "message": … }`) and the `source_workspace` of a DBeaver origin (canonical path of the workspace it was imported from). The 4 → 5 migration rewrites nothing and removes these keys from a version 4 file (hand edits); the version 4 file is kept as `connections.json.bak`; an older NineSQL refuses a schema 5 file. Fixture: `crates/ninesql-core/tests/fixtures/connections/v5.json`.
- **`navigator.json`** (schema 1, P4-B): navigator filters per project, beside `connections.json` ([Metadata service](#metadata-service-p4-b), [ADR-0026](adr/0026-phase-4-metadata-navigator-and-wire-engine-decisions.md) §1).
- **`snippets.json`** (schema 1, P5-C): SQL snippets of the project, beside `connections.json`: name (unique, case-insensitive, at most 128 bytes), body (at most 64 KiB), optional engine and description; at most 1 000. A body with a URI holding credentials, or a credential word together with a literal typed in the body, is refused; such entries in a hand-edited file are dropped at load and reported ([ADR-0027](adr/0027-phase-5-editing-transfer-and-export-decisions.md) §4).
- **Writes of one connection**: `Workspace::update_connection` replaces one connection under the write guard instead of rewriting the caller's whole list.

## Error handling and logging
- Typed errors per crate (`thiserror`), mapped by `ninesql-core` to user-facing messages with an optional technical detail panel.
- `tracing` to a rotated file in `$XDG_STATE_HOME/ninesql/`; no values, no passwords, no query text on production connections.
- A panic in a driver task fails that query or session, never the application.
