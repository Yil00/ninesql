# Engine capabilities

The human-readable mirror of each driver's `Capabilities` ([ADR-0004](adr/0004-driver-api-runtime-and-results.md)). The UI only offers what a driver declares (I8). The capability model exists (P0-B). The first drivers are `ninesql-driver-pgwire` for **PostgreSQL** (P1-B, [details below](#pgwire-postgresql-p1-b)) and `ninesql-driver-mysqlwire` for **MySQL** and **MariaDB** (P1-B, [details below](#mysqlwire-mysql-and-mariadb-p1-b)); every other engine row is still the plan. A driver PR updates its row with what its integration tests prove.

Legend: ✅ supported · ◐ partial (see note) · ❌ not supported by the engine · 🗓 planned · — not applicable.

## Capability model
Defined in `crates/ninesql-driver-api/src/capabilities.rs` (`Capabilities`, P0-B); this section mirrors its rustdoc. A driver starts from `Capabilities::minimal(engine)` and switches on only what its integration tests prove. Anything not declared is hidden or disabled by the UI, never attempted (I8). `Session::capabilities()` gives the exact values for the connected server version; `Driver::capabilities(engine, None)` gives the pre-connect values used by the connection dialog.

| Field | Type | Meaning | UI effect when not declared |
|---|---|---|---|
| `query_languages` | set of `Sql`, `InfluxQl`, `MongoQuery`, `RedisCommand`, `SearchDsl`, `Cypher` | Languages accepted by `Session::execute` | Editor mode not offered |
| `result_kinds` | set of `Tabular` (Arrow batches), `Documents` | Kinds of result produced | Grid or document viewer not offered |
| `metadata.kinds` | set of `ObjectKind` | Object kinds `Metadata::list` returns (catalog, schema, table, view, materialized view, column, index, constraint, foreign key, trigger, routine, sequence, type, partition, user, role, collection, key, label, relationship type) | Navigator node hidden |
| `metadata.ddl` | set of `ObjectKind` | Kinds `Metadata::ddl` produces DDL for | "Generate DDL" hidden |
| `editing` | `insert`, `update`, `delete`, `requires_unique_key` | In-grid edits, rendered by `Dialect::render_edit` as parameterized DML | Grid read-only (also read-only for a result without a unique key when `requires_unique_key`) |
| `transactions` | `manual_commit`, `savepoints`, `isolation_levels` | Manual commit mode, savepoints, selectable isolation levels | Commit / rollback toolbar hidden, auto-commit forced |

| `multiple_result_sets` | bool | One statement may yield several result sets | Single result tab |
| `server_side_timeout` | bool | The engine also enforces statement timeouts | Timeout enforced by the result stream only |
| `tls` | set of `TlsMode` | TLS modes offered (`disable`, `require`, `verify-ca`, `verify-full`); empty for file engines | TLS section disabled |
| `parameters` | bool | Bind parameters in statements | Parameter prompt not offered |
| `extra_reserved_properties` | set of keys | Driver property keys this driver reserves on top of the global rule (`is_reserved_property`); compared after the same normalization | Enforced at connect by `Capabilities::check_properties`; validation of these per-driver keys in `ninesql-core` (connection dialog, DBeaver import) is planned with the first driver (P1-B) — until then such a key can be saved and is refused at connect (fails closed) |
| `retains_secret_after_connect` | bool | The driver keeps the connection secret in memory (zeroized on drop) after `connect` returned, for reconnects and for auxiliary connections or requests that authenticate later (cancel, metadata, keep-alive) | When `false`, every secret is dropped before `connect` returns and reconnects ask the core again; see [Secret retention](#secret-retention-after-connect-l5) |

`ReadOnlyMechanism` values (ADR-0007): `SessionSetting { liftable }` (session-level `SET … READ ONLY`), `TransactionMode` (every transaction started read-only by the driver), `OpenMode` (file opened read-only), `ServerSetting { liftable }` (per-session server setting such as ClickHouse `readonly = 1`, not liftable, or `readonly = 2`, liftable), `ReadEndpointsOnly` (only read endpoints are called, InfluxDB 3), and `ClientSideOnly` (no engine-side mechanism: the driver refuses writes it can classify). Every value except `ClientSideOnly` counts as engine-side. `liftable` means a client statement can switch the mechanism off again (PostgreSQL, MySQL / MariaDB / TiDB session settings).

Rules every driver follows whatever its mechanism (rustdoc of `Driver::connect` and `Session::execute`):
- read-only is applied **before** `connect` returns and before init statements run; if it cannot be applied, connect fails;
- driver properties go through `Capabilities::check_properties` (the global rule plus the engine's `extra_reserved_properties`): they can never set TLS / certificate verification, host / port, credentials, read-only / access mode, multi-statements, init SQL or lexical modes (`sslmode`, `useSSL`, `trustServerCertificate`, `readonly`, `options`, `allowMultiQueries`, `initSql`, `sql_mode`, `encrypt`, `keystore`, `proxy`, `hosts`, `url`, `autoReconnect`, `allowPublicKeyRetrieval`, PostgreSQL `replication` (walsender mode bypasses the read-only transaction) and `gssencmode` (GSS encryption would replace TLS), MongoDB `authSource` / `authMechanism` until typed fields exist…); `is_reserved_property` is the canonical rule, which `ninesql-core` reuses (each driver's `extra_reserved_properties` are enforced at connect today and will also be checked by `ninesql-core` from P1-B); keys are compared after normalization (ASCII letters lower-cased, digits kept, separators dropped), and keys holding a non-ASCII or control character, or no letter or digit at all, are always reserved (fails closed); connection settings come only from the typed fields and are passed to the client as structured options, never formatted into a DSN (host, user and database may contain `;`, `&`, `@`); accepted values are passed as typed client options, never spliced into a connection string or URL; property values are `PropertyValue::Plain` or `PropertyValue::Secret` and are never logged;
- exactly one statement per protocol call: text the dialect splits into several statements is refused (`MultipleStatements`), and the dialect's lexical rules follow the session's modes (MySQL `NO_BACKSLASH_ESCAPES` and `ANSI_QUOTES`, executable comments `/*! … */`, `--` needing a space; PostgreSQL `standard_conforming_strings`, `E'…'` strings, dollar quotes, `$` inside identifiers, nested comments; the client encoding, kept UTF-8: a `SET NAMES` / `client_encoding` / `character_set_*` change to anything else counts as `ChangesAccessMode`);
- in a read-only session, statements the dialect classifies as writes are refused client-side as well, and statements that may lift the access mode (class `ChangesAccessMode`: any `SET` / `RESET` / `PRAGMA` outside an allowlist of harmless settings such as `search_path` or `time_zone`, quoted names included, `set_config(…)`, `BEGIN READ WRITE`…) are always refused;
- with a liftable mechanism, the driver also verifies the access mode after every statement (PostgreSQL ≥ 14 `ParameterStatus`, a read-back before 14; MySQL session-state tracking, or a read-back) and closes the session if it changed; driver-internal reconnects re-apply and verify read-only before running anything;
- every result goes through `ResultStream`, which enforces the caller's `FetchBudget` (`batch_rows` default 200, clamped to 10 000; `max_bytes` default 256 MiB; optional `max_rows`; `max_batch_bytes` default 8 MiB; `max_row_bytes` default 4 MiB; `max_value_bytes` default 1 MiB; value ≤ row ≤ batch ≤ total), the timeout and the cancel token, counts result-set headers, notices and update counts against the budget, and ends with `Truncated` at the budget (I6). A batch cut by the budget is copied (copy-on-slice), so the bytes counted are the bytes retained. Drivers end each batch at the row or byte limit (`BatchLimiter`) and cut oversized values and over-wide rows (`RowBudget`), flagging the column with the `ninesql.truncated` field metadata, or wrapping a document value in `DocValue::Truncated`; a flagged column or document is not editable; an empty batch still counts 64 bytes; documents are nested at most 100 levels (`MAX_DOCUMENT_DEPTH`: drivers enforce it while decoding, the stream rejects deeper documents, and dropping a document is iterative whatever its depth);
- the stream checks the grammar: `Rows` need a tabular header and a schema equal to it up to field metadata, `Documents` need a document header, otherwise the stream fails with `Protocol`; a `Truncated` item sent by the driver (`Truncation::new`) ends the stream;
- **timeout** (`ExecOptions::timeout`): measured from `execute`; a watchdog task on the driver runtime calls the server-side cancel at the deadline even when the consumer has stopped polling (a paused grid), and the next poll yields `Timeout`;
- **executions and cancel** (`ExecutionTracker`): each `execute` is one execution with an `ExecutionId`; the session stays `Busy` until the server confirmed that the statement ended (last message, error or acknowledged cancel) and every cancel request sent for it returned; every cancel handle (`ResultStream::cancel_handle`, `Session::cancel_handle`) is scoped to one execution and does nothing once it ended, so a late cancel never hits the next statement. After a cancel the stream drains the raw stream until the server confirms the end (bounded by `SERVER_CANCEL_GRACE`, 5 s); a driver that cannot confirm a dropped stream's end in bounded time closes the session. Engines whose cancel targets the connection (PostgreSQL cancel request, MySQL `KILL QUERY`, SQLite interrupt) rely on the busy rule; engines with addressed cancel send the execution's id (Trino query id, ClickHouse `query_id`, Elasticsearch task id, MongoDB `opId`). The cancel request of a stream is sent once, as a detached task, so it still reaches the server if the consumer drops a `next()` call mid-abort, and a retry waits for that same request;
- **idle cursors**: where the engine ignores a cancel while the backend waits for the client (PostgreSQL suspended portal), the cancel handle also flags the raw stream, whose next poll closes the cursor (`Close` + `Sync`, or `ROLLBACK`) and confirms the end instead of fetching more rows. pgwire also sets `idle_in_transaction_session_timeout`, and its integration tests pause a cursor, let the deadline pass and check that the locks it held are released;
- **metadata** connections (when separate from the main one) use the same TLS settings, SSH route, read-only mechanism and property rules as the session; `PageRequest.filter` and object names are bound as parameters, and a SQL name filter is a literal substring (`escape_like`, `LIKE ? ESCAPE '!'`: `!` rather than a backslash, which MySQL's default `sql_mode` would treat as an escape in the statement text);
- **SSH**: `TunnelInfo.host_key` is the weakest host-key policy across every hop, and `TunnelInfo.hops` lists each hop with its own policy; `security_warnings()` reports `SshHostKeyNotVerified` when any hop is unverified and `SshHopHostKeyNotVerified { hop }` per unverified hop.

**Classifier limit** (L4): the statement classifier recognises functions with side effects only from a known list (sequences, `dblink*`, backend control, replication slots and origins, `pg_stat_reset*`, `pg_backup_*`, `pg_wal_replay_*`, `pg_logical_emit_message`, large-object writers, SQLite `load_extension`). A user-defined function or procedure called from a `SELECT` is classified `Read`: read-only sessions stay protected by the engine-side mechanism, but the production confirmation is not asked for such calls, and an engine declared `ClientSideOnly` cannot stop them. PostgreSQL `U&"…"` names are decoded before matching; a malformed escape or `UESCAPE` makes the statement `Unknown`.

The conformance helpers of the `mock` feature are reused by every driver's integration tests: `conformance::assert_reserved_properties_rejected`, `assert_read_only_refuses_writes` (with `writes_for(engine)`: the engine-neutral `WRITES` plus the family's access-mode statements), `assert_multiple_statements_refused`, `assert_access_mode_change_detected`, `assert_stale_cancel_ignored`, `assert_batches_within_budget` (batch rows, batch / row / value bytes, documents included), `assert_identifier_quoting` (with `IDENTIFIER_SAMPLES`; `assert_dialect_quoting_roundtrip` without a server) and `assert_verify_full_rejects_untrusted_certificate` (driver-supplied parameters for a TLS endpoint signed by a test CA, the CA file and a host name the certificate does not cover: `verify-full` with the CA must connect (positive control, so a server without TLS cannot pass), `verify-full` and `verify-ca` without the CA must fail with a TLS error, and with the CA but the wrong `server_name` `verify-ca` connects while `verify-full` fails; no TLS error may echo the password).

The mock driver (feature `mock` of `ninesql-driver-api`, engine id `mock`) declares every capability by default and accepts overrides so UI tests can check that undeclared features are hidden. It reserves one extra property key (`mock_backdoor`), does not retain the secret after connect, cancels like PostgreSQL (the simulated backend stops whatever runs; handles are execution-scoped) and simulates a self-signed TLS endpoint (`self-signed.mock.invalid`).

## Secret retention after connect (L5)
Declared per driver in `Capabilities::retains_secret_after_connect`. It covers **every** authentication after `connect` returns: automatic reconnects, and auxiliary connections or requests that need credentials (a cancel on a new connection, a separate metadata connection, a keep-alive). When `false`, the driver drops every `Secret` before `connect` returns: the auxiliary connections it needs are opened and authenticated during `connect`, and a reconnect needs fresh parameters from the core (keyring, vault or prompt). When `true`, the secret stays in the driver's memory, zeroized on drop, only for those uses, and is dropped with the session. No driver declares `true`.

| Family | Planned | Status |
|---|---|---|
| pgwire | `false`: the password is dropped (zeroized) before `connect` returns; the cancel request authenticates with the backend key from the handshake; reconnects go through the core | ✅ (PostgreSQL) |
| mysqlwire | `false`: `KILL QUERY` runs on a control connection opened and authenticated during `connect` (same resolved address, same TLS settings, same read-only mode), then the password is dropped (zeroized) before `connect` returns; a keep-alive pings the control connection every 120 s; reconnects go through the core | ✅ (MySQL, MariaDB) |
| clickhouse, trino, search | Cancel is an authenticated HTTP request (`KILL QUERY`, `DELETE /v1/query/{id}`, `_tasks/_cancel`): `true` unless the client keeps an authenticated session | 🗓 |
| sqlite, duckdb | No secret (file engines) | 🗓 |
| Other families | Declared by each driver PR | 🗓 |

## pgwire: PostgreSQL (P1-B)
`ninesql-driver-pgwire` serves the engine id `postgresql` only. TimescaleDB, YugabyteDB and QuestDB are not declared until their own integration tests prove their overrides (I8): `Driver::capabilities` refuses them.

**Client.** The driver speaks the protocol itself on top of the message codec of `postgres-protocol` (rust-postgres, MIT / Apache-2.0), tokio and rustls with the `ring` provider, instead of `tokio-postgres` ([ADR-0003](adr/0003-supported-engines-v1.md) allows replacing a client): it needs `ParameterStatus` after every statement (read-only verification, lexical modes), full control of portals (`Close` + `Sync` on cancel), a cancel request over the session's TLS settings and a `DataRow` reader that cuts values while reading them. SCRAM-SHA-256 and md5 are implemented in the driver with `ring` and `md-5` so every buffer derived from the password is zeroized. No C library, no OpenSSL (`openssl-probe`, pulled by `rustls-native-certs`, only locates the system CA files).

**Connect.**
- Settings travel as startup parameters (`user`, `database`, `application_name`, `client_encoding=UTF8`, `DateStyle=ISO`), never as a DSN. Driver properties: the global rule plus the extra keys above are refused, then only an allowlist is accepted and sent as startup parameters: `search_path`, `TimeZone`, `statement_timeout`, `lock_timeout`, `work_mem`, `client_min_messages` (any other key fails the connect with `InvalidParams`, naming the key only). A `search_path` value that lists `pg_catalog` after another schema is refused. This check is best-effort: it reads the property value only, so a later `SET search_path` or a `set_config` call in a statement is not checked, and `pg_temp` keeps PostgreSQL's own search rules. The driver's internal queries do not rely on it (schema-qualified, below). A DBeaver import carries pgjdbc properties (JDBC URL parameters, driver properties) that are not on this allowlist: until the import maps or drops them (P2-C), such a connection fails at connect with `InvalidParams`.
- TLS: `disable`, `require` (encrypted, certificate not verified; handshake signatures still checked), `verify-ca` (chain checked, host name not checked), `verify-full` (chain and host name). Trust anchors follow libpq's `sslrootcert`: `verify-ca` **requires** `TlsConfig::ca_file` and trusts only that file (chain-only checks against the public roots would accept any publicly certified server); `verify-full` trusts only the CA file when one is set, and the platform trust store otherwise. (The rustdoc of `TlsConfig::ca_file` in `ninesql-driver-api` still says "in addition to the platform trust store": to align in a separate reviewed API PR.) The name verified is `TlsConfig::server_name` when set (SSH tunnel endpoints), else the endpoint host; an IP address is verified against IP SANs. A server that refuses TLS fails the connect: there is never a fallback to plain text. Client certificates: PEM chain and unencrypted PEM key (an encrypted key is refused for now). Cancel requests use the same TLS settings.
- Authentication: SCRAM-SHA-256 (without channel binding: `SCRAM-SHA-256-PLUS` is not offered yet) and md5; GSSAPI / SSPI / Kerberos are refused. The server's SCRAM signature must be verified before `AuthenticationOk` is accepted, a second authentication request is refused, and the server may ask for at most 1 000 000 PBKDF2 iterations (computed off the async workers). A transport counts as protected only with `verify-ca` / `verify-full` TLS, or an SSH tunnel whose hops all verify host keys and whose local end (endpoint host and resolved peer address) is loopback; `require` is not protected. A cleartext password is refused over an unprotected transport; md5 is allowed there with a logged warning (the digest can be cracked offline).
- Internal queries (navigator, type-name lookup, read-only read-back, the idle-timeout setting) never depend on the session's `search_path` (CVE-2018-1058 class): every operator is written `OPERATOR(pg_catalog.…)` and every function, type, collation and relation is schema-qualified; a test plants better-matching user operators on the `search_path` and checks they never run. Internal results are bounded (the server is asked for at most the rows needed, and the driver caps rows and bytes).
- Supported servers: tested on PostgreSQL 18 (`dev/`); catalog queries need PostgreSQL 11 or later (`prokind`).

**Execute.** Extended protocol, one statement per call (`ensure_single_statement` with the session's lexical rules: `standard_conforming_strings` from `ParameterStatus`; a client encoding other than UTF8 closes the session). The statement is parsed and described first (`Parse` + `Describe`), then:
- `SELECT`-class statements outside a transaction run in a driver-implicit read transaction (`BEGIN`, then `idle_in_transaction_session_timeout` set to 300 s for the transaction, unless a stricter non-zero value is already in force) through a portal fetched `batch_rows` rows per `Execute` (fewer when rows are wide, so one fetch stays near `max_batch_bytes`): nothing runs ahead of the consumer. `COMMIT` only when the portal ran to completion; a dropped stream, a cancel, a timeout or an error end with `Close` + `ROLLBACK` without fetching more (idle-cursor rule), even while the consumer is not polling, so a read-class statement with side effects is never partially committed. The 300 s server-side bound ends a session whose consumer never comes back (PostgreSQL then terminates the session).
- Inside the user's transaction (manual commit, or an explicit `BEGIN`) the same portal fetch runs without `BEGIN` / `COMMIT`; cancel or drop sends `Close` + `Sync`.
- Other row-returning statements outside a transaction (`INSERT … RETURNING`, `CALL`, statements the classifier does not see as reads) run in one `Execute`, read incrementally from the socket (TCP back-pressure). A stream dropped while such a statement runs is cancelled by the driver if no row arrived yet; once rows arrive (the write is done) it is drained without cancel, bounded by 5 s, after which the session is closed.
- Manual-commit mode starts a transaction (`BEGIN`) before the first statement that is not transaction control; switching back to auto-commit commits (JDBC semantics).

**Types** (Arrow): `bool` → Boolean; `int2` / `int4` / `int8` → Int16 / Int32 / Int64; `oid` → UInt32; `float4` / `float8` → Float32 / Float64; `bytea` → Binary; `date` → Date32; `time` → Time64(µs); `timestamp` → Timestamp(µs); `timestamptz` → Timestamp(µs, UTC). Everything else is `Utf8` in PostgreSQL's text form with the type name in `ninesql.type`: `numeric` (no faithful Arrow decimal for `NaN`, infinities and unconstrained precision), `interval`, `uuid`, `json` / `jsonb`, arrays (text form for now), `timetz`, network, geometric, range, bit, text search, enums and domains (names looked up in `pg_type`). `text`, `varchar`, `char(n)`, `name` are plain `Utf8`. Infinite dates and timestamps become NULL, flag the column `ninesql.truncated` (not editable) and add a warning notice.

**Results.** Values are cut to `max_value_bytes` / `max_row_bytes` while the `DataRow` is read (the rest is skipped on the socket, never buffered) and flagged `ninesql.truncated`. Notices are stream items (severity, SQLSTATE, message and hint), delivered in chunks of at most 1 000 notices / 1 MiB; in the driver's own round trips, notices beyond twice that are dropped and summarized in one warning; `DETAIL` is left out of errors and notices because it often quotes row values. Update counts come from the command tag (`INSERT`, `UPDATE`, `DELETE`, `MERGE`, `COPY`, `SELECT … INTO`); `NULL` for other commands. Not offered: `COPY FROM STDIN` (refused with `CopyFail`), `COPY TO STDOUT` (output discarded, then an error), `LISTEN` / `NOTIFY` (notifications dropped), several result sets per statement.

**Cancel and timeout.** `CancelRequest` with the backend key on a new connection to the session's resolved address, with the same TLS settings; handles are execution-scoped (`ExecutionTracker`) and the session stays `Busy` until `ReadyForQuery` confirmed the end. Timeouts go through the `ResultStream` watchdog (`server_side_timeout = false`).

**Metadata** shares the session's connection: a navigator call while a result streams fails with `Busy`. Filters, names and cursors are bound parameters; filters are literal substrings (`LIKE $1 ESCAPE '!'`); pages are keyset pages (by name, by column number for columns). Routines are listed with their argument types (`f(integer, text)`) so overloads stay distinct. DDL generation is not offered yet.

**Tests** (`crates/drivers/ninesql-driver-pgwire/tests/postgres.rs`, against `dev/`): every conformance helper (reserved properties, read-only writes, access-mode lift, multiple statements, batch budgets on the 1 000 000-row `big_events`, identifier quoting, stale cancel, `verify-full` against the dev service's test CA), the idle-cursor lock release (a paused cursor's lock and `idle in transaction` state are gone once its deadline passed, checked from a second session), drop / cancel / timeout paths, transactions, edits, metadata and type mapping. The dev service generates its test CA at first start ([dev/tls/postgresql-tls.sh](../dev/tls/postgresql-tls.sh)). md5 and cleartext authentication have unit tests only (the dev server uses SCRAM-SHA-256); the read-back used before PostgreSQL 14 has no server to run against in `dev/`.

## mysqlwire: MySQL and MariaDB (P1-B)
`ninesql-driver-mysqlwire` serves the engine ids `mysql` and `mariadb`. TiDB is not declared until its own integration tests prove its overrides (I8): `Driver::capabilities` refuses it, and a server whose version says TiDB is refused at connect. The engine must match the server: a `mysql` connection to a MariaDB server (or the reverse) fails at connect with a message naming the server version, since their capabilities differ.

**Client.** The driver implements the client/server protocol itself on top of tokio and rustls with the `ring` provider (no protocol crate, no new dependency; [docs/03](03-tech-stack.md#driver-clients)): packets read as a stream across the 16 MiB packet boundary, so values are cut while rows are read. `caching_sha2_password` and `mysql_native_password` are computed with `ring`, every buffer derived from the password zeroized. No C library, no OpenSSL. Client capabilities: protocol 4.1, plugin authentication, transactions, multiple results (for `CALL`), connect attributes (`program_name` = the connection's application name). Never `CLIENT_MULTI_STATEMENTS`, never `CLIENT_LOCAL_FILES` (a `LOAD DATA LOCAL` request from the server is answered with an empty file and the statement fails), no compression, never `CLIENT_IGNORE_SPACE`.

**Connect.**
- The user, database and character set (`utf8mb4_general_ci`, then `SET NAMES utf8mb4`, verified) travel in the handshake, never in a DSN. Driver properties: the global rule plus the extra keys above are refused, then only an allowlist is accepted and applied with `SET SESSION` after connect, values as inert literals (digits, or a hexadecimal string): `time_zone`, `lock_wait_timeout`, `innodb_lock_wait_timeout`, `group_concat_max_len`, and `max_execution_time` (MySQL) or `max_statement_time` (MariaDB); any other key, or a malformed value, fails the connect with `InvalidParams` naming the key only. A DBeaver import carries Connector/J properties that are not on this allowlist: until the import maps or drops them (P2-C), such a connection fails at connect.
- TLS: same modes and trust rules as pgwire: `disable`, `require` (encrypted, certificate not verified), `verify-ca` (requires `TlsConfig::ca_file` and trusts only it; host name not checked), `verify-full` (the CA file alone when set, the platform trust store otherwise; host name checked against `TlsConfig::server_name` or the endpoint host, IP addresses against IP SANs). A server that does not offer TLS fails the connect: never a fallback to plain text. Client certificates: PEM chain and unencrypted PEM key. The control connection uses the same TLS settings.
- Authentication: `caching_sha2_password` (MySQL 8 default) and `mysql_native_password` (MariaDB default), one plugin switch at most. The password itself is sent only over a protected transport, as in pgwire (verified TLS, or an SSH tunnel whose hops all verify host keys and whose local end is loopback): `caching_sha2_password` full authentication (the server has no cached verifier for the account, typically the first connection after a server restart) and `mysql_clear_password` are refused otherwise, with a message saying how to connect (verified TLS once). The server's RSA public key is never requested (`allowPublicKeyRetrieval` is reserved: a man in the middle could send his own); `sha256_password`, `client_ed25519`, `auth_gssapi_client` and other plugins are refused. Challenge-response scrambles (`caching_sha2_password` fast path, `mysql_native_password`) are allowed over any transport.
- Session setup, before anything else runs: `SET NAMES utf8mb4`, `CONNECTION_ID()` read for `KILL QUERY`, `net_write_timeout` raised to 300 s (only ever raised: a paused result keeps the server waiting that long, then the server closes the connection and the session reports `Closed`), `autocommit` from the connection type, the accepted properties, then read-only, then init statements.
- Internal queries never depend on user objects or session modes: built-in functions only (they cannot be shadowed by stored functions), tables qualified with `information_schema`, system variables read as `@@SESSION.…`, user input (filter, schema and table names, cursors) only as hexadecimal literals compared as binary strings (`CAST(… AS BINARY)`), so `sql_mode` (`ANSI_QUOTES`, `NO_BACKSLASH_ESCAPES`, `PIPES_AS_CONCAT`), the character set and collations cannot change what they mean. Internal results are bounded (rows, bytes and value sizes).
- The engine and version are checked on the cleartext greeting and again with `VERSION()` inside the (possibly TLS) session. Authentication frames bypass the transport's write buffer, from zeroized buffers.
- Supported servers: tested on MySQL 8.4 and MariaDB 11.8 (`dev/`); protocol 4.1 with plugin authentication is required (MySQL ≥ 5.5, every MariaDB).

**Execute.** Text protocol (`COM_QUERY`), one statement per call (`ensure_single_statement` with the session's lexical rules; the protocol rejects a second statement anyway, since multi-statements are off). The dialect follows the session's `sql_mode`: `NO_BACKSLASH_ESCAPES` from the server status flags of every response and from the read-back, `ANSI_QUOTES` from the read-back (`"…"` identifiers are rewritten into backtick identifiers of the same length before the shared lexer splits or classifies, because `LexicalRules` has no `ANSI_QUOTES` switch). A stored-program definition (`CREATE PROCEDURE | FUNCTION | TRIGGER | EVENT … BEGIN … END`) is one statement: `;` inside its `BEGIN … END` body does not split it (text after the closing `END` does); it classifies `Unknown` (the riskiest statement of its body), so it needs confirmation in production and is refused in read-only sessions. Parameters are inlined client-side as literals that cannot leave their token in any `sql_mode` or character set: hexadecimal strings (`CONVERT(X'…' USING utf8mb4)` for text and JSON, `X'…'` for bytes), digits (negative numbers in parentheses), `DATE` / `TIMESTAMP` literals; placeholders are found with the same lexical rules, so a `?` in a string, identifier or comment is never replaced, and the counts of placeholders and parameters must match. UTC timestamps, NaN and infinities are refused (MySQL has no time-zone-aware `DATETIME`, no NaN). Rows are read as the consumer asks: a full batch is delivered and nothing more is read until the next poll (TCP back-pressure pauses the server). Every result set of a `CALL` is delivered in turn (`multiple_result_sets`), then its update count. Manual-commit mode is the server's `autocommit = 0`; `auto_commit()` and `in_transaction()` follow the server status flags; switching back to auto-commit commits (`SET autocommit = 1`).

**Types** (Arrow): `TINYINT` / `SMALLINT` / `MEDIUMINT` / `INT` / `BIGINT` → `Int8` / `Int16` / `Int32` / `Int32` / `Int64` (`UInt*` when `UNSIGNED`); `YEAR` → `Int16`; `FLOAT` / `DOUBLE` → `Float32` / `Float64`; `DATE` → `Date32`; `DATETIME` → `Timestamp(µs)`; `TIMESTAMP` → `Timestamp(µs)` in the session time zone (`ninesql.type` = `timestamp`); text types → `Utf8`; binary types and `BLOB`s → `Binary`. With `ninesql.type`: `DECIMAL` (`Utf8`: precision 65), `TIME` (`Utf8`: a duration up to ± 838:59:59), `JSON` (`Utf8`; MariaDB reports `JSON` columns as `LONGTEXT`), `ENUM`, `SET` (`Utf8`), `BIT`, `GEOMETRY`, `VECTOR` (`Binary`). Zero or invalid dates (`0000-00-00`) become NULL, flag the column `ninesql.truncated` (not editable) and add a warning notice.

**Results.** Column definitions are bounded (4 MiB per result set, names cut to 1 KiB) and the driver's own queries by rows, bytes per row and value. Values are cut to `max_value_bytes` / `max_row_bytes` while the row is read (the rest is skipped on the socket, never buffered) and flagged `ninesql.truncated`. The server's warnings become notices after the statement (`SHOW WARNINGS LIMIT 1000`: level, code, message). Errors carry the server's error number as `code` and the SQLSTATE in the message; `1792` / `25006` is `ReadOnly`, an interrupted statement after a cancel is `Cancelled`. Update counts come from the OK packet (affected rows). Not offered: `LOAD DATA LOCAL INFILE`, prepared statements (`COM_STMT_*`), compression.

**Read-only verification.** After every statement in a read-only session, and after statements that may change session modes in any session (classes `Session`, `ChangesAccessMode`, `Unknown`, which include `SET` and `CALL`), one read-back: `@@SESSION.sql_mode`, the three `character_set_*` variables and `transaction_read_only`. A lifted read-only mode closes the session (`ReadOnly`, then `Closed`); a character set that is not UTF-8 closes any session (`Closed`); any failure of the read-back closes the session (fails closed). In a read-only session the read-back is followed by `SET SESSION TRANSACTION READ ONLY`: `SET TRANSACTION … READ WRITE` without `SESSION` (also in its comma form, `SET TRANSACTION ISOLATION LEVEL READ COMMITTED, READ WRITE`, which the shared classifier sees as `Session`, and from a MariaDB stored function) only changes the *next* transaction and leaves `transaction_read_only` at 1, so the read-back cannot see it; re-asserting the session characteristic resets that pending mode on both engines, inside an open transaction too (security review H1, tested in autocommit and manual mode). Driver statements (transaction control, settings, metadata, the read-back) are bounded by 60 s; past it the session is closed. Session-state tracking is not used: a statement can turn it off, while the read-back cannot be avoided. Consequence: in a read-only session the read-back runs between two user statements, so `FOUND_ROWS()` and `ROW_COUNT()` refer to it.

**Cancel and timeout.** `KILL QUERY <connection id>` on the control connection; handles are execution-scoped (`ExecutionTracker`), the session stays `Busy` until the server confirmed the end, and a dropped or cancelled stream is drained (bounded by 5 s, then the session is closed). A stream dropped while a write-class statement streams rows (`… RETURNING` on MariaDB) is drained without `KILL QUERY` once rows arrived. A `KILL QUERY` that arrives after its statement ended can interrupt the driver's own read-back: it is retried once. Behind a proxy that rewrites connection ids (ProxySQL, some load balancers) `KILL QUERY` may not reach the right backend: connect to the server directly. Timeouts go through the `ResultStream` watchdog (`server_side_timeout = false`; `max_execution_time` / `max_statement_time` can be set as properties).

**Metadata** shares the session's connection: a navigator call while a result streams fails with `Busy`. Databases are listed as `Schema`; tables (`BASE TABLE`, MariaDB `SYSTEM VERSIONED`), views (`VIEW`, `SYSTEM VIEW`), columns and routines come from `information_schema`; filters are literal substrings (`CAST(name AS BINARY) LIKE X'…' ESCAPE '!'`, built with `escape_like`); pages are keyset pages by binary name (by ordinal for columns; routines by name and type, since a function and a procedure may share a name). DDL generation is not offered yet.

**Tests** (`crates/drivers/ninesql-driver-mysqlwire/tests/mysql.rs`, every test on both `dev/` engines): every conformance helper (reserved properties, read-only writes, access-mode lift through a stored function, multiple statements, batch budgets on the 1 000 000-row `big_events`, identifier quoting, stale cancel, `verify-full` against the dev services' test CA), `caching_sha2_password` full authentication refused over plain TCP and accepted over verified TLS (MySQL), dropped streams (mid-result and mid-statement), cancel and timeout (also over TLS), transactions and isolation levels, edits and parameters with hostile text, warnings as notices, both result sets of a `CALL`, `EXPLAIN` in the declared formats, `LOAD DATA LOCAL` refused, metadata pages and filters, a wrong password and a wrong engine, a connection killed by the server. The dev services generate their test CA at first start ([dev/tls/mysql-tls.sh](../dev/tls/mysql-tls.sh)). Fake servers in the unit tests check that the password is never sent over an unprotected transport (full `caching_sha2_password` exchange, switch to `mysql_clear_password`), that a second plugin switch is refused and that a server without TLS fails a TLS connection; `CLIENT_MULTI_STATEMENTS` and `CLIENT_LOCAL_FILES` are checked off in the handshake response.
