# Engine capabilities

The human-readable mirror of each driver's `Capabilities` ([ADR-0004](adr/0004-driver-api-runtime-and-results.md)). The UI only offers what a driver declares (I8). The capability model exists (P0-B). The first drivers are `ninesql-driver-pgwire` for **PostgreSQL** (P1-B, [details below](#pgwire-postgresql-p1-b)) and, since P4-C, **TimescaleDB**, **YugabyteDB** and **QuestDB** ([details below](#wire-compatible-engines-p4-c)), `ninesql-driver-mysqlwire` for **MySQL** and **MariaDB** (P1-B, [details below](#mysqlwire-mysql-and-mariadb-p1-b)) and, since P4-C, **TiDB**, and `ninesql-driver-sqlite` for **SQLite** (P1-B, [details below](#sqlite-sqlite-p1-b)); every other engine row is still the plan. A driver PR updates its row with what its integration tests prove.

Legend: ✅ supported · ◐ partial (see note) · ❌ not supported by the engine · 🗓 planned · — not applicable.

## Capability model
Defined in `crates/ninesql-driver-api/src/capabilities.rs` (`Capabilities`, P0-B); this section mirrors its rustdoc. A driver starts from `Capabilities::minimal(engine)` and switches on only what its integration tests prove. Anything not declared is hidden or disabled by the UI, never attempted (I8). `Session::capabilities()` gives the exact values for the connected server version; `Driver::capabilities(engine, None)` gives the pre-connect values used by the connection dialog.

| Field | Type | Meaning | UI effect when not declared |
|---|---|---|---|
| `query_languages` | set of `Sql`, `InfluxQl`, `MongoQuery`, `RedisCommand`, `SearchDsl`, `Cypher` | Languages accepted by `Session::execute` | Editor mode not offered |
| `result_kinds` | set of `Tabular` (Arrow batches), `Documents` | Kinds of result produced | Grid or document viewer not offered |
| `metadata.kinds` | set of `ObjectKind` | Object kinds `Metadata::list` returns (catalog, schema, table, view, materialized view, column, index, constraint, foreign key, trigger, routine, sequence, type, partition, user, role, collection, key, label, relationship type, event) | Navigator node hidden |
| `metadata.ddl` | set of `ObjectKind` | Kinds `Metadata::ddl` produces DDL for | "Generate DDL" hidden |
| `editing` | `insert`, `update`, `delete`, `requires_unique_key` | In-grid edits, generated by `dml::generate` as parameterized DML plus a literal preview ([DML generation](#dml-generation-p5-b)); `Dialect::render_edit` is the older parameterized-only form | Grid read-only (also read-only for a result without a unique key when `requires_unique_key`) |
| `transactions` | `manual_commit`, `savepoints`, `isolation_levels` | Manual commit mode, savepoints, selectable isolation levels | Commit / rollback toolbar hidden, auto-commit forced |
| `read_only` | `ReadOnlyMechanism` (below) | How a read-only session is enforced (I3) | `ClientSideOnly` is shown in plain words with a read-only account recommendation |
| `cancel` | `ServerSide` / `LocalOnly` | Whether cancel reaches the server | Cancel still offered; `LocalOnly` is labelled "stop fetching" |
| `explain` | set of `Text`, `Json`, `Analyze` | Explain formats (`Analyze` runs the statement) | "Explain" hidden |
| `multiple_result_sets` | bool | One statement may yield several result sets | Single result tab |
| `server_side_timeout` | bool | The engine also enforces statement timeouts | Timeout enforced by the result stream only |
| `tls` | set of `TlsMode` | TLS modes offered (`disable`, `require`, `verify-ca`, `verify-full`); empty for file engines | TLS section disabled |
| `parameters` | bool | Bind parameters in statements | Parameter prompt not offered |
| `extra_reserved_properties` | set of keys | Driver property keys this driver reserves on top of the global rule (`is_reserved_property`); compared after the same normalization | Enforced at connect by `Capabilities::check_properties`, and refused when a connection is saved or imported by `ninesql-core` (`DriverRegistry::validate_connection` / `Connection::validate_for_driver`) |
| `connect` | `ConnectCapabilities` (below) | Connection settings the driver accepts: property allowlist, authentication kinds, password-exchange policies, whether `verify-ca` needs a CA file, client certificates, encrypted client keys | The driver refuses anything else at connect (`ConnectCapabilities::check_connect_params`, before any network or file access), and `ninesql-core` refuses it when the connection is saved or imported, so the dialog and the import never store a connection the driver would refuse (M2) |
| `retains_secret_after_connect` | bool | The driver keeps the connection secret in memory (zeroized on drop) after `connect` returned, for reconnects and for auxiliary connections or requests that authenticate later (cancel, metadata, keep-alive) | When `false`, every secret is dropped before `connect` returns and reconnects ask the core again; see [Secret retention](#secret-retention-after-connect-l5) |

`ConnectCapabilities` fields (wave 2 integration review, M2; `ConnectCapabilities::default()` is the most conservative declaration):
- `accepted_properties`: driver property keys accepted, compared after the normalization of the reserved-key rule; `None` means every key that is not reserved; a reserved key is refused even when listed;
- `auth`: the `AuthKind`s accepted (`None`, `Password`, `Token`);
- `password_exchanges`: the `PasswordExchange` policies the driver can enforce (`Any`, always accepted; `ScramOnly`: only a SCRAM exchange in which the server proves it knows the verifier, as libpq's `require_auth=scram-sha-256`; it stops method downgrades, not a relaying man in the middle, against which only `verify-full` TLS protects: no channel binding yet);
- `verify_ca_requires_ca_file`: `verify-ca` needs `TlsConfig::ca_file` ([ADR-0019](adr/0019-tls-ca-file-semantics.md) rule 2; `true` for every driver that offers TLS); refused at connect with a TLS error;
- `client_certificates`, `encrypted_client_keys`: mTLS, and client keys protected by a passphrase.

| Family | Accepted properties | Authentication | Password exchanges | `verify-ca` needs a CA file | Client certificates | Encrypted client keys |
|---|---|---|---|---|---|---|
| pgwire (PostgreSQL, TimescaleDB, YugabyteDB) | `search_path`, `TimeZone`, `statement_timeout`, `lock_timeout`, `work_mem`, `client_min_messages` | `Password` (user name, password optional) | `Any`, `ScramOnly` | yes | yes (PEM chain, unencrypted PEM key) | no |
| pgwire (QuestDB) | none (QuestDB ignores PostgreSQL session settings) | `Password` | `Any` only: QuestDB asks for a cleartext password | — (no TLS) | no | no |
| mysqlwire | `time_zone`, `lock_wait_timeout`, `innodb_lock_wait_timeout`, `group_concat_max_len`; `max_execution_time` (MySQL, TiDB) or `max_statement_time` (MariaDB) | `Password` | `Any` only: no MySQL exchange proves that the server knows the password verifier (`caching_sha2_password` is not SCRAM) | yes (TiDB: — , no TLS declared yet) | yes (PEM chain, unencrypted PEM key) | no |
| sqlite | `busy_timeout`, `cache_size`, `foreign_keys` | `None` | `Any` | — (no TLS) | no | no |

`ninesql-core` checks a saved connection against these fields in `Connection::validate_for_driver` (called by `DriverRegistry::validate_connection` and again by the connect flow): a property off the allowlist, an authentication method not listed, a password-exchange policy not listed, a TLS mode outside `Capabilities::tls` (a driver without TLS accepts only `disable` on network endpoints; a driver declaring TLS without `disable` refuses it), and, on network endpoints with TLS enabled, `verify-ca` without a CA file, a client certificate or an encrypted client key the driver does not support are refused with `ConnectionError::InvalidField`, naming the field, never the value. `Workspace::save_connections_checked` and `create_connection_checked` run these checks on every connection before saving. The password-exchange policy is the connection's `password_exchange` field (`connections.json` schema 3), passed to `ConnectParams::password_exchange`.

`ReadOnlyMechanism` values (ADR-0007): `SessionSetting { liftable }` (session-level `SET … READ ONLY`), `TransactionMode` (every transaction started read-only by the driver), `OpenMode` (file opened read-only), `ServerSetting { liftable }` (per-session server setting such as ClickHouse `readonly = 1`, not liftable, or `readonly = 2`, liftable), `ReadEndpointsOnly` (only read endpoints are called, InfluxDB 3), and `ClientSideOnly` (no engine-side mechanism: the driver refuses writes it can classify). Every value except `ClientSideOnly` counts as engine-side. `liftable` means a client statement can switch the mechanism off again (PostgreSQL, MySQL / MariaDB / TiDB session settings).

Rules every driver follows whatever its mechanism (rustdoc of `Driver::connect` and `Session::execute`):
- read-only is applied **before** `connect` returns and before init statements run; if it cannot be applied, connect fails;
- driver properties go through `Capabilities::check_properties` (the global rule plus the engine's `extra_reserved_properties`): they can never set TLS / certificate verification, host / port, credentials, read-only / access mode, multi-statements, init SQL or lexical modes (`sslmode`, `useSSL`, `trustServerCertificate`, `readonly`, `options`, `allowMultiQueries`, `initSql`, `sql_mode`, `encrypt`, `keystore`, `proxy`, `hosts`, `url`, `autoReconnect`, `allowPublicKeyRetrieval`, PostgreSQL `replication` (walsender mode bypasses the read-only transaction) and `gssencmode` (GSS encryption would replace TLS), MongoDB `authSource` / `authMechanism` until typed fields exist…); `is_reserved_property` is the canonical rule, which `ninesql-core` reuses (each driver's `extra_reserved_properties` and its `connect.accepted_properties` allowlist are enforced at connect and checked by `ninesql-core` when a connection is saved or imported); keys are compared after normalization (ASCII letters lower-cased, digits kept, separators dropped), and keys holding a non-ASCII or control character, or no letter or digit at all, are always reserved (fails closed); connection settings come only from the typed fields and are passed to the client as structured options, never formatted into a DSN (host, user and database may contain `;`, `&`, `@`); accepted values are passed as typed client options, never spliced into a connection string or URL; property values are `PropertyValue::Plain` or `PropertyValue::Secret` and are never logged;
- exactly one statement per protocol call: text the dialect splits into several statements is refused (`MultipleStatements`), and the dialect's lexical rules follow the session's modes (MySQL `NO_BACKSLASH_ESCAPES` and `ANSI_QUOTES`, executable comments `/*! … */`, `--` needing a space; PostgreSQL `standard_conforming_strings`, `E'…'` strings, dollar quotes, `$` inside identifiers, nested comments; the client encoding, kept UTF-8: a `SET NAMES` / `client_encoding` / `character_set_*` change to anything else counts as `ChangesAccessMode`);
- in a read-only session, statements the dialect classifies as writes are refused client-side as well, and statements that may lift the access mode (class `ChangesAccessMode`: any `SET` / `RESET` / `PRAGMA` outside an allowlist of harmless settings such as `search_path` or `time_zone`, quoted names included, `set_config(…)`, `BEGIN READ WRITE`, `SET [SESSION | LOCAL] TRANSACTION …` with `READ WRITE` in **any** comma segment, as in `SET TRANSACTION ISOLATION LEVEL READ COMMITTED, READ WRITE`…) are always refused; a `WITH` statement is a read only when its parentheses balance and its main statement (`SELECT`, `VALUES`, `TABLE`, or a DML keyword) is found outside every CTE body: an unbalanced or unterminated `WITH`, or one without a main statement, is `Unknown` (a main statement written in parentheses, `WITH c AS (…) (SELECT …)`, is not looked into and is `Unknown` too, which only asks for confirmation);
- **statement text in logs** (ADR-0007 §1 and §6, L1): drivers log statement text at `trace` level only when `ConnectParams::may_log_statements()` is `true`, i.e. `log_statements` (set by the core from the connection type's `log_query_text`) and not `production`; a custom type with `log_query_text = false` is honoured, not only production; and never a text that may hold a credential (`ninesql_driver_api::text_may_hold_credentials`, the rule the core applies to its logs and history: a credential word – password, passwd, pwd, passphrase, identified, secret(s), credential(s), (un)encrypted, encrypt, decrypt, token, apikey, privatekey, crypt – as a whole word in any case, `_` separating words, or a URI with credentials `scheme://user:password@`), init SQL included; pgwire, mysqlwire and sqlite apply it through `may_log_statement_text` and test it with `conformance::assert_credential_statements_not_logged`;
- **files inside a DBeaver workspace** (I4): `ConnectParams::inside_dbeaver_workspace` marks an `Endpoint::File` inside `DBeaverData`; file drivers then open it read-only whatever `read_only` says, never create it, and never create or modify a file next to it; network drivers ignore the flag;
- with a liftable mechanism, the driver also verifies the access mode after every statement (PostgreSQL ≥ 14 `ParameterStatus`, a read-back before 14; MySQL session-state tracking, or a read-back) and closes the session if it changed; driver-internal reconnects re-apply and verify read-only before running anything;
- every result goes through `ResultStream`, which enforces the caller's `FetchBudget` (`batch_rows` default 200, clamped to 10 000; `max_bytes` default 256 MiB; optional `max_rows`; `max_batch_bytes` default 8 MiB; `max_row_bytes` default 4 MiB; `max_value_bytes` default 1 MiB; value ≤ row ≤ batch ≤ total), the timeout and the cancel token, counts result-set headers, notices and update counts against the budget, and ends with `Truncated` at the budget (I6). A batch cut by the budget is copied (copy-on-slice), so the bytes counted are the bytes retained. Drivers end each batch at the row or byte limit (`BatchLimiter`) and cut oversized values and over-wide rows (`RowBudget`), flagging the column with the `ninesql.truncated` field metadata, or wrapping a document value in `DocValue::Truncated`; a flagged column or document is not editable; an empty batch still counts 64 bytes; documents are nested at most 100 levels (`MAX_DOCUMENT_DEPTH`: drivers enforce it while decoding, the stream rejects deeper documents, and dropping a document is iterative whatever its depth);
- the stream checks the grammar: `Rows` need a tabular header and a schema equal to it up to field metadata, `Documents` need a document header, otherwise the stream fails with `Protocol`; a `Truncated` item sent by the driver (`Truncation::new`) ends the stream;
- **timeout** (`ExecOptions::timeout`): measured from `execute`; a watchdog task on the driver runtime calls the server-side cancel at the deadline even when the consumer has stopped polling (a paused grid), and the next poll yields `Timeout`;
- **executions and cancel** (`ExecutionTracker`): each `execute` is one execution with an `ExecutionId`; the session stays `Busy` until the server confirmed that the statement ended (last message, error or acknowledged cancel) and every cancel request sent for it returned; every cancel handle (`ResultStream::cancel_handle`, `Session::cancel_handle`) is scoped to one execution and does nothing once it ended, so a late cancel never hits the next statement. After a cancel the stream drains the raw stream until the server confirms the end (bounded by `SERVER_CANCEL_GRACE`, 5 s); a driver that cannot confirm a dropped stream's end in bounded time closes the session. Engines whose cancel targets the connection (PostgreSQL cancel request, MySQL `KILL QUERY`, SQLite interrupt) rely on the busy rule; engines with addressed cancel send the execution's id (Trino query id, ClickHouse `query_id`, Elasticsearch task id, MongoDB `opId`). The cancel request of a stream is sent once, as a detached task, so it still reaches the server if the consumer drops a `next()` call mid-abort, and a retry waits for that same request;
- **idle cursors**: where the engine ignores a cancel while the backend waits for the client (PostgreSQL suspended portal), the cancel handle also flags the raw stream, whose next poll closes the cursor (`Close` + `Sync`, or `ROLLBACK`) and confirms the end instead of fetching more rows. pgwire also sets `idle_in_transaction_session_timeout`, and its integration tests pause a cursor, let the deadline pass and check that the locks it held are released;
- **metadata** (P4-A): calls only read and work on read-only sessions (I3); a page holds at most `PageRequest::limit` items (drivers clamp it to 10 000, or lower where a page needs a second statement) and internal results are byte-capped by the driver (I6); a dropped call is cancelled server-side where the engine can, and `Session::cancel_handle` also reaches a running metadata call; DDL text larger than 1 MiB is an error, never returned cut; a page whose rows pass a driver's 32 MiB internal cap fails with a non-fatal `Query` error ("use a smaller page or a filter"), the session and its transaction stay (security review L3). **DDL refusals the UI should expect** for objects of a kind declared in `metadata.ddl` (security review L5): pgwire base types (`TypeInfo::flavour == "base"`) and foreign tables (`TableInfo::flavour == "foreign"`); a pgwire table whose rebuilt DDL would need more than 1 600 columns or 10 000 constraints or indexes; sqlite indexes created by a constraint (`sqlite_autoindex_*`, an empty stored `CREATE`); mysqlwire definitions the user may not see (`SHOW CREATE` without the privilege); MariaDB sequences list with an empty `SequenceInfo` (no start or increment reported) but do have DDL. The UI can hide "Generate DDL" from these flavours and names; other refusals arrive as `Query` errors. `ObjectDetails` carries what the navigator, the object editor and completion need: `Column` (type, nullability, default, key, generated), `Table` (row estimate, flavour, `partition_key`), `Constraint` (kind, columns, definition), `ForeignKey` (columns, `referenced_table` as a path of the same driver, referenced columns, update / delete actions), `Index` (key parts, unique, primary, method, predicate), `Trigger` (timing, events, row / statement, enabled), `Routine` (function / procedure, bare name, arguments, return type, language), `Sequence`, `Type` (flavour, base type, enum labels), `Partition` (bound, method, row estimate, schema, sub-partitioned); comments are in `ObjectInfo::comment`, names are unquoted;
- **metadata** connections (when separate from the main one) use the same TLS settings, SSH route, read-only mechanism and property rules as the session; `PageRequest.filter` and object names never reach statement text as written: they are bound as parameters (pgwire for PostgreSQL, TimescaleDB and YugabyteDB, sqlite), or, where the protocol or the statement takes no parameter, inlined in a form that cannot change the statement: mysqlwire's text protocol has no bind parameters, so user input is a hexadecimal literal compared as a binary string (`CAST(col AS BINARY) = X'…'`) and `SHOW CREATE` names are backtick-quoted with backticks doubled; QuestDB binds them wherever it accepts a parameter, and `table_columns()`, `table_partitions()` and `SHOW CREATE` (which take a constant or a name) get a name only after it was found in `tables()` through a bound parameter and checked to hold no `'`, `"`, `\` or control character (security review L7). A SQL name filter is a literal substring (`escape_like`, `LIKE ? ESCAPE '!'`: `!` rather than a backslash, which MySQL's default `sql_mode` would treat as an escape in the statement text);
- **SSH**: `TunnelInfo.host_key` is the weakest host-key policy across every hop (`Disabled` < `AcceptNew` < `Strict`), and `TunnelInfo.hops` lists each hop with its own policy; `security_warnings()` reports `SshHostKeyNotVerified` when any hop is unverified, else `SshHostKeyAcceptNew` when the weakest hop accepts new keys without asking ([ADR-0016](adr/0016-ssh-rsa-and-host-key-policies.md) §2), plus `SshHopHostKeyNotVerified { hop }` or `SshHopHostKeyAcceptNew { hop }` per hop. `ninesql-ssh` reports `AcceptNew` hops as `HostKeyVerification::AcceptNew` (they used to be reported as `Disabled`). Drivers treat only an all-`Strict` tunnel as a protected transport.

**Classifier limit** (L4): the statement classifier recognises functions with side effects only from a known list (sequences, `dblink*`, backend control, `pg_promote`, `pg_switch_wal`, `pg_create_*` (restore points, replication slots), replication slots and origins, `pg_stat_reset*`, `pg_backup_*`, `pg_wal_replay_*`, `pg_logical_emit_message`, large-object functions (`lo_import`, `lo_export`, `lo_unlink` and the writers), and, since the P5 security review (L5), PostgreSQL advisory locks and unlocks (`pg_advisory_*`, `pg_try_advisory_*`, the `_xact` and `_shared` variants included), `pg_notify`, `pg_sleep*` and server file access (`pg_read_file`, `pg_read_binary_file`, `pg_ls_dir`, `pg_stat_file`), and, since L6 of the same review, every server directory listing `pg_ls_*` (`pg_ls_waldir`, `pg_ls_logdir`, `pg_ls_tmpdir`, `pg_ls_archive_statusdir`…), adminpack's `pg_file_*` (`pg_file_write`, `pg_file_unlink`, `pg_file_rename`, `pg_file_sync`) and `pg_logdir_ls`, index maintenance (`brin_summarize_new_values`, `brin_summarize_range`, `brin_desummarize_range`, `gin_clean_pending_list`), `txid_current` and `pg_current_xact_id` (they assign a transaction id), and the pre-10 `pg_switch_xlog` / `pg_xlog_replay_*`, and, since the second P5 security review, `pg_log_standby_snapshot`, `pg_sync_replication_slots`, `pg_truncate_visibility_map` (pg_visibility), `autoprewarm_dump_now`, `autoprewarm_start_worker` and `pg_prewarm` (pg_prewarm), `pg_buffercache_evict`, `pg_buffercache_evict_relation` and `pg_buffercache_evict_all` (pg_buffercache), `heap_force_kill` and `heap_force_freeze` (pg_surgery), the PostgreSQL 18 statistics writers (`pg_restore_relation_stats`, `pg_restore_attribute_stats`, `pg_clear_relation_stats`, `pg_clear_attribute_stats`) and `pg_stat_statements_reset`; MySQL-family `SLEEP`, `BENCHMARK`, `LOAD_FILE`, `MASTER_POS_WAIT`, `SOURCE_POS_WAIT`, `MASTER_GTID_WAIT`, `WAIT_FOR_EXECUTED_GTID_SET`, `WAIT_UNTIL_SQL_THREAD_AFTER_GTIDS` ([below](#mysqlwire-mysql-and-mariadb-p1-b)); SQLite `load_extension`), so such a call is `Unknown`: it is confirmed on production, refused by the edit service's filter check and by the transfer's "exports run reads only" rule. A name counts only right before `(` (comments and blanks between are skipped), unquoted or quoted, whatever the case and whatever its schema qualification (`pg_catalog.pg_sleep(…)`, `"pg_catalog"."pg_sleep"(…)`, `` `sleep`(…) ``); a column with the same name stays a read. `set_config(…)` is `ChangesAccessMode`. A user-defined function or procedure called from a `SELECT` is classified `Read`: read-only sessions stay protected by the engine-side mechanism, but the production confirmation is not asked for such calls, and an engine declared `ClientSideOnly` cannot stop them. PostgreSQL `U&"…"` names are decoded before matching; a malformed escape or `UESCAPE` makes the statement `Unknown`.

**Statements that run another statement, and `CREATE OR REPLACE`** (P1-E review M1, L1): an `EXPLAIN` that runs its statement is classified as the statement it runs, at least `Read`. It runs when the option list is parenthesised (PostgreSQL `EXPLAIN (…)`, whose option names may be quoted or `U&`-escaped: `EXPLAIN ("analyze") DELETE FROM t`, `EXPLAIN (FORMAT JSON, "analyze" on) …` and `EXPLAIN (U&"analyze") …` really delete on PostgreSQL 18) or when `ANALYZE` / `ANALYSE` appears in any form (bare, quoted, backquoted, `U&`-escaped). `DESCRIBE` / `DESC` follow the same rule (MySQL / MariaDB synonyms of `EXPLAIN`: `DESC ANALYZE DELETE …`); `DESCRIBE t` stays `Read`. The class is the riskiest of the statements starting at every explainable keyword after `EXPLAIN`, so a misread option cannot hide the real start, and `Unknown` when the text after the options is not an explainable statement or the option list is unbalanced. The reading is strict: `EXPLAIN (FORMAT JSON) DELETE FROM t`, which PostgreSQL does not run, also asks for confirmation in production (the pgwire `Json` explain of a `DELETE` therefore needs a confirmation too). A plain `EXPLAIN DELETE …` and SQLite's `EXPLAIN [QUERY PLAN] …` (SQLite never runs the explained statement) are `Read`. A statement starting with `ANALYZE` / `ANALYSE` is `Unknown`: MariaDB `ANALYZE [FORMAT=JSON] <statement>` runs the statement (tested on MariaDB 11.8: `ANALYZE DELETE` deletes), elsewhere it writes statistics. MySQL 8.4 `EXPLAIN ANALYZE` runs the plan of a multi-table `DELETE` / `UPDATE` without keeping the changes (single-table DML is "not executable by iterator executor"); it is classified as the statement anyway. `CREATE OR REPLACE …` (function, view, procedure, trigger, rule; MySQL / MariaDB views, MariaDB tables and sequences) silently overwrites an existing object: it is `Destructive`, so it asks for confirmation on connection types that confirm destructive statements (production), where a plain `CREATE` (`Ddl`) does not. Tested engine-side in pgwire and mysqlwire: in a read-only session these forms are refused client-side, and sent past the classifier with a forged `Read` class they fail with `25006` / `1792`, no row deleted.


### Script splitting and classification (P3-D, F-SQL-18)
**Two splits.** `Dialect::split_statements` is what a driver sends in one protocol call; `ensure_single_statement` refuses text it splits into several spans. `Dialect::split_script` is for "execute script": it returns `ScriptItem`s in order, each with a byte span (`StatementSpan`), its kind and the line / column of its start and end (`TextPosition`: 1-based lines ending at `\n`, 1-based columns in Unicode scalar values, `LineIndex` / `position_at` for engine error offsets, F-SQL-12). Kinds: `Statement` (run its text with `Session::execute`, one call per item; its text passes `ensure_single_statement` and is classified like any statement), `ClientDirective` (MySQL `DELIMITER`, applied by the splitter and never sent), `Refused(ScriptRefusal)` (`CopyFromStdin`, `PsqlMetaCommand`, `MysqlClientCommand`, `InvalidDelimiter`; never sent, and a caller running the script stops before it or refuses the script). A span runs from the first token to the last, so leading comments and the terminator are excluded; MySQL executable-comment openers and closers are part of it (`/*!40101 SET NAMES utf8mb4 */` is sent whole, with its version condition).

| Dialect | Splitting rules (on top of quotes and comments) |
|---|---|
| pgwire | psql's: a `;` ends a statement only outside parentheses (`CREATE RULE … DO ALSO (INSERT …; INSERT …)` is one statement) and outside the `BEGIN … END` of a `CREATE [OR REPLACE] FUNCTION \| PROCEDURE` (SQL-standard `BEGIN ATOMIC` bodies, PostgreSQL 14+; `BEGIN` / `CASE` / `END` counted outside parentheses). Dollar quotes (ASCII and non-ASCII tags), `E'…'` strings, `standard_conforming_strings` (from the session), nested block comments, `U&'…'`, a carriage return ending a `--` comment. `COPY … FROM STDIN` and its inline data (from the line after the `;` the lexer found up to a line holding `\.`, or the end) are one `Refused(CopyFromStdin)` item: data lines are never split or sent (the driver refuses COPY input anyway). A statement starting with `\` is a psql meta-command, refused to the end of its line |
| mysqlwire | The mysql client's `DELIMITER` at the start of a statement (case-insensitive, to the end of its line; refused when empty or holding a backslash, a quote, `#`, `--` or `/*`, keeping the previous delimiter). With a custom delimiter, the text between two delimiters (found in code only: not in strings, identifiers, comments or executable comments) is split again with `split_statements`, so a statement item is always one statement. A stored program (`CREATE [OR REPLACE] [ALGORITHM = …] [DEFINER = …] [SQL SECURITY …] [AGGREGATE] PROCEDURE \| FUNCTION \| TRIGGER \| EVENT … BEGIN … END`, the kind right after those clauses; the definer is skipped up to the next clause keyword, so dotted hosts such as `root@127.0.0.1` and quoted forms work) and a MariaDB `BEGIN NOT ATOMIC … END` block are one statement without `DELIMITER` too. `NO_BACKSLASH_ESCAPES` and `ANSI_QUOTES` from the session; `#` and `-- ` comments (`--x` is not a comment); executable comments `/*! … */` and `/*M! … */` are code, and a `;` inside one still ends a statement, as for the mysql client (so `SELECT 1 /*! ; DROP TABLE t */` is refused as two statements). A statement starting with `\` is a client command, refused |
| sqlite | SQLite's tokenizer through `lexer_view` (`[…]` and backquoted identifiers, Tcl-style variables, no backslash escapes, block comments that do not nest). A `[EXPLAIN [QUERY PLAN]] CREATE [TEMP] TRIGGER … BEGIN … END` is one statement: the body ends at the first statement that starts with `END` (right after a `;`, as in SQLite's grammar and `sqlite3_complete`), so `CASE … END` inside it does not end it |

**Contract for callers running a script** (security review H2; rustdoc of `Dialect::split_script`). The items are valid only for the lexical modes in force when the script was split (MySQL `NO_BACKSLASH_ESCAPES` / `ANSI_QUOTES`, PostgreSQL `standard_conforming_strings`): after `SET SESSION sql_mode = 'NO_BACKSLASH_ESCAPES'`, `UPDATE t SET a = 'x\' -- ' WHERE id = 1` has no `WHERE`. So the caller (the core's "execute script", P3-C):
1. classifies each item with the session's dialect **just before running it**, and confirms from that class only;
2. after **every** item, compares the session dialect's `lexical_rules()` with the rules the pending items were split with, and when they differ drops the pending items and splits on with the new dialect from the end of that item (re-review L2: a `SET` changes them, but so can a `ROLLBACK`, `COMMIT` or `ROLLBACK TO SAVEPOINT` that undoes a `SET`, or a function calling `set_config`; `item_may_change_lexical_modes` names only the obvious cases). `lexical_rules()` captures every mode the splitters use (mysqlwire reports `ANSI_QUOTES` through `double_quote_backslash`).

To stay linear, the caller runs the script lazily (re-review M1): `Dialect::split_script_ahead(script, from, &state)` returns the next few items from `from` (the `end` position of the last item handled, or `TextPosition::START`), each exactly as a full split would give it, for the cost of a small window of text; `Dialect::script_state_after` keeps the `ScriptState` (the MySQL `DELIMITER` in force) up to date item by item, so nothing before `from` is read again. A `ScriptState` delimiter that the `DELIMITER` directive would refuse (empty, with whitespace, a backslash, a quote, `#`, `--` or `/*`) can never be in force: mysqlwire returns one `Refused(InvalidDelimiter)` item for the rest of the script (`;` means the default); pgwire and sqlite have no directive and ignore a state delimiter. `split_script_from` still exists but splits the whole rest (and, in mysqlwire, re-reads the text before `from` for the delimiter). `conformance::script_plan` is the reference loop, tested in pgwire and mysqlwire (`script_is_resplit_after_a_lexical_mode_change`, `rollback_undoing_a_mode_change_resplits`, `alternating_mode_changes_run_in_linear_time`).

**Cost.** Splitting and positions are linear: positions are computed with a forward cursor; pgwire and mysqlwire split in windows sized from the last step (512 B to 64 KiB), so a meta-command, a `COPY` block or a `DELIMITER` every few bytes costs a few hundred bytes of lexing; mysqlwire counts a stored-program body's blocks incrementally and finds a custom delimiter with an early-stopping scan. Measured in debug builds: 200 000 `SELECT 1;` on one line 0.07 s (ANSI) to 0.2 s (pgwire, mysqlwire); `CREATE PROCEDURE … BEGIN` with 32 768 statements 0.03 s; 32 768 `\echo` lines 0.56 s; 16 384 `COPY` blocks 0.43 s; 16 384 `DELIMITER` directives 0.33 s. Running a script through `script_plan` when every statement changes the lexical modes (about 276 KB, 7 000 to 8 000 mode changes): 0.26 s on mysqlwire (0.05 s under a custom `DELIMITER`), 0.22 s on pgwire. Under a custom `DELIMITER`, a lazy step splits a window of the block too, not the whole block up to the next delimiter (security review L2: a 1 MB `DELIMITER $$` block of alternating `SET sql_mode` statements, re-split after each, took about two minutes in a release build; 300 KB of it now takes about 1 s in a debug build, `long_custom_delimiter_block_with_mode_changes_runs_in_linear_time`); the window keeps a 64-byte margin before its end, more than the lexers' lookahead, so a delimiter found in it is the first of the whole rest, and each step equals `split_script_from` at that point (differential tests at every item boundary). Bounded perf tests run in each driver's `tests/dialect.rs`.

A heuristic mistake in a merge cannot run an unclassified statement: PostgreSQL's extended protocol, MySQL without `CLIENT_MULTI_STATEMENTS` and SQLite's `prepare` each refuse a second statement in one call, and the classifier splits on every `;` whatever the merges.

**Classifier additions** (P3-D, security-relevant; on top of the rules above):
- MySQL / MariaDB **conditional executable comments** may or may not run: `/*!NNNNN … */` runs only from server version `NNNNN`, `/*M! … */` only on MariaDB (a plain comment for MySQL). The classifier tries every combination of them run or skipped and keeps the riskiest, so `DELETE FROM t /*!99999 WHERE 0 */` and, on MySQL, `UPDATE t SET a = 1 /*M! WHERE id = 1 */` are `Destructive` (tested: both update every row on MySQL 8.4). More than eight conditional comments in one text, a text longer than 64 KiB holding any (security review L2), an unterminated one, one whose body holds `/*` or `*/` in a token (an engine that skips it ends it elsewhere), or a `;` inside one, make the text `Unknown`. So does any `;` inside an executable comment: the piece after it starts inside the comment and reads differently once sent alone, and a piece of comment markers only is no statement (re-review L1). Consequence: mysqldump view headers (`/*!50001 CREATE ALGORITHM=… */ /*!50013 DEFINER=… */ /*!50001 VIEW … */`) are `Unknown` and need confirmation in production;
- MySQL **user variables** (`@name`, with `.` and `$` in the name) are one token, never a keyword, and **`$` is an identifier character** in MySQL / MariaDB (also at the start) and SQLite: `UPDATE t SET a = @WHERE` and `DELETE FROM t$WHERE` are `Destructive` (tested on MySQL 8.4 and MariaDB 11.8: `@WHERE` is `NULL` and every row is updated). SQLite variable names (`:WHERE`, `@WHERE`, `$WHERE`, `#WHERE`) are neutralised by `lexer_view`;
- **PostgreSQL line comments end at a carriage return** as at a line feed (PostgreSQL's lexer; MySQL and SQLite end them at a line feed only): `SELECT 1 --x\r, pg_terminate_backend(42)` is `Unknown`;
- **`BEGIN`** is `Transaction` only when every word after it is a transaction mode (`WORK`, `TRANSACTION`, isolation levels, `READ ONLY` / `READ WRITE`, `[NOT] DEFERRABLE`, SQLite `DEFERRED` / `IMMEDIATE` / `EXCLUSIVE`); MariaDB `BEGIN NOT ATOMIC …` (a compound statement that runs its body) and `BEGIN ATOMIC …` are `Unknown`;
- **triggers, rules and events**: a `CREATE TRIGGER` / `CREATE RULE` is classified as the riskiest statement of its body (after `BEGIN`, `DO` or `FOR EACH ROW | STATEMENT`, so the header's `AFTER UPDATE OF c ON t` does not count), at least `Ddl`: a trigger whose body deletes every row of a table is `Destructive`. A MySQL / MariaDB `CREATE EVENT` is `Unknown` (its body may run at once);
- **keywords used as names** (security review H1): a keyword right after `.` or `AS` is a name (`RETURNING 1 AS where`, `x.where`, ``(SELECT 1 AS `where`) x … x.where``), so it never counts as the `WHERE` of a `DELETE` / `UPDATE`, the `TRANSACTION` of `START TRANSACTION` (which must follow `START` directly), the main statement of a `WITH`, or the object kind of a `CREATE`; `SET "transaction" …` names a setting. Before looking for a `CREATE`'s object kind, the classifier skips `[OR REPLACE] [ALGORITHM = x] DEFINER = user[@host]` as the lexer reads it (`CURRENT_USER[()]`, a dotted `@host`, quoted user and host), so `CREATE DEFINER = view@localhost TRIGGER … DELETE …` is a trigger; `CREATE SCHEMA` counts only right after `CREATE` (re-review L3); Every keyword test whose presence lowers a class follows this rule, so a name can only over-classify;
- **identifiers have no backslash escapes in PostgreSQL** (security review M1): with `standard_conforming_strings = off` a backslash escapes in strings only, not in `"…"` or `U&"…"` (`LexicalRules::double_quote_backslash`, on for MySQL / MariaDB unless `ANSI_QUOTES`): `DELETE FROM rv AS "x\" -- " WHERE id = 1` is `Destructive`;
- **`CREATE SCHEMA` elements** (security review M2): a top-level `GRANT` / `REVOKE` inside a `CREATE` makes it at least `Destructive`, and PostgreSQL `CREATE SCHEMA … CREATE … GRANT …` takes the riskiest class of its elements (at least `Ddl`);
- not changed, by design (ADR-0007 §3 does not list them): `MERGE`, `REPLACE INTO`, `INSERT … ON CONFLICT DO UPDATE` and `INSERT … ON DUPLICATE KEY UPDATE` are `Write`.

**Corpus and property tests.** `crates/ninesql-driver-api/tests/corpus/classification.txt` holds the statements with their expected class per dialect (`pg`, `mysql`, `mariadb`, `sqlite`), including every past bypass (Tcl variables, `EXPLAIN ("analyze")`, the `SET TRANSACTION …, READ WRITE` comma form, `WITH` without a main statement) and the ones above; the format is documented on `conformance::CLASSIFICATION_CORPUS`. Each driver runs it in its `tests/dialect.rs` (`conformance::assert_classification_corpus`, with the session modes `no_backslash_escapes`, `ansi_quotes`, `scs_off`), which also checks that a leading `SELECT 1;` never lowers a class and that a script never classifies below one of its `split_script` statements. Property tests per driver (`assert_script_split_invariants`, `assert_join_split_roundtrip`, `STATEMENT_POOL`): spans ordered, on `char` boundaries and with matching positions on random text and token soup; every statement item is at most one statement for `split_statements`; joined statements split back to themselves with their class, also under a custom `DELIMITER`; a joined script classifies as its riskiest statement; noise before a statement never hides it. Engine tests (`scripts_split_as_*`) run scripts through `split_script` against PostgreSQL 18, MySQL 8.4, MariaDB 11.8 and SQLite 3.54 and check that every item runs and does what the split says.

**Limits.** A piece of a MySQL script that starts inside an executable comment (after a `;` in it) is lexed on its own without that context and may split further: the driver then refuses it as several statements (fails closed). A statement whose last token is followed by a comment ends at that token, so a trailing MySQL `--` (a comment only at the end of a text) may change meaning when sent alone; nothing can follow it. psql variables (`:name`), `\g` inside a statement and mysql client commands other than `DELIMITER` and backslash commands are not interpreted.

The conformance helpers of the `mock` feature are reused by every driver's integration tests: `conformance::assert_reserved_properties_rejected`, `assert_read_only_refuses_writes` (with `writes_for(engine)`: the engine-neutral `WRITES` plus the family's access-mode statements), `assert_multiple_statements_refused`, `assert_access_mode_change_detected`, `assert_stale_cancel_ignored`, `assert_batches_within_budget` (batch rows, batch / row / value bytes, documents included), `assert_identifier_quoting` (with `IDENTIFIER_SAMPLES`; `assert_dialect_quoting_roundtrip` without a server) and `assert_verify_full_rejects_untrusted_certificate` (driver-supplied parameters for a TLS endpoint signed by a test CA, the CA file and a host name the certificate does not cover: `verify-full` with the CA must connect (positive control, so a server without TLS cannot pass), `verify-full` and `verify-ca` without the CA must fail with a TLS error, and with the CA but the wrong `server_name` `verify-ca` connects while `verify-full` fails; no TLS error may echo the password).

The mock driver (feature `mock` of `ninesql-driver-api`, engine id `mock`) declares every capability by default and accepts overrides so UI tests can check that undeclared features are hidden. It reserves one extra property key (`mock_backdoor`), does not retain the secret after connect, cancels like PostgreSQL (the simulated backend stops whatever runs; handles are execution-scoped) and simulates a self-signed TLS endpoint (`self-signed.mock.invalid`).

## DML generation (P5-B)
Row edits (F-DATA-04) and the "SQL `INSERT`" export and copy (F-XFER-01, F-DATA-06) go through `ninesql_driver_api::dml`. It changes no capability: the drivers already declared `editing`.

**API.** `dml::generate(dialect, &caps.editing, &DmlRequest)` returns a `DmlStatement`; `dml::generate_batch` does it for several rows (one statement per row, `DmlBatch::preview_script` joins the previews with `;`); `dml::insert_preview(dialect, table, values)` renders an export `INSERT` without editing capabilities (nothing is executed); `cell_value(batch, column, row)` reads a grid cell as a `Param` from the batch itself, so a column the batch flags `ninesql.truncated` is refused; `choose_row_key(&[KeyCandidate])` picks the key from metadata, with candidates built by `KeyCandidate::from_index(&IndexInfo, not_null)` from the driver's index flags only (`valid`, `deferrable`, `nulls_distinct`, per-part `expressions`, `predicate`): invalid, deferrable, partial and expression indexes never count (review M1). A request names the table (unquoted path), the columns (`DmlColumn`: name plus `ColumnType`, the Arrow type and the `ninesql.type` engine type name, `DmlColumn::from_field`), the key columns with their original values and a `KeyKind`, and the new values (`ColumnChange` holds the original and the new value). Each `DmlStatement` has:
- `statement`: what is **executed**, every value a bound parameter, never inlined;
- `preview`: the same statement with typed literals, for the DML preview, copy and export;
- `expected_rows` (always 1) and `check_affected(count)`: the core runs each save in an explicit transaction and rolls it back when an update count is not exactly 1 or is unknown (rustdoc contract); a MySQL-family table whose storage engine is not transactional (`TableInfo::transactional == Some(false)`: MyISAM, MEMORY, ARCHIVE, CSV, Aria…) cannot be rolled back, so the core refuses to edit it, with no override; on the MySQL family an unknown value (`None`) is refused too (review M2, P5-A core review M1);
- `unchecked_columns`: edited columns left out of the optimistic-concurrency `WHERE` because the engine has no reliable `=` for their type;
- `lexical_rules`: the session modes in force when the preview was rendered (informational: literals do not depend on them).

**Rules, all engines.** Identifiers are quoted with the dialect's quoting and schema-qualified; empty names and NUL are refused, and so are names the engine would truncate (PostgreSQL over 63 bytes of UTF-8, MySQL family over 64 characters or outside the BMP). `UPDATE` and `DELETE` always have a `WHERE` on the key: an empty key is refused (`DmlError::NoKey`, the grid stays read-only), a `NULL` key value is refused unless the key is a unique key whose `NULL`s are not distinct (PostgreSQL `NULLS NOT DISTINCT`, then `IS NULL`; such a key is refused when `Dialect::supports_unique_nulls_not_distinct()` is false: every engine but PostgreSQL 15+, TimescaleDB included by its server version, YugabyteDB 11 excluded), and a key column without reliable equality is refused. `Concurrency::EditedColumns` adds the original values of the edited columns (`IS NULL` for a `NULL`). An edit kind the driver does not declare is refused before anything is rendered (`DmlError::NotSupported`; QuestDB declares none). A cut grid value (`ninesql.truncated`) is refused by `cell_value`. Self-check: the parameterized text and the preview must each split as exactly one statement and classify as `Write` with the session dialect, and the preview holds no NUL, or generation fails. Errors name columns (escaped, cut), never values; `Debug` never shows the preview or values.

**Preview literals.** Every literal reads back as exactly the value the bound parameter gives, **in every lexical mode of the engine** (a preview or export may be replayed in another session; security review H1) (tested by running both forms on each engine and comparing the rows). Control characters, line and paragraph separators, bidirectional controls and invisible formatting characters (`dml::needs_escape`) are never shown raw inside a string literal: the SQL editor strips or flags some of them (ADR-0025 §3). Dates and timestamps are limited to the years 1 to 9999.

| Engine | Strings | Bytes | Numbers | Booleans | Date / time | Other types | Refused |
|---|---|---|---|---|---|---|---|
| PostgreSQL, TimescaleDB, YugabyteDB | `'…'` with `''`; `E'…'` when the text holds `\`, a control or an invisible character (`\\`, `\n`, `\t`, `\uXXXX`): independent of `standard_conforming_strings` | always `E'\\x…'::pg_catalog.bytea` | bare only when the value's kind matches the column's (an integer in an integer column, a float in a floating-point column, a decimal in `numeric`); `'NaN'`, `'Infinity'`, `'-Infinity'`, `'-0.0'` and mismatched kinds quoted and cast | `TRUE` / `FALSE` in a boolean column, `'t'` / `'f'` elsewhere | the text the driver binds, cast to the column type: `'2024-01-01'::pg_catalog.date`, `'… +00'::timestamp with time zone`, `'12:00:00'::time without time zone` | quoted text cast to the column's built-in type, qualified `pg_catalog.<type>` unless the type is spelled with SQL keywords (`integer`, `interval`, `timestamp with time zone`…, which no user type can shadow): `pg_catalog.uuid`, `pg_catalog.jsonb`, `interval`, `integer[]` (any built-in base type with `[]`); typmods dropped; an unknown or user-defined type stays an untyped literal, resolved like the parameter; never `character` / `bit` (a cast without length truncates) | NUL in text |

**Equality used in `WHERE`.** Not comparable, so never a key and left out of the concurrency guard (`unchecked_columns`): PostgreSQL `json`, `xml` and the geometric types (`point`, `line`, `lseg`, `box`, `path`, `polygon`, `circle`) and their arrays; MySQL family `JSON`, spatial types, `VECTOR`, `BIT` (compared with a hexadecimal literal it is read as a number) and `FLOAT` (the text protocol sends about six significant digits, so the value read back is not the stored one). SQLite: the dialect compares every column type (each value is written with the storage class the driver binds, so `=` / `IS` match the stored value exactly; REAL values are read back exactly).

**Update counts.** mysqlwire now connects with `CLIENT_FOUND_ROWS`: an `UPDATE`'s count is the number of rows **matched** (as JDBC drivers report it), not the number whose value changed, so an edit that writes an unchanged value still reports one row. This also changes the update count shown for user `UPDATE` statements on MySQL, MariaDB and TiDB. PostgreSQL and SQLite already count matched rows.

**Metadata for editing (review M1, M2).** `IndexInfo` carries `valid`, `deferrable`, `nulls_distinct`, `partial` and per-part `expressions` (defaults are conservative: not valid, unknown parts). pgwire reports `unique` as `indisunique` and sets `valid` (`indisvalid` and `indisready`) and `deferrable` (`indimmediate = false`), which key selection refuses; it reads `indnullsnotdistinct` where the server has it and flags expression parts (`indkey = 0`); mysqlwire flags functional key parts (MySQL 8); sqlite flags expression parts (`cid = -2`) and partial indexes (`partial`, with `predicate` left `None`: its text is not read). `TableInfo::transactional` is `Some(true)` for PostgreSQL and ordinary SQLite tables, read from `information_schema.TABLES.ENGINE` on the MySQL family (`None` for views and unknown engines, a SQLite virtual table and QuestDB). A SQLite `INTEGER PRIMARY KEY` (rowid alias) has no index entry: the core takes it from `ColumnInfo::primary_key`.

**Tests.** Offline (`tests/dml.rs` of each driver, `dml` unit tests of the API): property tests with hostile identifiers (quotes, backticks, brackets, NUL, newlines, bidirectional and invisible characters, reserved words, `/*!`, `$$`, Tcl variables) and hostile values in every lexical mode (PostgreSQL `standard_conforming_strings` on and off, MySQL `NO_BACKSLASH_ESCAPES` and `ANSI_QUOTES`): generation either refuses with a typed error or yields texts that split as one statement and classify as `Write`; every literal stays one token and is identical in every mode of its dialect (no backslash in a MySQL literal); a batch preview splits into one statement per row. Engine tests (PostgreSQL, TimescaleDB, MySQL, MariaDB, TiDB against `dev/`; SQLite on temporary files): insert, update with the concurrency guard (then the same statement with stale originals changes nothing) and delete through the parameterized form on one row and through the preview on another, with composite keys, every common type and hostile values; the rows must match after each step; a property test does the same with random values (64 cases on PostgreSQL, 48 per engine and mode on the MySQL family, 256 on SQLite); no key and a `NULL` in a nullable unique key are refused, a `NULLS NOT DISTINCT` key matches with `IS NULL`; hostile schema, table and column names round-trip; on the MySQL family, previews and updates rendered under `NO_BACKSLASH_ESCAPES,ANSI_QUOTES` are replayed in a default-mode session and the reverse (including `\'' -- '`), giving the same rows and leaving a victim row unchanged; index flags and `transactional` are checked on live servers (an invalid index from a failed `CREATE UNIQUE INDEX CONCURRENTLY`, a deferrable constraint, expression, partial and `NULLS NOT DISTINCT` indexes on PostgreSQL; InnoDB and MyISAM tables and a functional index on MySQL). YugabyteDB was not run (its container needs more free disk than the test machine had).

## Secret retention after connect (L5)
Declared per driver in `Capabilities::retains_secret_after_connect`. It covers **every** authentication after `connect` returns: automatic reconnects, and auxiliary connections or requests that need credentials (a cancel on a new connection, a separate metadata connection, a keep-alive). When `false`, the driver drops every `Secret` before `connect` returns: the auxiliary connections it needs are opened and authenticated during `connect`, and a reconnect needs fresh parameters from the core (keyring, vault or prompt). When `true`, the secret stays in the driver's memory, zeroized on drop, only for those uses, and is dropped with the session. No driver declares `true`.

## pgwire: PostgreSQL (P1-B)
`ninesql-driver-pgwire` serves the engine ids `postgresql` and, since P4-C, `timescaledb`, `yugabytedb` and `questdb`, each with its own capabilities ([below](#wire-compatible-engines-p4-c)). This section describes PostgreSQL; the other engines differ only as stated there.

**Client.** The driver speaks the protocol itself on top of the message codec of `postgres-protocol` (rust-postgres, MIT / Apache-2.0), tokio and rustls with the `ring` provider, instead of `tokio-postgres` ([ADR-0003](adr/0003-supported-engines-v1.md) allows replacing a client): it needs `ParameterStatus` after every statement (read-only verification, lexical modes), full control of portals (`Close` + `Sync` on cancel), a cancel request over the session's TLS settings and a `DataRow` reader that cuts values while reading them. SCRAM-SHA-256 and md5 are implemented in the driver with `ring` and `md-5` so every buffer derived from the password is zeroized. No C library, no OpenSSL (`openssl-probe`, pulled by `rustls-native-certs`, only locates the system CA files).

**Connect.**
- Settings travel as startup parameters (`user`, `database`, `application_name`, `client_encoding=UTF8`, `DateStyle=ISO`), never as a DSN. Driver properties: the global rule plus the extra keys above are refused, then only an allowlist is accepted and sent as startup parameters: `search_path`, `TimeZone`, `statement_timeout`, `lock_timeout`, `work_mem`, `client_min_messages` (any other key fails the connect with `InvalidParams`, naming the key only). A `search_path` value that lists `pg_catalog` after another schema is refused. This check is best-effort: it reads the property value only, so a later `SET search_path` or a `set_config` call in a statement is not checked, and `pg_temp` keeps PostgreSQL's own search rules. The driver's internal queries do not rely on it (schema-qualified, below). A DBeaver import carries pgjdbc properties (JDBC URL parameters, driver properties) that are not on this allowlist: until the import maps or drops them (P2-C), such a connection fails at connect with `InvalidParams`.
- TLS: `disable`, `require` (encrypted, certificate not verified; handshake signatures still checked), `verify-ca` (chain checked, host name not checked), `verify-full` (chain and host name). Trust anchors follow libpq's `sslrootcert`: `verify-ca` **requires** `TlsConfig::ca_file` and trusts only that file (chain-only checks against the public roots would accept any publicly certified server); `verify-full` trusts only the CA file when one is set, and the platform trust store otherwise. (The rustdoc of `TlsConfig::ca_file` in `ninesql-driver-api` states the same rules, [ADR-0019](adr/0019-tls-ca-file-semantics.md).) The name verified is `TlsConfig::server_name` when set (SSH tunnel endpoints), else the endpoint host; an IP address is verified against IP SANs. A server that refuses TLS fails the connect: there is never a fallback to plain text. Client certificates: PEM chain and unencrypted PEM key (an encrypted key is refused for now). Cancel requests use the same TLS settings.
- Authentication: SCRAM-SHA-256 (without channel binding: `SCRAM-SHA-256-PLUS` is not offered yet) and md5; GSSAPI / SSPI / Kerberos are refused. The server's SCRAM signature must be verified before `AuthenticationOk` is accepted, a second authentication request is refused, and the server may ask for at most 1 000 000 PBKDF2 iterations (computed off the async workers). A transport counts as protected only with `verify-ca` / `verify-full` TLS, or an SSH tunnel whose hops all verify host keys and whose local end (endpoint host and resolved peer address) is loopback; `require` is not protected. Such a tunnel protects the client → SSH server leg only: from the SSH server to the database, traffic is protected only by the connection's TLS mode, so a cleartext password crosses that leg unencrypted when the database does not run on the SSH server itself (the connection dialog warns about it when TLS is disabled; treating a tunnel as protected only when its target is loopback on the SSH server is an optional follow-up). A cleartext password is refused over an unprotected transport; md5 is allowed there with a logged warning (the digest can be cracked offline). With `ConnectParams::password_exchange = ScramOnly` (declared in `connect.password_exchanges`), only SCRAM-SHA-256 is accepted, whatever the transport: a request for md5 or a cleartext password, and a server that sends `AuthenticationOk` without a verified SCRAM exchange (trust), fail the connect with `Auth` before anything derived from the password is sent (libpq `require_auth=scram-sha-256`). This stops method downgrades only: there is no channel binding (the client sends `n,,`; `SCRAM-SHA-256-PLUS` with `tls-server-end-point` is a follow-up), so with TLS `require` or `disable` a man in the middle that relays the exchange to the real server still passes. `verify-full` (or `verify-ca` with a private CA) is what protects against a man in the middle. Statement text is logged at `trace` level only when `may_log_statements()`.
- Internal queries (navigator, type-name lookup, read-only read-back, the idle-timeout setting) never depend on the session's `search_path` (CVE-2018-1058 class): every operator is written `OPERATOR(pg_catalog.…)` and every function, type, collation and relation is schema-qualified; a test plants better-matching user operators on the `search_path` and checks they never run. Internal results are bounded (the server is asked for at most the rows needed, and the driver caps rows and bytes).
- Supported servers: tested on PostgreSQL 18 (`dev/`); catalog queries need PostgreSQL 11 or later (`prokind`).

**Execute.** Extended protocol, one statement per call (`ensure_single_statement` with the session's lexical rules: `standard_conforming_strings` from `ParameterStatus`; a client encoding other than UTF8 closes the session). The statement is parsed and described first (`Parse` + `Describe`), then:
- `SELECT`-class statements outside a transaction run in a driver-implicit read transaction (`BEGIN`, then `idle_in_transaction_session_timeout` set to 300 s for the transaction, unless a stricter non-zero value is already in force) through a portal fetched `batch_rows` rows per `Execute` (fewer when rows are wide, so one fetch stays near `max_batch_bytes`): nothing runs ahead of the consumer. `COMMIT` only when the portal ran to completion; a dropped stream, a cancel, a timeout or an error end with `Close` + `ROLLBACK` without fetching more (idle-cursor rule), even while the consumer is not polling, so a read-class statement with side effects is never partially committed. The 300 s server-side bound ends a session whose consumer never comes back (PostgreSQL then terminates the session).
- Inside the user's transaction (manual commit, or an explicit `BEGIN`) the same portal fetch runs without `BEGIN` / `COMMIT`; cancel or drop sends `Close` + `Sync`.
- Other row-returning statements outside a transaction (`INSERT … RETURNING`, `CALL`, statements the classifier does not see as reads) run in one `Execute`, read incrementally from the socket (TCP back-pressure). A stream dropped while such a statement runs is cancelled by the driver if no row arrived yet; once rows arrive (the write is done) it is drained without cancel, bounded by 5 s, after which the session is closed.
- Manual-commit mode starts a transaction (`BEGIN`) before the first statement that is not transaction control; switching back to auto-commit commits (JDBC semantics).

**Types** (Arrow): `bool` → Boolean; `int2` / `int4` / `int8` → Int16 / Int32 / Int64; `oid` → UInt32; `float4` / `float8` → Float32 / Float64; `bytea` → Binary; `date` → Date32; `time` → Time64(µs); `timestamp` → Timestamp(µs); `timestamptz` → Timestamp(µs, UTC). Everything else is `Utf8` in PostgreSQL's text form with the type name in `ninesql.type`: `numeric` (no faithful Arrow decimal for `NaN`, infinities and unconstrained precision), `interval`, `uuid`, `json` / `jsonb`, arrays (text form for now), `timetz`, network, geometric, range, bit, text search, enums and domains (names looked up in `pg_type`). `text`, `varchar`, `char(n)`, `name` are plain `Utf8`. Infinite dates and timestamps become NULL, flag the column `ninesql.truncated` (not editable) and add a warning notice.

**Results.** Values are cut to `max_value_bytes` / `max_row_bytes` while the `DataRow` is read (the rest is skipped on the socket, never buffered) and flagged `ninesql.truncated`. Notices are stream items (severity, SQLSTATE, message and hint), delivered in chunks of at most 1 000 notices / 1 MiB; in the driver's own round trips, notices beyond twice that are dropped and summarized in one warning; `DETAIL` is left out of errors and notices because it often quotes row values. Update counts come from the command tag (`INSERT`, `UPDATE`, `DELETE`, `MERGE`, `COPY`, `SELECT … INTO`); `NULL` for other commands. Not offered: `COPY FROM STDIN` (refused with `CopyFail`), `COPY TO STDOUT` (output discarded, then an error), `LISTEN` / `NOTIFY` (notifications dropped), several result sets per statement.

**Cancel and timeout.** `CancelRequest` with the backend key on a new connection to the session's resolved address, with the same TLS settings; handles are execution-scoped (`ExecutionTracker`) and the session stays `Busy` until `ReadyForQuery` confirmed the end. Timeouts go through the `ResultStream` watchdog (`server_side_timeout = false`).

**Metadata** (P4-A) shares the session's connection: a navigator call while a result streams fails with `Busy`. Filters, names and cursors are bound parameters; filters are literal substrings (`LIKE $1 ESCAPE '!'`); pages are keyset pages (by name, by column number for columns), at most 10 000 items. Paths: `[Schema]`; under a schema, tables, views, materialized views, sequences, types and routines; under a table or a partition, columns, constraints, foreign keys, indexes, triggers and partitions (which nest); under a view, columns and triggers; under a materialized view, columns and indexes. Partitions are listed under their parent, not among the schema's tables. A relation is resolved to its oid first (one more statement per partition level), then every listing binds the oid. Routines are listed with their identity arguments (`f(integer, text)`) so overloads stay distinct; aggregates, window functions and the constructors created with a range type are not listed. Types exclude array types, table row types and the implicit multiranges. Key columns travel hex-encoded (a PostgreSQL identifier may hold any character but NUL). The catalogs are not listed: a PostgreSQL session is bound to one database (`Catalog` is not declared). A dropped call sends a cancel request scoped to its execution, and only while its statement runs. In an open transaction every navigator statement runs inside `SAVEPOINT ninesql_meta`, released on success and rolled back to on an error or a cancel (allowed in read-only transactions), so neither a server error nor the cancel of an abandoned call aborts the user's transaction (security review M1; tested: `BEGIN`, a write, an abandoned and a failing navigator call, then the transaction commits the write). The parts of a rebuilt `CREATE TABLE` are read whole (values up to 1 MiB) and a part that reaches its row cap fails the DDL rather than shortening it (M2; tested with a 75 KiB `CHECK`). `TYPE_DDL_SQL` uses searched `CASE WHEN … OPERATOR(pg_catalog.=)`; a unit test rejects simple `CASE <expr> WHEN` and unqualified `"char"` casts (L1).

**DDL** (F-NAV-07) for every listed kind but columns: `CREATE SCHEMA … AUTHORIZATION`; tables reconstructed from the catalog (columns with type, `DEFAULT`, identity, stored or virtual generated expression and `NOT NULL`; local constraints through `pg_get_constraintdef`; `PARTITION BY`; `UNLOGGED`; then the indexes no constraint creates, through `pg_get_indexdef`, and `COMMENT ON` statements); a partition as `CREATE TABLE … PARTITION OF … FOR VALUES …`; views and materialized views through `pg_get_viewdef`; constraints and foreign keys as `ALTER TABLE … ADD CONSTRAINT`; `pg_get_indexdef`, `pg_get_triggerdef`, `pg_get_functiondef`; sequences and enum, domain, composite and range types reconstructed (base types have no DDL; foreign tables neither). Identifiers are quoted by the server (`format('%I')`, `quote_ident`), never in Rust. Identity options, collations, storage parameters, privileges and ownership beyond the schema's are not reproduced.

**Metadata tests** (`crates/drivers/ninesql-driver-pgwire/tests/metadata.rs`, on PostgreSQL 18): every declared kind lists the expected objects of a fixture schema with names holding quotes, Unicode and reserved words, and the "nine" dataset (tables, foreign keys with targets, indexes, unique constraints, the view, the `mood` type), all on a **read-only** session; a DDL round trip (the DDL of 20 objects of every kind is run after the schema is dropped, and the regenerated DDL is identical); paging over 1 205 tables in pages of 500; a call dropped while blocked behind a catalog lock frees the session (server-side cancel), and `Session::cancel_handle` stops a running metadata call. The `search_path` test runs every new listing and DDL query against planted user operators.

**Tests** (`crates/drivers/ninesql-driver-pgwire/tests/postgres.rs`, against `dev/`): every conformance helper (reserved properties, read-only writes, access-mode lift, multiple statements, batch budgets on the 1 000 000-row `big_events`, identifier quoting, stale cancel, `verify-full` against the dev service's test CA), the idle-cursor lock release (a paused cursor's lock and `idle in transaction` state are gone once its deadline passed, checked from a second session), drop / cancel / timeout paths, transactions, edits, metadata and type mapping. The dev service generates its test CA at first start ([dev/tls/postgresql-tls.sh](../dev/tls/postgresql-tls.sh)). md5 and cleartext authentication, and the SCRAM-only refusals, have unit tests against a scripted server only (the dev server uses SCRAM-SHA-256); the read-back used before PostgreSQL 14 has no server to run against in `dev/`.

## mysqlwire: MySQL and MariaDB (P1-B)
`ninesql-driver-mysqlwire` serves the engine ids `mysql`, `mariadb` and, since P4-C, `tidb` ([below](#wire-compatible-engines-p4-c)). The engine must match the server: a `mysql` connection to a MariaDB or TiDB server (or any other mismatch) fails at connect with a message naming the server version, since their capabilities differ.

**Client.** The driver implements the client/server protocol itself on top of tokio and rustls with the `ring` provider (no protocol crate, no new dependency; [docs/03](03-tech-stack.md#driver-clients)): packets read as a stream across the 16 MiB packet boundary, so values are cut while rows are read. `caching_sha2_password` and `mysql_native_password` are computed with `ring`, every buffer derived from the password zeroized. No C library, no OpenSSL. Client capabilities: protocol 4.1, plugin authentication, transactions, multiple results (for `CALL`), connect attributes (`program_name` = the connection's application name). Never `CLIENT_MULTI_STATEMENTS`, never `CLIENT_LOCAL_FILES` (a `LOAD DATA LOCAL` request from the server is answered with an empty file and the statement fails), no compression, never `CLIENT_IGNORE_SPACE`.

**Connect.**
- The user, database and character set (`utf8mb4_general_ci`, then `SET NAMES utf8mb4`, verified) travel in the handshake, never in a DSN. Driver properties: the global rule plus the extra keys above are refused, then only an allowlist is accepted and applied with `SET SESSION` after connect, values as inert literals (digits, or a hexadecimal string): `time_zone`, `lock_wait_timeout`, `innodb_lock_wait_timeout`, `group_concat_max_len`, and `max_execution_time` (MySQL) or `max_statement_time` (MariaDB); any other key, or a malformed value, fails the connect with `InvalidParams` naming the key only. A DBeaver import carries Connector/J properties that are not on this allowlist: until the import maps or drops them (P2-C), such a connection fails at connect.
- TLS: same modes and trust rules as pgwire: `disable`, `require` (encrypted, certificate not verified), `verify-ca` (requires `TlsConfig::ca_file` and trusts only it; host name not checked), `verify-full` (the CA file alone when set, the platform trust store otherwise; host name checked against `TlsConfig::server_name` or the endpoint host, IP addresses against IP SANs). A server that does not offer TLS fails the connect: never a fallback to plain text. Client certificates: PEM chain and unencrypted PEM key. The control connection uses the same TLS settings.
- `PasswordExchange::ScramOnly` is not offered (`connect.password_exchanges` is `Any` only) and is refused at connect with `InvalidParams`: no exchange of the MySQL protocol proves that the server knows the password verifier. Statement text is logged at `trace` level only when `may_log_statements()`.
- Authentication: `caching_sha2_password` (MySQL 8 default) and `mysql_native_password` (MariaDB default), one plugin switch at most. The password itself is sent only over a protected transport, as in pgwire (verified TLS, or an SSH tunnel whose hops all verify host keys and whose local end is loopback; such a tunnel protects the client → SSH server leg only, as in pgwire): `caching_sha2_password` full authentication (the server has no cached verifier for the account, typically the first connection after a server restart) and `mysql_clear_password` are refused otherwise, with a message saying how to connect (verified TLS once). The server's RSA public key is never requested (`allowPublicKeyRetrieval` is reserved: a man in the middle could send his own); `sha256_password`, `client_ed25519`, `auth_gssapi_client` and other plugins are refused. Challenge-response scrambles (`caching_sha2_password` fast path, `mysql_native_password`) are allowed over any transport.
- Session setup, before anything else runs: `SET NAMES utf8mb4`, `CONNECTION_ID()` read for `KILL QUERY`, `net_write_timeout` raised to 300 s (only ever raised: a paused result keeps the server waiting that long, then the server closes the connection and the session reports `Closed`), `autocommit` from the connection type, the accepted properties, then read-only, then init statements.
- Internal queries never depend on user objects or session modes: built-in functions only (they cannot be shadowed by stored functions), tables qualified with `information_schema`, system variables read as `@@SESSION.…`, user input (filter, schema and table names, cursors) only as hexadecimal literals compared as binary strings (`CAST(… AS BINARY)`), so `sql_mode` (`ANSI_QUOTES`, `NO_BACKSLASH_ESCAPES`, `PIPES_AS_CONCAT`), the character set and collations cannot change what they mean. Internal results are bounded (rows, bytes and value sizes).
- The engine and version are checked on the cleartext greeting and again with `VERSION()` inside the (possibly TLS) session. Authentication frames bypass the transport's write buffer, from zeroized buffers.
- Supported servers: tested on MySQL 8.4 and MariaDB 11.8 (`dev/`); protocol 4.1 with plugin authentication is required (MySQL ≥ 5.5, every MariaDB).

**Execute.** Text protocol (`COM_QUERY`), text holding a NUL byte refused (`InvalidParams`, as in sqlite), one statement per call (`ensure_single_statement` with the session's lexical rules; the protocol rejects a second statement anyway, since multi-statements are off). The dialect follows the session's `sql_mode`: `NO_BACKSLASH_ESCAPES` from the server status flags of every response and from the read-back, `ANSI_QUOTES` from the read-back (`"…"` identifiers are rewritten into backtick identifiers of the same length before the shared lexer splits or classifies, and the dialect's `lexical_rules()` report the mode through `double_quote_backslash`, off with `ANSI_QUOTES`). A stored-program definition (`CREATE PROCEDURE | FUNCTION | TRIGGER | EVENT … BEGIN … END`) is one statement: `;` inside its `BEGIN … END` body does not split it (text after the closing `END` does); it classifies as the riskiest of its `;`-separated pieces, at least `Ddl` (a body with control flow, `IF`, `LOOP`, `RETURN`…, is `Unknown`; a trigger is classified with its whole body, P3-D), so it is refused in read-only sessions and needs confirmation in production unless it is a plain `Ddl`. With `DELIMITER` in a script, see [Script splitting](#script-splitting-and-classification-p3-d-f-sql-18). Parameters are inlined client-side as literals that cannot leave their token in any `sql_mode` or character set: hexadecimal strings (`CONCAT(_utf8mb4 X'…')` for text and JSON, `X'…'` for bytes), digits (negative numbers in parentheses), `DATE` / `TIMESTAMP` literals; placeholders are found with the same lexical rules, so a `?` in a string, identifier or comment is never replaced, and the counts of placeholders and parameters must match. UTC timestamps, NaN and infinities are refused (MySQL has no time-zone-aware `DATETIME`, no NaN). Rows are read as the consumer asks: a full batch is delivered and nothing more is read until the next poll (TCP back-pressure pauses the server). Every result set of a `CALL` is delivered in turn (`multiple_result_sets`), then its update count. Manual-commit mode is the server's `autocommit = 0`; `auto_commit()` and `in_transaction()` follow the server status flags; switching back to auto-commit commits (`SET autocommit = 1`).

**Types** (Arrow): `TINYINT` / `SMALLINT` / `MEDIUMINT` / `INT` / `BIGINT` → `Int8` / `Int16` / `Int32` / `Int32` / `Int64` (`UInt*` when `UNSIGNED`); `YEAR` → `Int16`; `FLOAT` / `DOUBLE` → `Float32` / `Float64`; `DATE` → `Date32`; `DATETIME` → `Timestamp(µs)`; `TIMESTAMP` → `Timestamp(µs)` in the session time zone (`ninesql.type` = `timestamp`); text types → `Utf8`; binary types and `BLOB`s → `Binary`. With `ninesql.type`: `DECIMAL` (`Utf8`: precision 65), `TIME` (`Utf8`: a duration up to ± 838:59:59), `JSON` (`Utf8`; MariaDB reports `JSON` columns as `LONGTEXT`), `ENUM`, `SET` (`Utf8`), `BIT`, `GEOMETRY`, `VECTOR` (`Binary`). Zero or invalid dates (`0000-00-00`) become NULL, flag the column `ninesql.truncated` (not editable) and add a warning notice.

**Results.** Column definitions are bounded (4 MiB per result set, names cut to 1 KiB) and the driver's own queries by rows, bytes per row and value. Values are cut to `max_value_bytes` / `max_row_bytes` while the row is read (the rest is skipped on the socket, never buffered) and flagged `ninesql.truncated`. The server's warnings become notices after the statement (`SHOW WARNINGS LIMIT 1000`: level, code, message). Errors carry the server's error number as `code` and the SQLSTATE in the message; `1792` / `25006` is `ReadOnly`, an interrupted statement after a cancel is `Cancelled`. Update counts come from the OK packet (affected rows). Not offered: `LOAD DATA LOCAL INFILE`, prepared statements (`COM_STMT_*`), compression.

**Read-only verification.** After every statement in a read-only session, and after statements that may change session modes in any session (classes `Session`, `ChangesAccessMode`, `Unknown`, which include `SET` and `CALL`), one read-back: `@@SESSION.sql_mode`, the three `character_set_*` variables and `transaction_read_only`. A lifted read-only mode closes the session (`ReadOnly`, then `Closed`); a character set that is not UTF-8 closes any session (`Closed`); any failure of the read-back closes the session (fails closed). In a read-only session the read-back is followed by `SET SESSION TRANSACTION READ ONLY`: `SET TRANSACTION … READ WRITE` without `SESSION` (also in its comma form, `SET TRANSACTION ISOLATION LEVEL READ COMMITTED, READ WRITE`, which the shared classifier now refuses client-side as `ChangesAccessMode`, and from a MariaDB stored function, which no classifier sees) only changes the *next* transaction and leaves `transaction_read_only` at 1, so the read-back cannot see it; re-asserting the session characteristic resets that pending mode on both engines, inside an open transaction too (security review H1, tested in autocommit and manual mode). Driver statements (transaction control, settings, metadata, the read-back) are bounded by 60 s; past it the session is closed. Session-state tracking is not used: a statement can turn it off, while the read-back cannot be avoided. Consequence: in a read-only session the read-back runs between two user statements, so `FOUND_ROWS()` and `ROW_COUNT()` refer to it.

**Cancel and timeout.** `KILL QUERY <connection id>` on the control connection; handles are execution-scoped (`ExecutionTracker`), the session stays `Busy` until the server confirmed the end, and a dropped or cancelled stream is drained (bounded by 5 s, then the session is closed). A stream dropped while a write-class statement streams rows (`… RETURNING` on MariaDB) is drained without `KILL QUERY` once rows arrived. A `KILL QUERY` that arrives after its statement ended can interrupt the driver's own read-back: it is retried once. Behind a proxy that rewrites connection ids (ProxySQL, some load balancers) `KILL QUERY` may not reach the right backend: connect to the server directly. Timeouts go through the `ResultStream` watchdog (`server_side_timeout = false`; `max_execution_time` / `max_statement_time` can be set as properties).

**Metadata** (P4-A) shares the session's connection: a navigator call while a result streams fails with `Busy`. Databases are listed as `Schema`; under a schema, tables (`BASE TABLE`, MariaDB `SYSTEM VERSIONED`; partitioned tables flagged with their partition key), views (`VIEW`, `SYSTEM VIEW`), sequences (MariaDB only, `TABLE_TYPE = 'SEQUENCE'`; their start / increment are not reported), routines (function or procedure, return type, body language) and events; under a table, columns, constraints (`TABLE_CONSTRAINTS` with `CHECK_CONSTRAINTS`; check names are per schema on MySQL and per table on MariaDB), foreign keys (`REFERENTIAL_CONSTRAINTS` with `KEY_COLUMN_USAGE`), indexes (`STATISTICS`; functional key parts as their expression on MySQL 8.0.13+), triggers and partitions (with their `VALUES LESS THAN` / `VALUES IN` bound); under a view, columns. Everything comes from `information_schema`; user input reaches the text only as hexadecimal binary literals; filters are literal substrings (`CAST(name AS BINARY) LIKE X'…' ESCAPE '!'`, built with `escape_like`); pages are keyset pages by binary name (by ordinal for columns and partitions; routines by name and type, since a function and a procedure may share a name; both then have the same path). Constraints, foreign keys and indexes read their key columns with a second statement over the page's name range, so their pages hold at most 500 items. A dropped call is stopped with `KILL QUERY` on the control connection, scoped to its execution.

**DDL** (F-NAV-07): the server's `SHOW CREATE DATABASE | TABLE | VIEW | TRIGGER | FUNCTION | PROCEDURE | EVENT` (and `SEQUENCE` on MariaDB), as the engine returns it, with backtick-quoted names (a backtick doubled; a name with NUL refused). Keys, indexes and partitions are part of the table's DDL and have none of their own. For a function and a procedure sharing a name, both definitions are returned, function first, as one mysql-client script with `DELIMITER` markers (a delimiter neither body contains), at most 1 MiB in total (security review L2; tested by running the script through the driver's splitter). The quoting relies on UTF-8 connection character sets, which the session verifies after every statement that may change them (it closes the session otherwise). A definition the user may not see (`SHOW CREATE` returns `NULL` without the privilege) is an error. **Metadata tests** (`crates/drivers/ninesql-driver-mysqlwire/tests/metadata.rs`, on MySQL 8.4 and MariaDB 11.8): every declared kind on a read-only session, with a table name holding a backtick, a quote and Unicode, and the "nine" dataset; a DDL round trip (tables, a partitioned table, a view, a trigger, routines, an event, a MariaDB sequence are dropped and re-created from their DDL, which then regenerates identically); paging over 120 tables. Cancel of a metadata call is not integration-tested on these engines (no catalog query can be blocked on demand); it uses the statement path's `KILL QUERY`, which is.

**Tests** (`crates/drivers/ninesql-driver-mysqlwire/tests/mysql.rs`, every test on both `dev/` engines): every conformance helper (reserved properties, read-only writes, access-mode lift through a stored function, multiple statements, batch budgets on the 1 000 000-row `big_events`, identifier quoting, stale cancel, `verify-full` against the dev services' test CA), `caching_sha2_password` full authentication refused over plain TCP and accepted over verified TLS (MySQL), dropped streams (mid-result and mid-statement), cancel and timeout (also over TLS), transactions and isolation levels, edits and parameters with hostile text, warnings as notices, both result sets of a `CALL`, `EXPLAIN` in the declared formats, `LOAD DATA LOCAL` refused, metadata pages and filters, a wrong password and a wrong engine, a connection killed by the server. The dev services generate their test CA at first start ([dev/tls/mysql-tls.sh](../dev/tls/mysql-tls.sh)). Fake servers in the unit tests check that the password is never sent over an unprotected transport (full `caching_sha2_password` exchange, switch to `mysql_clear_password`), that a second plugin switch is refused and that a server without TLS fails a TLS connection; `CLIENT_MULTI_STATEMENTS` and `CLIENT_LOCAL_FILES` are checked off in the handshake response.

## Wire-compatible engines (P4-C)
TimescaleDB, YugabyteDB and QuestDB (pgwire) and TiDB (mysqlwire) are separate engine ids ([ADR-0003](adr/0003-supported-engines-v1.md)) with their own capabilities, dialect overrides and integration tests against their `dev/` containers (`crates/drivers/ninesql-driver-pgwire/tests/wire_engines.rs`, `crates/drivers/ninesql-driver-mysqlwire/tests/tidb.rs`). Everything not stated here is as for PostgreSQL or MySQL above.

**Engine check at connect.** The server must be the declared engine, or the connect fails with `Connect` ("this server reports version …, which is …, not …; choose the matching engine"; the version is shown without control characters, never the password):
- pgwire reads the `server_version` startup parameter (YugabyteDB reports `15.12-YB-…`; a parameter naming YugabyteDB or QuestDB refuses another engine at once), then, before read-only and init statements, `pg_catalog.version()` in the session (QuestDB reports a plain `11.3` startup parameter and names itself only there). `timescaledb` also needs the `timescaledb` extension in the connection's database (`pg_extension`): without it the connect fails, asking to choose PostgreSQL or to create the extension. A `postgresql` connection to a database that has the extension is accepted: it is PostgreSQL, browsed without hypertable awareness (chunks listed as tables of `_timescaledb_internal`). The extension version is shown in `Capabilities::server_version` (`18.6, TimescaleDB 2.32.0`).
- mysqlwire reads the version on the cleartext greeting and again with `VERSION()` in the session, as for MySQL / MariaDB; a version holding `TiDB` is TiDB.

**TimescaleDB** (tested on 2.32.0 with PostgreSQL 18.6). The PostgreSQL capabilities, read-only mechanism, cancel and DDL. Metadata: hypertables are listed among the schema's tables with flavour `hypertable`, continuous aggregates among its views with flavour `continuous aggregate`; **chunks are not listed** (a chunk is a table inheriting from a hypertable, compressed chunks included; recognised through `pg_inherits` and `_timescaledb_catalog.hypertable`, which keep their shape across TimescaleDB 2.x, unlike `_timescaledb_catalog.chunk`); a chunk is still reachable with SQL and `timescaledb_information.chunks`. The rebuilt DDL of a hypertable is its `CREATE TABLE` without the `create_hypertable` call, and a continuous aggregate's is its user view over the materialization hypertable, not the original `CREATE MATERIALIZED VIEW … WITH (timescaledb.continuous)`. Dialect: TimescaleDB functions and procedures that drop, move, convert or schedule changes to data (`drop_chunks`, `compress_chunk`, `decompress_chunk`, `freeze_chunk`, `create_hypertable`, `add_retention_policy`, `refresh_continuous_aggregate`, `move_chunk`, `merge_chunks`, the `*_job` and `*_policy` functions, the multi-node functions `distributed_exec`, `*_data_node`, `copy_chunk`, `set_replication_factor`…, 52 names; a word or quoted name right before `(`, schema-qualified or not), and any call qualified with `_timescaledb_functions`, `_timescaledb_internal` or `timescaledb_experimental`, classify as `Unknown`: confirmation in production, refused in read-only sessions (and refused engine-side there too). This applies in **every pgwire dialect**, PostgreSQL included (security review M1): a `postgresql` connection to a database with the extension is accepted, and DBeaver imports usually use the PostgreSQL driver; the cost elsewhere is at most an extra confirmation for a user function of the same name.

**YugabyteDB** (tested on 2026.1.3, YSQL 15.12). The PostgreSQL capabilities, read-only mechanism (`default_transaction_read_only` and the `ParameterStatus` check are the same), cancel request, metadata and DDL: the YSQL catalog has every `pg_get_*def` function and catalog the P4-A queries use, and the "nine" dataset browses fully (tablets are not shown; YugabyteDB's sharding appears in index DDL as `lsm (… HASH)`). Isolation levels: repeatable read and serializable; read committed only when `BEGIN ISOLATION LEVEL READ COMMITTED` really runs read committed (`yb_effective_transaction_isolation_level`, read at connect), since a YugabyteDB server without its read-committed mode runs it as snapshot isolation. `set_isolation_level` refuses an undeclared level on every pgwire engine.

**TLS on TimescaleDB and YugabyteDB.** Both declare the PostgreSQL TLS modes, CA file and client certificates (the same code path as PostgreSQL), but their `dev/` services have no TLS, so TLS is **not integration-tested** on these two engines.

**QuestDB** (tested on 10.2.0). QuestDB speaks a limited PostgreSQL protocol:
- *connect*: cleartext password only, so the existing rule applies: the password is sent only over a protected transport (verified TLS, which open-source QuestDB does not offer, or an SSH tunnel whose hops all verify host keys and whose local end is loopback); plain TCP fails with `Auth` before the password is sent. `ScramOnly` is not offered, no driver property is accepted, `tls` is `disable` only, no client certificate;
- *read-only*: [table above](#read-only-mechanism-adr-0007-i3);
- *transactions*: none declared; `set_auto_commit(false)`, `begin`, savepoints and isolation levels return `Unsupported`, statements of class `Transaction` (`BEGIN`, `COMMIT`, `ROLLBACK`, `START TRANSACTION`, `SAVEPOINT`…) are refused with `Unsupported`, `commit` / `rollback` with nothing open do nothing, `in_transaction()` is always `false` (QuestDB reports a transaction block after some DDL) and navigator statements never use a savepoint;
- *execute*: every statement runs in one `Execute` without a driver transaction (QuestDB has no `set_config` and no transaction to hold a suspended portal), read as the consumer asks (TCP back-pressure pauses the server); a dropped, cancelled or timed-out read sends a cancel request (QuestDB sends a backend key; `cancel` is `ServerSide` when it did, `LocalOnly` before connect); tested with a two-second timeout on a long `long_sequence` count and a stream dropped mid-`big_events`;
- *metadata* (from QuestDB's own functions, no `pg_catalog`): root kinds `Table`, `View`, `MaterializedView` from `tables()` (`table_type` `T`, `V`, `M`; tables flagged `wal` / `non-wal`, row count, `partition_key` as `<designated timestamp> BY <unit>`), under a table or a materialized view `Column` (`table_columns()`, in table order, paged by position) and `Partition` (`table_partitions()`: bound `min .. max`, row count, unit; none for `PARTITION BY NONE`), under a view `Column`; DDL from `SHOW CREATE TABLE | VIEW | MATERIALIZED VIEW`. Filters are literal substrings (`strpos(name, $n) > 0`, bound); pages are keyset pages by name. `table_columns()` and `table_partitions()` accept only a string constant and `SHOW CREATE` a name: there the name is written as a constant only after it was found in `tables()` with a bound parameter and checked to hold no `'`, `"`, `\` or control character (QuestDB refuses them in table names). QuestDB has no `search_path`, user operators or user functions, so the qualified-operator rule of PostgreSQL does not apply;
- *dialect*: PostgreSQL's lexical rules (QuestDB reports `standard_conforming_strings = on`). QuestDB statements outside PostgreSQL's grammar that change data, files or the server classify as `Unknown` by their first word: `RENAME`, `VACUUM`, `REINDEX`, `SNAPSHOT`, `CHECKPOINT`, `BACKUP`, `COPY`, `CANCEL`, `REFRESH`, `DECLARE`; so do `reload_config()`, `cancel_query()`, `flush_query_cache()`, `dump_memory_usage()` and `dump_thread_stacks()` (all present on QuestDB 10.2; the dumps write to the server log). `ALTER TABLE … DROP | DETACH PARTITION`, `DROP ALL TABLES`, `TRUNCATE` and `UPDATE` without `WHERE` are already `Destructive`. No `EXPLAIN ANALYZE` (QuestDB has none); `EXPLAIN` and `EXPLAIN (FORMAT JSON)` work. Cases in `engine_dialects_classify_their_own_statements`;
- *types*: QuestDB reports PostgreSQL type OIDs; `SYMBOL`, `IPV4`, `LONG256`, `GEOHASH` arrive as text; the "nine" `all_types` table (one column per QuestDB type) decodes.

**TiDB** (tested on 8.5.8, `unistore`). MySQL's protocol, authentication, parameters and execution:
- *read-only*: [table above](#read-only-mechanism-adr-0007-i3); the session re-assert `SET SESSION TRANSACTION READ ONLY` is not sent (TiDB refuses it);
- *metadata*: from `information_schema` as for MySQL; schemas, tables, views, **sequences** (`TABLE_TYPE = 'SEQUENCE'`, listed with an empty `SequenceInfo` as on MariaDB; DDL through `SHOW CREATE SEQUENCE`), columns, constraints, foreign keys (TiDB 8.5 enforces them), indexes (`STATISTICS.EXPRESSION` exists), partitions. No triggers, stored routines or events (TiDB has none), so they are not declared;
- *transactions*: manual commit, savepoints, read committed and repeatable read (TiDB refuses serializable and read uncommitted with error 8048; `set_isolation_level` refuses undeclared levels on every mysqlwire engine);
- *explain*: text, JSON as `EXPLAIN FORMAT = 'tidb_json'` (TiDB refuses `FORMAT=JSON`), `EXPLAIN ANALYZE` (runs the statement);
- *dialect*: TiDB's executable comments `/*T![feature] … */`, which the shared lexer reads as comments while TiDB runs their content, make a statement `Unknown` (`tidb_dialect_overrides`);
- *cancel*: `KILL QUERY` on the control connection, tested with a two-second timeout on `SLEEP(60)`;
- *TLS*: not declared (`disable` only) until the dev service has a test CA to prove `verify-full` (follow-up), so **every TiDB connection is plaintext for now**, remote ones included: use an SSH tunnel to reach a remote TiDB (`mysql_native_password` scrambles are allowed over plain TCP, the password itself never is); `CALL` result sets not declared (no stored procedures);
- *side effects* (every mysqlwire dialect, MySQL and MariaDB included, security review L4): `NEXTVAL`, `SETVAL`, `LASTVAL` (over-classified with them), `NEXT VALUE FOR`, `NEXTVAL FOR`, `PREVIOUS VALUE FOR`, `GET_LOCK`, `RELEASE_LOCK` and `RELEASE_ALL_LOCKS` classify as `Unknown` (`tidb_dialect_overrides`); since the P5 security review (L5) also `SLEEP`, `BENCHMARK`, `LOAD_FILE`, `MASTER_POS_WAIT`, `SOURCE_POS_WAIT`, `MASTER_GTID_WAIT` (MariaDB), `WAIT_FOR_EXECUTED_GTID_SET` and `WAIT_UNTIL_SQL_THREAD_AFTER_GTIDS`, matched as a word or a backquoted (or, with `ANSI_QUOTES`, double-quoted) name right before `(`; a qualified `db.sleep(…)` (a stored function) is over-classified with them.

## sqlite: SQLite (P1-B)
`ninesql-driver-sqlite` serves the engine id `sqlite`.

**Client.** `rusqlite` 0.42 with the SQLite 3.54.1 amalgamation bundled by `libsqlite3-sys` (no system library; [docs/03](03-tech-stack.md#driver-clients)); features `column_decltype`, `hooks`, `limits`, never `load_extension`. The driver's own code keeps `#![forbid(unsafe_code)]`. Each session owns one dedicated OS thread that holds the connection (SQLite is synchronous): never the GPUI thread, never Tokio's shared blocking pool, which a paused result would otherwise hold. No network traffic of any kind (I2).

**Open.**
- `Endpoint::File` only takes an **absolute** path (a relative path would depend on the working directory). It is canonicalized (symbolic links and `..` resolved, so the file opened is the file checked) and opened with `SQLITE_OPEN_NOFOLLOW` (a link swapped in after the check makes the open fail). An absolute path never starts with `file:` and is never `:memory:`, so SQLite never reads it as a URI, although the bundled build enables URIs (`SQLITE_USE_URI`); the driver never passes `SQLITE_OPEN_URI`. The target must be a regular file (a directory, a FIFO or a device such as `/dev/zero` is refused). Residual: someone who can write to the directory could swap the checked file for a FIFO between the check and the open, which would block the connection thread until the connect timeout; this needs write access to the user's own directory and is outside the threat model. A missing file is created only when `create_if_missing` is set **and** the session is read-write, in an existing directory; otherwise the connect fails and nothing is created.
- `Endpoint::InMemory` opens a private in-memory database (never a shared cache), read-write only: a read-only in-memory database would be empty, so it is refused.
- A user name or password, an SSH tunnel, a proxy or a database name other than `main` are refused with `InvalidParams` (no secret is ever held: `retains_secret_after_connect = false`). TLS settings are ignored (`tls` is empty).
- The file must hold a readable schema (`SELECT count(*) FROM sqlite_schema`): a file that is not a database fails the connect with `Connect`.
- Driver properties: the global rule plus the extra keys above are refused, then only an allowlist is accepted, parsed and applied by the driver (never the user's text): `busy_timeout` (milliseconds, `0..=600000`, default 5000), `cache_size` (KiB form only, `-1048576..=-1`: at most 1 GiB), `foreign_keys` (`on` / `off`; **on** by default in the bundled build, unlike the `sqlite3` shell). Any other key, or a malformed value, fails the connect with `InvalidParams` naming the key only. A DBeaver import carries sqlite-jdbc properties that are not on this allowlist: until the import maps or drops them (P2-C), such a connection fails at connect.

**Engine-side protections in every session** (read-only or not): `SQLITE_DBCONFIG_DEFENSIVE` (no `writable_schema` writes, no `journal_mode = OFF`, no shadow-table writes), `SQLITE_DBCONFIG_TRUSTED_SCHEMA` off (views and triggers stored in a hostile file cannot call functions with side effects or virtual tables), `PRAGMA cell_size_check = ON`, `SQLITE_DBCONFIG_DQS_DML` and `DQS_DDL` off (a double-quoted name is always an identifier, never a string literal that would make an edit's `WHERE "id" = ?` match every row; stored schemas written with double-quoted strings still load), the pragmas that would undo these (`trusted_schema`, `cell_size_check`, `writable_schema` with a value) denied by the authorizer, `load_extension` never enabled and denied by the authorizer (with `fts3_tokenizer`), and `SQLITE_LIMIT_LENGTH` set per statement to the caller's `max_bytes` (at least 16 MiB, at most 10⁹ bytes), so a single value larger than the result's byte budget fails the statement (`string or blob too big`) instead of being loaded whole.

**Read-only** (`OpenMode`, not liftable; see the [table above](#read-only-mechanism-adr-0007-i3)). Applied before `connect` returns and before init statements run. The authorizer and the open mode are set from Rust and cannot be changed from SQL; `query_only` could only be changed by a pragma the authorizer denies. The driver still verifies after **every** statement (the user's, and its own transaction control and navigator queries) that the file is opened read-only, `SQLITE_LIMIT_ATTACHED` is 0, the defensive flag is on and the trusted-schema flag off, `pragma_database_list` holds only `main` / `temp`, and `query_only` reads 1; then it re-asserts `PRAGMA query_only = ON`. Any failure closes the session (`ReadOnly`, then `Closed`). Client-side, statements the dialect classifies as writes or access-mode changes are refused first. `set_read_only` to another mode returns `Unsupported`: reconnect with the new mode. Bypasses tested, each refused client-side and, sent directly to the connection past the classifier, denied engine-side with no file created or modified in the directory: DML (also `REPLACE`, `INSERT … RETURNING`, a CTE `DELETE`), DDL, temporary tables, views and triggers, `VACUUM`, `VACUUM INTO` (which writes a new file even from a read-only connection), `ATTACH` (plain path, `file:` URI with `mode=rwc`, `:memory:`), `DETACH`, `load_extension`, `PRAGMA query_only = OFF` / `(0)` / `main.` / `[query_only]`, `writable_schema`, `temp_store`, `journal_mode`, `user_version`, `optimize`, `ANALYZE`, `REINDEX`, `BEGIN IMMEDIATE` / `EXCLUSIVE`, and writes through a trigger (they cannot start); a write in init statements fails the connect.

**Files inside a DBeaver workspace (I4).** When `ConnectParams::inside_dbeaver_workspace` is set on a file endpoint, the driver opens the file read-only (whatever `read_only` says; `create_if_missing` is ignored and a missing file is an error) **and immutable** (`file:` + the canonical path, every byte outside `[A-Za-z0-9/._~-]` percent-encoded, + `?mode=ro&immutable=1`, built by the driver: user text is never read as a URI), whatever its journal mode and sidecar files: SQLite then creates no journal, `-wal` or `-shm` file next to it. The first result of the session carries a warning notice. Residuals: committed pages still held in a `-wal` file (a writer that crashed, or one still running) or in a hot `-journal` are **not visible** in such a session, and the notice says so; if another program writes to the database while the session is open, results may be stale or fail with `SQLITE_CORRUPT` (the file is never damaged). The core sets the flag for every file endpoint it recognises inside a DBeaver workspace, fail-closed ([docs/05](05-security.md#files-inside-a-dbeaver-workspace)); [docs/06](06-dbeaver-interop.md) also has the import force `read_only = true`. Without the flag, a read-only session never writes the database file and creates no file next to it in the common case: a plain read-only open of a **WAL**-mode database would create its `-wal` and `-shm` files, so when the header says WAL (bytes 18 and 19 equal to 2) and neither file exists, the driver opens it immutable in the same way. When a `-shm` file already exists (a live writer), the database is opened normally; when only a `-wal` file exists, the normal open creates the `-shm` file, which SQLite needs to read the committed pages of the `-wal` (the DBeaver flag avoids it, at the cost above).

**Execute.** One statement per call: the dialect refuses text it splits into several statements (`MultipleStatements`), and SQLite's `prepare` refuses a second statement anyway. The dialect is ANSI with SQLite's lexical rules (`` `…` `` identifiers, no backslash escapes); Before splitting and classifying, the text is rewritten, byte offsets kept, the way SQLite's tokenizer reads it: `[…]` identifiers become `"…"` identifiers, and the parenthesised part of a Tcl-style variable (`$a(…)`, `:a(…)`, `@a(…)`, `#a(…)`, `$a::b(…)`, which runs to the next whitespace or `)`, quotes and comment markers included) becomes neutral bytes, so a quote, a comment marker or a `;` inside them cannot hide a statement from the classifier (security review H1). The shared classifier already returns `Unknown` for a `WITH` whose main statement it never finds (unbalanced or unterminated text); as a further safety net, a `WITH` statement in which `INSERT`, `UPDATE`, `DELETE` or `REPLACE` appears as a whole word in code (outside strings, quoted identifiers, variables and comments, as SQLite's tokenizer reads it; so `updated_at` or `'delete'` do not count) is never classified below `Unknown`; incomplete text, which SQLite refuses anyway, falls back to whole words anywhere. The schema-reading pragmas the authorizer allows (`PRAGMA table_info(t)`, `PRAGMA query_only`, `PRAGMA integrity_check`…) classify as reads; every other pragma, `ATTACH`, `DETACH`, `VACUUM`, `ANALYZE` and `REINDEX` classify as access-mode changes or unknown (confirmation in production, refused in read-only sessions). The statement runs lazily: nothing is prepared before the stream is first polled, and each poll steps at most one batch (`BatchLimiter`, `RowBudget`), so a paused grid pauses the statement. Parameters are bound natively (`?`, `?NNN`, `:name` by position): booleans as 0 / 1, decimals and JSON as text, dates as `YYYY-MM-DD`, timestamps as `YYYY-MM-DD HH:MM:SS.ffffff` (`Z` suffix for UTC); NaN and years outside 0–9999 are refused (`Unsupported`). Manual-commit mode opens a transaction (`BEGIN`, deferred) before the first statement that is not transaction control; switching back to auto-commit commits; `commit` and `rollback` without an open transaction do nothing; closing the session rolls back. Isolation: serializable only.

**Types** (Arrow). SQLite types values, not columns: one Arrow type per result column, from the declared type with SQLite's affinity rules: contains `INT` → `Int64`; `CHAR` / `CLOB` / `TEXT` → `Utf8`; `BLOB` → `Binary`; `REAL` / `FLOA` / `DOUB` → `Float64`; `BOOLEAN` / `BOOL` → `Boolean` (0 and 1); anything else (`NUMERIC`, `DECIMAL(p,s)`, `DATE`, `DATETIME`, `JSON`…) → `Utf8` in text form with the declared type in `ninesql.type` (cut to 64 bytes). A column without a declared type (an expression, an untyped table column) takes the storage class of its first non-NULL value in the first batch (`Utf8` when there is none). A value whose storage class does not fit its column (text in an `INTEGER` column, `42` in an untyped column first seen as text) is converted when exact for display (a number to its text form, text to its bytes, an integer to a float within 2⁵³) and becomes NULL otherwise; the column is flagged `ninesql.truncated` for that batch (not editable: writing the value back would change its storage class) and one warning notice per column says so. Text that is not valid UTF-8 (a corrupt or hostile file) is shown with replacement characters and flagged the same way.

**Results.** Values are cut to `max_value_bytes` / `max_row_bytes` as they are copied out of SQLite (only the kept prefix is copied; SQLite itself holds at most the current row, bounded by `SQLITE_LIMIT_LENGTH` above) and flagged `ninesql.truncated`. Column names are cut to 1 KiB. Update counts: the number of rows changed by the statement itself (triggers excluded) when it changed rows, `0` for an `INSERT` / `UPDATE` / `DELETE` / `REPLACE` that changed none, `NULL` for other statements; `… RETURNING` gives its rows, then the count. A result left paused for more than 300 s (`PAUSED_RESULT_TIMEOUT`) is closed by the driver, since its statement holds a read transaction (a `SHARED` lock or a WAL snapshot) that blocks writers of other processes; the next poll reports it. Errors carry SQLite's extended result code as `code` and SQLite's message, never the statement text (the client library's own message quotes it: the driver keeps only SQLite's message and turns the offset into `position`); `SQLITE_READONLY`, and an authorizer denial in a read-only session, are `ReadOnly`; an interrupted statement is `Cancelled`.

**Cancel and timeout.** `sqlite3_interrupt` through the connection's interrupt handle, plus a flag the connection thread reads between rows and while a result is paused (an interrupt only stops a statement that is stepping); handles are execution-scoped (`ExecutionTracker`) and the session stays `Busy` until the thread confirmed the end. A stale interrupt cannot reach the next statement: SQLite clears it when the next statement starts with no other statement active, and the driver retries its own internal statement once if a racing interrupt hits it. Timeouts go through the `ResultStream` watchdog (`server_side_timeout = false`), which also fires while the consumer does not poll. Lock waits are bounded by `busy_timeout`; the driver's own statements by 60 s (progress handler), a thread that does not answer within 120 s closes the session. `close` interrupts a running statement and ends a paused one. Dropping a stream whose statement still runs, or dropping the session, also interrupts it (a statement that produces no row, such as a large `count(*)`, would otherwise run on and keep its lock); the interrupt is sent while the execution is known not to have ended, so it cannot reach the next one. The progress handler also stops a statement of a closing session or a cancelled execution.

**Metadata** is served by the session's thread: a navigator call while a result streams fails with `Busy`. Schemas come from `pragma_database_list` (`main`, plus `temp` once it exists), tables and views from `<schema>.sqlite_schema` (internal `sqlite_*` tables hidden; virtual tables flagged `virtual`), columns from `pragma_table_xinfo` (type, nullability, default, primary key, generated columns as auto-generated). Filters, names and cursors are bound parameters; filters are literal substrings (`LIKE ?1 ESCAPE '!'`, case-insensitive for ASCII as SQLite's `LIKE`); pages are keyset pages by name (by column number for columns). A schema name reaches the SQL text only as a quoted identifier, after it was found in `pragma_database_list`. Under a table (P4-A): foreign keys from `pragma_foreign_key_list` (SQLite does not report their name: they are named `fk_<id>` after the engine's id; a `REFERENCES t` without columns targets `t`'s primary key; the filter matches the name or the referenced table; past the 10 000-row internal cap the cut key is dropped and the next page continues after the last complete one, security review L4), indexes from `pragma_index_list` / `pragma_index_xinfo` (an expression key part is reported as `(expression)`, and a partial index's predicate is not reported: SQLite exposes neither), triggers from `sqlite_schema` (timing and event read from the stored `CREATE TRIGGER` text; SQLite triggers are always row triggers); under a view, columns and triggers. Constraints are not listed as their own kind: SQLite does not expose check constraints, primary keys are on the columns and unique constraints are listed as unique indexes. DDL: the stored `CREATE` text of tables, views, indexes and triggers, up to 1 MiB (an index created by a constraint has none). Navigator calls are local and bounded by the 60 s driver-statement limit; a dropped call is not interrupted (`Session::cancel_handle` sends `sqlite3_interrupt` to the connection; not integration-tested for navigator calls).

**Hostile and corrupt files.** Never a crash: a file that is not a database fails the connect; corrupt or truncated pages make the statements that read them fail with `Query` (`SQLITE_CORRUPT`) while the session stays usable; a value larger than the byte budget fails the statement instead of being loaded. Residual: `rusqlite` 0.42 treats a name that is not valid UTF-8 as a bug and panics (inside the authorizer callback, where it is caught and the statement is denied; in `Statement::column_name` and around declared types, where the driver catches it and fails the statement); the client library still prints the panic message on stderr. This relies on unwinding: a build profile with `panic = "abort"` would turn such a file into a crash (noted in the crate's `Cargo.toml`).
