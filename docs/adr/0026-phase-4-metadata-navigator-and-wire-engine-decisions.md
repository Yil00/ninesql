# ADR-0026: Phase 4 metadata, navigator and wire-engine decisions

- **Status**: Accepted (maintainer, 2026-11-16). It adds to [ADR-0008](0008-workspace-and-config-storage.md) §1 (a new machine-owned file in the project directory, §1.1 below) without editing it, applies [ADR-0007](0007-production-safety-model.md) §2 (read-only is engine-side) to engines that have no session read-only mode (§3.1, §3.2) and builds on [ADR-0003](0003-supported-engines-v1.md) (one crate per family, engine ids per engine) and [ADR-0004](0004-driver-api-runtime-and-results.md) (I6: metadata calls run on the driver runtime). It does not rewrite their decisions. Notes on §3.2 (TiDB account check, phase 4 review M1) and §3.4 (QuestDB password past a bastion, phase 4 review L4) were added on 2026-11-16 without changing its decisions. A [note on §1.3, §1.4 and §2.4](#note-on-13-14-and-24-metadata-gate-and-mysqlwire-navigator-reads-2026-11-19) (one metadata load at a time per session, statements behind the same gate, mysqlwire navigator reads in manual-commit mode) was added on 2026-11-19, accepted by the maintainer the same day, without changing its decisions.
- **Date**: 2026-11-16

## Context
Phase 4 landed on 2026-11-16: metadata and DDL in pgwire, mysqlwire and sqlite (P4-A), the core `MetadataService` (`crates/ninesql-core/src/metadata/`), the navigator UI (P4-B, `crates/ninesql-ui/src/navigator.rs`, `crates/ninesql-ui/src/browse/`) and the wire-compatible engines TimescaleDB, YugabyteDB, QuestDB and TiDB (P4-C). The task reports and the security reviews of P4-A, P4-B and P4-C listed decisions that touch accepted ADRs (ADR-0008 §1, ADR-0007 §2), are security-relevant or set limits. This ADR records them as implemented; it changes no behaviour. The rustdoc, [docs/02](../02-architecture.md#metadata-service-p4-b) and [docs/08](../08-engine-capabilities.md) are the reference.

Invariants involved: I1 (no secret on disk or in logs), I3 (read-only enforced by the engine), I6 (the UI thread never waits on I/O, bounded memory), I8 (capabilities declared honestly).

## Decision
### 1. Core metadata service
1. **Navigator filters live in a per-project `navigator.json`** (schema 1), in `$XDG_DATA_HOME/ninesql/workspace/<project>/`, beside `connections.json`: filters by connection id, then by kind name (include and exclude patterns, case sensitivity). It is a new machine-owned JSON file under ADR-0008 §2 and §3 (`schema_version`, atomic writes, `0600`), written under a process-wide writer lock, holding no secret and no object data. It is **not** a `connections.json` schema bump: filters change often, are not part of a connection's definition and must not trigger the migrations and checks of `connections.json`. A missing file means no filter; entries with an unknown kind or an invalid pattern are dropped at load and reported; a file that cannot be read (newer schema, invalid JSON) is reported, never overwritten, and filters are then kept in memory only.
2. **Server-side filtering only for a case-sensitive single include pattern.** Filters always apply client-side on every page. The service sends the driver a filter (`PageRequest::filter`, the longest literal run of the pattern, bound as a parameter, matched as a substring) only when the filter is case-sensitive and has exactly one include pattern; the client-side match then keeps the exact set. A case-insensitive filter is never sent: the drivers' `LIKE` is case-sensitive on some engines and would hide names the pattern accepts.
3. **Metadata is bound to the connection's oldest open session.** One cache per connection, tied to that session; when it ends, the cache is cleared, requests in flight fail with `SessionClosed` and `Invalidated` is sent; the next request binds another open session of the connection. A request cannot be pinned to another session (follow-up). Metadata calls share the session's connection, so a navigator call while a result streams fails with `Busy`.
4. **Default limits** (`MetadataConfig::default()`): 30 s per load or DDL fetch; pages of `PageRequest::DEFAULT_LIMIT` (1 000) objects, clamped to 1..=10 000; 10 pages per load, after which the node is incomplete and "Load more" continues; a cache of at most 4 096 entries and 64 MiB of estimated bytes per connection, least recently used evicted first; 4 driver calls at once per connection; an event channel of 1 024 events, overflow dropped and counted. Search: queries cut to 128 characters, at most 1 000 results, 500 000 candidates and 250 ms; it reads the cache only. Prefetch: explicit, at most 2 048 nodes and 6 levels, cancelled with its handle; nothing prefetches by default. Completion snapshots hold at most 250 000 objects.
5. **Engine errors go to the UI, never to the logs.** `MetadataError::Driver` carries the engine's message to the UI, shown through the label function (capped, invisible characters marked). Logs carry connection ids, kind names, counts and the stable `MetadataError::kind()` only: never object names, filter patterns or engine messages. Filter errors never echo a pattern.

### 2. Drivers
1. **`ObjectKind::Event`** is added to the driver API for MySQL / MariaDB scheduled events (`CREATE EVENT`), with the additive `ObjectDetails` variants `Constraint`, `ForeignKey`, `Index`, `Trigger`, `Routine`, `Sequence`, `Type`, `Partition` and `TableInfo::partition_key` (non-exhaustive detail structs).
2. **DDL over 1 MiB is an error, never returned cut**: a truncated `CREATE` could be run and create a different object. The same holds for the parts of a pgwire rebuilt `CREATE TABLE` (a part that reaches its row cap fails the DDL) and for the mysqlwire script of a function and a procedure sharing a name. A page whose rows pass a driver's 32 MiB internal cap fails with a non-fatal `Query` error; the session and its transaction stay.
3. **A dropped metadata call is cancelled on the server** where the engine can: pgwire sends a cancel request scoped to the call's execution, only while its statement runs; mysqlwire sends `KILL QUERY` on the control connection, scoped to the execution; sqlite navigator calls are local and bounded by the driver statement limit (`Session::cancel_handle` reaches them).
4. **pgwire savepoint inside an open transaction.** In an open transaction every navigator statement runs inside `SAVEPOINT ninesql_meta`, released on success and rolled back to on an error or a cancel (allowed in read-only transactions), so neither a catalog error nor the cancel of an abandoned call aborts the user's transaction. QuestDB has no transactions and never uses it.
5. **PostgreSQL partitions are listed under their parent table** (nested), not among the schema's tables; a partition's DDL is `CREATE TABLE … PARTITION OF … FOR VALUES …`.
6. **No PostgreSQL `Catalog` kind.** A PostgreSQL session is bound to one database; listing other databases would show objects the session cannot open. The tree starts at schemas. Browsing other databases needs one session per database (follow-up).
7. **Synthetic SQLite foreign-key names.** SQLite does not report a foreign key's name: keys are named `fk_<id>` after the engine's id, and the filter matches the name or the referenced table. SQLite has no `Constraint` kind (check constraints are not exposed; primary keys are on the columns; unique constraints are listed as unique indexes).

### 3. Wire-compatible engines
1. **QuestDB read-only path** (`ReadOnlyMechanism::ServerSetting { liftable: false }`). QuestDB has no read-only transaction and ignores `SET SESSION CHARACTERISTICS … READ ONLY`. A read-only session is accepted only when the server makes it read-only: the session's user is QuestDB's enabled read-only user, or the server is read-only. The driver checks it at connect from `SHOW PARAMETERS` with `current_user()` **and** with a write that changes nothing (an `INSERT … SELECT … FROM long_sequence(0)` into a table name QuestDB cannot hold), which must fail with a permission error; the two checks are ANDed because a read-only user enabled by a config reload logs in with write access on QuestDB 10.2 while `SHOW PARAMETERS` still names it. Otherwise the connect fails with `ReadOnly`: read-only is never faked. Verified on open-source QuestDB only (QuestDB Enterprise has its own access control).
2. **TiDB read-only only on a read-only instance** (`ServerSetting { liftable: true }`). TiDB has no session read-only mode. A read-only session is accepted only when `tidb_super_read_only` or `tidb_restricted_read_only` is on, read back at connect and after every statement (a lift by a privileged user closes the session at the next read-back); otherwise the connect fails with `ReadOnly`, recommending an account with `SELECT` privileges only. Accepted window: a statement that the classifier let through as a read can run between a lift and the next read-back.

   > **Note (2026-11-16, phase 4 review M1).** TiDB exempts accounts holding `RESTRICTED_REPLICA_WRITER_ADMIN` (directly or through an active role) from both `tidb_super_read_only` and `tidb_restricted_read_only`, so a read-only instance alone does not make a session read-only. A read-only TiDB session now also requires, at connect, that `SHOW GRANTS` (active roles expanded) lists none of `RESTRICTED_REPLICA_WRITER_ADMIN`, `SUPER`, `ALL PRIVILEGES ON *.*` (fail-closed), and that the write probe `DELETE FROM information_schema.CHARACTER_SETS WHERE FALSE`, which cannot change anything, fails with error 1836. `CURRENT_ROLE()` is read back with the instance's mode after every statement, and a change closes the session; role and privilege changes are refused client-side. The accepted window widens to the statements run while a lift propagates across TiDB servers, and to a privilege granted to the account or its active roles by another session after connect (not re-checked until the next connect). `root` and `SUPER` accounts can no longer open a read-only TiDB session.
3. **Wrong-engine policy.** The server must be the declared engine, or the connect fails before read-only and init statements (`server_version`, then `version()` in the session for pgwire; the greeting and `VERSION()` for mysqlwire). `timescaledb` is refused on a database without the `timescaledb` extension. `postgresql` is **accepted** on a database that has the extension: it is PostgreSQL, browsed without hypertable awareness (DBeaver imports usually use the PostgreSQL driver). A MySQL or MariaDB connection to TiDB, or the reverse, is refused.
4. **QuestDB cleartext-password policy.** QuestDB only asks for a cleartext password. pgwire's existing rule applies: the password is sent only over a protected transport, verified TLS (`verify-ca`, `verify-full`; open-source QuestDB has none) or an SSH tunnel whose hops all use the strict host-key policy and whose local end is loopback; over plain TCP the connect fails with `Auth` before the password is sent. `ScramOnly` and driver properties are not offered for QuestDB; `tls` is `disable` only; no transactions are declared.

   > **Note (2026-11-16, phase 4 review L4).** An SSH tunnel protects only the leg from NineSQL to the last SSH server. When that server is a bastion in front of a remote QuestDB, the cleartext password crosses the last hop (bastion to QuestDB) in clear. Users are told to tunnel to the QuestDB host itself (forwarding to its loopback). A future driver-API change should pass the tunnel target to the driver and require a loopback target for a cleartext password; until then the driver cannot tell the two cases apart.
5. **The Timescale function list applies in every pgwire dialect.** TimescaleDB functions and procedures that drop, move, convert or schedule changes to data (52 names), and any call qualified with `_timescaledb_functions`, `_timescaledb_internal` or `timescaledb_experimental`, classify as `Unknown` in every pgwire dialect, PostgreSQL included, since a `postgresql` connection to a database with the extension is accepted (§3.3). The cost elsewhere is at most an extra confirmation for a user function of the same name. Likewise, side-effect functions (`NEXTVAL`, `SETVAL`, `LASTVAL`, `NEXT VALUE FOR`, `GET_LOCK`, `RELEASE_LOCK`…) classify as `Unknown` in every MySQL-family dialect.
6. TiDB declares no TLS (`disable` only) until the dev service has a test CA to prove `verify-full` (I8: no mode is declared before it is tested).

### 4. Navigator UI
1. **Template placeholders keep only `[A-Za-z0-9_]`.** Values and conditions in "Generate SQL" templates are `<placeholders>` that no engine accepts; a placeholder keeps only `[A-Za-z0-9_]` (other characters become `_`), at most 32 characters, `<value_N>` when nothing is left. Real names appear only as identifiers quoted by the session dialect. Templates open in a new editor and are never run; `UPDATE` and `DELETE` always carry a `WHERE` line; `INSERT`, `UPDATE` and `DELETE` are not offered on read-only sessions.
2. **The key condition comes only from complete metadata**: from the primary-key constraint when the driver lists it, else from the column flags only when the column node is complete and nothing is hidden by a filter; otherwise `WHERE <condition>` with a comment saying why. A column list built from a filtered or incomplete node carries a comment too.
3. **Generation is refused for names the editor would change.** The SQL editor strips control characters and rewrites line ends ([ADR-0025](0025-phase-3-dialect-and-editor-decisions.md) §3); a template with such a name would target another object than the one shown. When a path segment, a listed column or a primary-key column would be changed, no template is opened; "Show DDL" with such text opens the object editor's read-only DDL tab instead; completion does not offer such names.
4. **Expanding a closed connection starts the connect flow**, with its usual prompts (vault unlock, "ask every time" passwords, host keys, confirmations); nothing is browsed without an open session.
5. **Completion default schema.** When an editor tab binds to a connection, unqualified names resolve in the connection's `default_schema` when it is set and listed, otherwise in the first schema the driver lists (the first catalog on engines without schemas); that schema is warmed (`warm_schema`), cancelled when the tab rebinds or closes. Completion reads the cache only.
6. **Navigator keyboard through the shared list actions** of gpui-kit (`gpui_kit::base::actions`: `SelectUp`, `SelectDown`, `SelectLeft`, `SelectRight`, `SelectFirst`, `SelectLast`, `SelectPageUp`, `SelectPageDown`, `Confirm`), bound in the navigator's key context, rather than new NineSQL actions: the arrows, Home, End, Page Up, Page Down and Enter behave as in other gpui-component lists. The navigator's own commands are NineSQL actions with key bindings and palette entries (AGENTS.md).
7. **Labels mark what would hide or reorder text**: control, bidirectional, zero-width and other `Default_Ignorable_Code_Point` characters are shown as `U+FFFD`, other space characters as `U+2423`, leading or trailing ASCII spaces as `U+2420`, in the tree, "Find object", the object editor, tab titles and dialogs.

## Consequences
- Filters can change without touching `connections.json`; a deleted connection leaves orphaned entries in `navigator.json` until a clean-up exists (follow-up).
- Read-only on QuestDB and TiDB depends on server configuration the user must set up; NineSQL refuses rather than pretends, and the tutorial says what to configure.
- Users with the PostgreSQL engine on a TimescaleDB database get Timescale's data-changing functions confirmed; a user function with one of those names gets an extra confirmation on any PostgreSQL connection.
- Large or hostile catalogs stay bounded (pages, byte caps, cache budget, search budget); a node past 10 pages needs "Load more", and search only finds what was loaded.
- To test: the navigator is tested on the mock driver only; a UI test against a real engine and the visual pass (P6-F) remain. The [Phase 4 follow-ups](../ROADMAP.md#phase-4-follow-ups) list the rest.

## Rejected alternatives
- **Filters in `connections.json`** (schema 6): a schema bump and its migration for a view preference, and filters would travel with exported connection definitions.
- **Always sending filters to the server**: wrong results with case-insensitive patterns on engines whose `LIKE` is case-sensitive, and engine-specific pattern syntax.
- **A dedicated metadata session per connection**: a second authentication, which drivers that drop secrets after connect cannot do (`retains_secret_after_connect = false`), and a second server session for every connection.
- **Returning DDL cut at the limit with a marker**: a cut `CREATE` can still run and create a different object.
- **Faking read-only on QuestDB and TiDB with client-side classification only** (`ClientSideOnly`): violates I3 for engines whose server can enforce it; refused in favour of server-side checks or a refusal.
- **Refusing `postgresql` on a TimescaleDB database**: breaks DBeaver imports that use the PostgreSQL driver for TimescaleDB; the Timescale function list in every pgwire dialect covers the risk instead.
- **Placeholders carrying the column name as is**: a crafted column name could add a statement, a comment or a line to a template.
- **A PostgreSQL `Catalog` level listing every database**: objects of other databases cannot be opened from the session.

## Note on §1.3, §1.4 and §2.4 (metadata gate and mysqlwire navigator reads, 2026-11-19)
Accepted (maintainer, 2026-11-19). Recorded after the P6 local tests batch, in which the editor's warm-up and the table-key read of "Open table data" failed with `Busy` on a session already running a navigator load. It refines how §1.3 (metadata bound to a session, `Busy` while a result streams) and §1.4 (4 driver calls at once per connection) are carried out, and adds a mysqlwire counterpart to the pgwire savepoint of §2.4. The decisions above are unchanged.

1. **One metadata load at a time per session, in FIFO order.** Metadata loads go through a gate on the `SessionHandle`, shared by every `MetadataService` bound to that session, and run one at a time in the order they asked. `MetadataConfig::max_concurrent_requests` (§1.4) is kept for compatibility and no longer used.
2. **Statements and transaction commands take the same gate** before they start, so they wait behind a running load instead of failing with `Busy`. The wait counts toward the statement's timeout; a cancel, a close or a lost tunnel ends it; the cancel is checked again once the gate is granted; past 250 ms the run reports `RunEvent::WaitingForMetadata`, which the editor toolbar shows.
3. **A load fails fast while a statement or a paused result holds the session**: `Busy`, within 250 ms, as §1.3 says. Binding a load to another open session of the connection stays a follow-up (§1.3).
4. **mysqlwire navigator reads in manual-commit mode.** MySQL has no counterpart to §2.4's need for a savepoint: a failed or killed MySQL statement does not abort the transaction. Instead, a navigator read in manual-commit mode that opened an implicit transaction ends it with `ROLLBACK AND NO CHAIN NO RELEASE`; a user transaction is left as it is; a failed rollback closes the session. A pending one-shot `SET TRANSACTION` is issued again after a navigator read, from validated values (never `READ WRITE` in a read-only session); when it cannot be known, it is marked unknown and the navigator is refused on that session. After an error packet, which carries no status flags, the status flags are read again with `COM_PING`.

Details: [docs/02, metadata service](../02-architecture.md#metadata-service-p4-b) and [docs/08, mysqlwire](../08-engine-capabilities.md#mysqlwire-mysql-and-mariadb-p1-b).
