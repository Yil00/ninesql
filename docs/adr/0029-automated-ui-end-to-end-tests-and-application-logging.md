# ADR-0029: Automated UI end-to-end tests and application logging

- **Status**: Proposed (2026-11-19); the design comments of the security review (2026-11-19) are folded into the decision below. Awaiting the maintainer's decision. Once accepted, it adds to [ADR-0004](0004-driver-api-runtime-and-results.md) (I6: the log writer never blocks the UI thread), to the [note on crash output of ADR-0005](0005-secrets-storage.md#note-on-crash-output-p6-e-2026-11-19) (logs, which the note leaves to the existing `tracing` rules) and to [ADR-0010](0010-packaging-and-distribution.md) (a test-only feature that release builds refuse). It changes no decision of those ADRs.
- **Date**: 2026-11-19

## Context
The NineSQL interface has been written without a display since phase 1. Every UI check that needs a window has been deferred to the end-of-MVP tests (P6-F, maintainer): the visual pass on Wayland and X11 and the manual run of the exit scenarios of phases 1 to 5. Today the UI is tested two ways:

- GPUI `TestAppContext` tests of view models and actions (AGENTS.md "Required tests"), **on the mock driver only** (`crates/ninesql-ui/src/**/tests.rs`). No UI test runs against a real engine ([ROADMAP](../ROADMAP.md#phase-4--navigator-and-metadata), phase 4 exit criterion).
- `make e2e-local` ([tutorial](../tutorials/local-e2e.md), `scripts/e2e-local.sh`, 2026-11-19): on the maintainer's desktop, the checks, the unit tests, the engine tests, and a GUI smoke test that opens a window with an empty temporary `HOME` and XDG directories for about 15 s, takes a screenshot only with `--screenshot` (the window of the launched process, found by its pid, on X11 / XWayland; none when no single window matches, never the whole screen, since the security re-review of 2026-11-19), sends `SIGTERM`, and writes a report to send back to a cloud agent session (archived only when gitleaks scanned it clean). The smoke test proves the window starts; it does not click, type or check any screen.

The maintainer wants end-to-end tests they start on their own Linux desktop (display and GPU), fully automated, whose logs, results and screenshots land in the same report. Three ways to drive a real window were weighed:

- **GPUI has no external automation interface.** There is no accessibility tree exposed for automation and no test driver protocol.
- **OS-level input** (`xdotool`, `ydotool`) clicks screen coordinates: brittle against layout, theme and scale changes, and blocked on Wayland by design (only `ydotool` with access to `/dev/uinput`, which is root-level).
- **AT-SPI** would need GPUI's accessibility support, which is not ready (the Orca test is still open, [Phase 0 follow-ups](../ROADMAP.md#phase-0-follow-ups)).

So the window has to be driven from inside the process, through the same GPUI `Action`s that key bindings and the command palette dispatch (AGENTS.md: every user-facing action is an `Action` with a key binding and a palette entry).

Facts that shape the decision, checked on the code at commit 853d6dd:

- **Screenshots from inside the process are not available on Linux.** GPUI (`gpui-pre` 0.3.12) has `Window::render_to_image`, but only behind its `test-support` feature, and only the macOS (Metal) and Windows (DirectX) renderers implement it; the Linux (wgpu) path returns "render_to_image not implemented for this platform". GPUI's `screen-capture` feature pulls `scap`, which `deny.toml` bans ([ADR-0013](0013-gpui-source-and-supply-chain.md)).
- **Nothing reads `RUST_LOG` today.** The `ninesql` binary (`crates/ninesql-ui/src/main.rs`) installs a panic hook and no `tracing` subscriber, and there is no `tracing-subscriber` in the workspace: every `tracing` event of the core, the drivers and the UI is dropped. The e2e harness sets `RUST_LOG=ninesql=debug,info` and says that it has no effect. A failing end-to-end step would leave no trace beyond the panic location.
- **The emit-site logging rules already exist.** Statement text is logged only at `trace`, only when `ConnectParams::log_statements` is set (from the connection type's `log_query_text`), never for production connections, and never when `ninesql_driver_api::hygiene::text_may_hold_credentials` is true; parameter and result values are never logged ([docs/05](../05-security.md), [ADR-0024](0024-phase-3-execution-history-and-preferences-decisions.md) §2). A subscriber cannot know which connection an event came from, so it cannot add the production rule; it can only choose levels, sinks and file safety.
- **Stderr reaches the journal.** A session started from a desktop entry sends stderr to the user journal, kept on disk by systemd-journald and readable by the `adm` and `systemd-journal` groups (P6-E review M2, the [note on crash output](0005-secrets-storage.md#note-on-crash-output-p6-e-2026-11-19)).
- **Release builds are made one way.** `packaging/deb/build.sh` (run by `make deb` and by `release.yml`) builds `cargo build --release --locked --offline -p ninesql-ui --bin ninesql` in the Ubuntu 22.04 builder with no `--features`. `make clippy` and the CI clippy job use `--all-features`.
- **The dev engines use throwaway credentials** listed in `dev/engines.json` (user, password, loopback host and port), and the first-run DBeaver detection reads known install locations under `$HOME`, so a window started with the user's real `$HOME` can show the names of their real DBeaver connections.

Invariants involved: I1 (no secret in logs, results or screenshots), I2 (no network listener, no traffic beyond declared connections), I3 (production confirmations and read-only enforcement are what the scenarios check), I4 (never the user's DBeaver files), I6 (logging and the runner never block the UI thread), I7 (licenses of the new crates).

## Decision

### 1. Step 1: UI tests against the real dev engines (`TestAppContext`)
1. `ninesql-ui` gets `TestAppContext` tests that run the real `pgwire`, `mysqlwire` and `sqlite` drivers (already dependencies of the crate for the binary) against the dev engines **PostgreSQL, MySQL, MariaDB** and a **SQLite file** created in a temporary directory, in addition to the mock-driver tests, which stay.
2. They drive the UI only through the registered `Action`s (the ones key bindings and the palette dispatch) and the view models' public state; they never call core services directly to make a step pass.
3. Scenarios, each on every engine where the driver declares the capability (I8; a capability the driver does not declare is asserted hidden or disabled, not skipped silently):
   - connect (connection dialog, Test connection, open session);
   - "Open table data" on the "nine" dataset, then edit a cell, insert, delete, "Preview changes…" and "Save changes", and read the rows back;
   - "Cancel" / "Stop fetching" on a paged result (the label follows the driver's cancel capability);
   - export to a file and CSV import;
   - the navigator: expand, "Load more", "Find object", the object editor, "Show DDL";
   - a write on a read-only session refused engine-side, with the error shown;
   - a destructive statement on a connection typed production stopped by "Run on production?", and the save and import confirmations on production.
4. Skip rule: the same as the driver integration tests. A test is skipped (not failed) when its engine is not reachable, unless `NINESQL_REQUIRE_ENGINES` lists it.
5. They run in the CI `driver-integration` job (`ninesql-ui` added to its test command and to `ENGINE_TEST_CRATES` in the `Makefile`), in `make test-engines` and therefore in the `engines` stage of `make e2e-local`.
6. Secrets: the tests use the in-memory secret store (`ninesql-secrets` feature `memory-store`, a dev-dependency) and the passwords of `dev/engines.json` only. Every test ends with the existing I1 scan: the dev password must not appear in any file the test wrote.
7. What it proves: view models, actions, confirmations and the core / driver round trip with real engines. What it does not prove: rendering, layout, fonts, GPU, input methods. That is step 2.

### 2. Step 2: a scenario runner in a real window (feature `e2e-scenarios`)
1. **A cargo feature, off by default.** `ninesql-ui` gets a feature `e2e-scenarios`. It is not in `default`, and no other crate of the workspace enables it. All runner code is behind `#[cfg(feature = "e2e-scenarios")]`. It is Linux-only.
2. **Never in a release build.** Three independent guards:
   1. *Compile-time refusal in packaging builds.* `packaging/deb/build.sh` passes `NINESQL_PACKAGE_BUILD=1` into the builder (and the Flatpak manifest sets it when the Flatpak is built). With the feature on, the binary crate contains
      `#[cfg(feature = "e2e-scenarios")] const _: () = assert!(option_env!("NINESQL_PACKAGE_BUILD").is_none(), "e2e-scenarios must not be built for a package");`
      so a package build with the feature fails to compile. Cargo tracks `option_env!` for rebuilds.
   2. *A marker checked after the build.* With the feature on, the binary embeds the fixed string `NINESQL-E2E-SCENARIOS-TEST-BUILD` as a `#[used] static` (so the optimiser and the linker keep it even if nothing reads it) and `ninesql --version` prints `ninesql <version> (e2e-scenarios test build, not for distribution)`. `build.sh` refuses a binary that contains the marker (`grep -a -c`) before cargo-deb packages it; `release.yml` checks the binary again, after the build and before signing, with `strings` and `grep`; and the install test (`packaging/deb/install-test.sh`, run by `make deb-install-test` and `release.yml`) refuses a `--version` line that contains `e2e`.
   3. *A manifest check.* A new `make e2e-feature-guard` target, run by `make check` and the CI `deny` job, reads `cargo metadata --format-version 1 --no-deps` and fails when `e2e-scenarios` appears in the `default` feature of `ninesql-ui` or in the features any workspace crate turns on for `ninesql-ui`.

   `make clippy` and the CI clippy job use `--all-features`, so they compile the runner (it is linted like the rest of the code); they produce no artifact that is packaged or shipped.

   The window title of a test build also carries `[E2E TEST BUILD]`, so every screenshot shows which build took it.
3. **How a run starts.** Only a binary built with the feature accepts `--e2e-run <scenario-file> --e2e-out <directory>`; the release argument parser is unchanged and still refuses every other argument (status 2). No environment variable starts a run, so a stray variable in the user's session cannot. `make e2e-local` gains a `scenarios` stage that builds the test binary (`cargo build --release -p ninesql-ui --bin ninesql --features e2e-scenarios`, into its own target subdirectory so it never replaces `target/release/ninesql`) and runs each scenario file.
4. **Isolation from the user's data (refuses to start otherwise).** The harness creates one fresh run directory and sets `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` inside it (`XDG_RUNTIME_DIR` and the display variables stay, the window needs them). Before GPUI starts, the runner checks that all five are set, absolute, inside one directory that is owned by the user with mode `0700`, that contains the `--e2e-out` directory, and whose NineSQL subdirectories are empty at start; that this directory is not the user's account home directory (read from the password database, not from `$HOME`) nor any of the default XDG locations under it; and that it lies under the system temporary directory or under the repository's `target/`. Any failed check stops the run before anything is read or written, with status 2 and a fixed message. A separate `HOME` also keeps the first-run DBeaver detection away from the user's real DBeaver workspaces (I4, and their connection names stay out of screenshots).
5. **Connections only to the dev engines, enforced in the core.** A scenario names dev engine ids (`postgresql`, `mysql`, `mariadb`) and SQLite files by name. The runner builds the connections itself from `dev/engines.json` (path given in the scenario file, resolved inside the repository). The loopback rule is not left to the runner: with the feature on, `ninesql-core` compiles an endpoint filter into `SessionManager::open` and the driver registry that resolves every network endpoint of a connection, SSH hops and jump hosts included, and refuses the open unless every resolved address is a loopback address (checked after DNS resolution, so a name that resolves elsewhere is refused). A connection created through the UI during a scenario goes through the same filter, so a scenario cannot reach another host (I2). SQLite files are created inside the run directory; DBeaver import scenarios use copies of the synthetic fixtures of `crates/ninesql-dbeaver/tests/fixtures/` in the run directory.
   - *File targets.* In a test build, the file targets of the export dialogs, the CSV import and "Export connections to DBeaver…" are refused unless they lie inside the run directory, so a scenario cannot write elsewhere on the user's disk.
   - *Secrets.* The runner forces the encrypted-vault backend in the run directory, with a master password generated at random per run and never written anywhere, and refuses to start (status 2) if the binary was built with the `secret-service` feature, so a scenario never reads or writes the user's keyring.
   - *Scenario files are code.* A scenario dispatches actions on real sessions; scenario files live in the repository and are reviewed like source code. The runner reads only the file named by `--e2e-run`.
6. **What a scenario is.** A TOML file (the format `settings.toml` uses), a list of steps:
   - `action`: dispatch a registered action by its full name, the name keymap overrides use (`"ninesql_editor::ExecuteStatement"`), to the focused element, as a key binding would;
   - `keys` / `text`: keystrokes and text delivered through GPUI's own keystroke dispatch to the focused element (the path a real key press takes after the platform layer), never through OS input injection;
   - `wait`: wait until a named view state matches (for example a dialog titled "Run on production?" is open, the grid has at least N rows, a status entry reads a given label), with a per-step timeout (default 10 s, at most 120 s) and a whole-run timeout (default 15 min);
   - `checkpoint`: a named screenshot point (§2.7);
   - `expect`: an assertion on a view state, recorded pass or fail.

   View states are read through a read-only probe compiled only with the feature: named, typed getters over the view models (no access to secret fields, which the UI never formats anyway). Steps run as one task on the GPUI foreground executor with GPUI timers; the runner never blocks the UI thread (I6).
7. **Screenshots: captured by the harness, of the NineSQL window only.** Because GPUI cannot capture a frame on Linux (Context), the runner, at a `checkpoint`, waits until the state of the step has been presented in a frame, writes one line `ninesql-e2e checkpoint <n> <name>` to its standard output (a pipe the harness owns), and holds the UI still for a fixed time (`checkpoint_hold_ms`, default 1 500 ms). The harness captures **the NineSQL window only**, never the whole screen:
   - on X11, and on Wayland through XWayland (the harness unsets `WAYLAND_DISPLAY` for the run, so GPUI uses its X11 backend), with ImageMagick `import -window <id>`, the id found by the pid of the process the harness started (`xdotool search --pid`, or the pid column of `wmctrl -lp`), never by WM_CLASS alone, so a NineSQL window of the maintainer's own is never picked; when none or several windows match, no screenshot is taken and the report says why. Before each capture the harness activates and raises the window (`xdotool windowactivate --sync`, or `wmctrl -i -a`) so no other window or notification covers it; nothing clicks or types. `import -window` still copies the window's screen area, so an overlapping popup can appear: screenshots are not scrubbed, and the report tells the user to check them before sending;
   - native Wayland screenshots: a run inside a nested compositor dedicated to the run, captured whole (it holds only NineSQL); see open question 4.

   If GPUI later implements `render_to_image` on Linux, a new ADR may move capture into the process (it would bring GPUI's `test-support` into the test build).
8. **Results.** The runner writes `results.json` in the `--e2e-out` directory: schema version, commit, scenario, per step the name, kind, outcome (`pass`, `fail`, `timeout`, `skipped` with the reason), duration and the checkpoint names, and the window size and scale factor. It holds no statement text typed into a production connection's editor, no parameter value, no cell value and no password; failure messages are the UI's own user-facing messages. The harness adds the screenshots and the logs (§3) to the `make e2e-local` report.
9. **No listener, socket or inbound channel.** The runner opens no port, no Unix socket, no D-Bus name, no named pipe, and reads nothing at run time but its scenario file, `dev/engines.json` and its own run directory. Its only output channel besides files is its standard output, and it takes no input from the harness during a run (no acknowledgement on stdin; the fixed hold replaces it). D-Bus use is the application's own (the lock watcher), unchanged.
10. **I1 check of every run.** At the end of a run, the runner scans every file under the run directory (results, logs, workspace files, vault excepted as ciphertext) for each password of `dev/engines.json` and for the run's master password, and fails the run if one appears. Screenshots cannot be scanned this way; they show what the UI shows, and the UI never formats a password (AGENTS.md).
11. **P6-F becomes a review.** The visual pass of P6-F becomes a review of these screenshots by the maintainer, or by a cloud agent session that reads them from the report. What stays manual: input methods (IME), HiDPI and fractional scaling on real monitors, the Orca test, drag gestures, the check of the DBeaver export in DBeaver itself, and anything the scenarios do not cover yet.

### 3. Application logging (both steps, and every user)
1. **A subscriber in the binary only.** `tracing-subscriber` is added as a dependency of `ninesql-ui` for the `ninesql` binary (`fmt` and `env-filter` features, `ansi` off). Library crates keep emitting `tracing` events and never install a subscriber. The panic hook of `main.rs` is unchanged and stays installed first; panics do not go through `tracing`.
2. **Stderr, on by default, at `warn`.** By default the binary logs events at `warn` and above to stderr, one line per event, with no ANSI colours. `info` and `debug` are opt-in, so a desktop session's journal receives only warnings and errors, which by the emit-site rules carry no statement text and no value.
   - *Prerequisite, before stderr at `warn` goes live:* an audit of the existing `warn` / `error` events that log an error with `error = %e` (28 at the review, for example in `ninesql-driver-pgwire/src/cancel.rs`, `ninesql-ssh/src/tunnel.rs`, `ninesql-core/src/history.rs`, `ninesql-driver-api/src/result.rs`). An engine's error message can quote values (a duplicate key, a failing cast), so none of those events may carry the engine's message: they log a `driver_error_kind` (the typed error variant) instead, and the message stays in the UI. Stderr at `warn` is not turned on before that audit lands.
3. **A file log, off by default.** A file log is opt-in: `[logging] file_level` in `settings.toml` (`"off"` by default; `"error"`, `"warn"`, `"info"` or `"debug"`), or the filter of §3.4 for one run. It writes to `$XDG_STATE_HOME/ninesql/logs/ninesql.log`:
   - the `logs` directory created `0700`, the file `0600`, opened with `O_NOFOLLOW` and refused when it is not a regular file owned by the user (the rules of `history.sqlite`, ADR-0024 §2.4);
   - size cap and rotation: at most 8 MiB per file; on reaching it, and at startup when the file is over the cap, `ninesql.log` becomes `ninesql.log.1`, `.1` becomes `.2`, and `.2` is deleted, so at most 24 MiB in three files;
   - written by one background thread through a bounded channel; when the channel is full, events are dropped and counted, and the count is logged once the channel drains (I6: the UI thread never waits on the disk).
4. **Filter.** The `NINESQL_LOG` environment variable takes the `RUST_LOG` syntax (`ninesql_core=debug,warn`) and applies to both sinks for that run; it also turns the file log on at its level. `RUST_LOG` itself is ignored, so a value set for other tools in the user's session does not change what NineSQL writes. The harness of `make e2e-local` sets `NINESQL_LOG` instead of `RUST_LOG`.
5. **`trace` is clamped in release builds.** In release builds the subscriber caps every filter at `debug` whatever `NINESQL_LOG` or `settings.toml` says, and says once at startup that it did. `trace` (where statement text lives) is available in debug builds only. The emit-site rules stay the protection that matters (never production, never `log_query_text = false`, never a statement with a credential word); the clamp adds that a shipped binary writes no statement text at all, since the lexical credential rule cannot catch every secret (a secret typed as a literal in an `INSERT`, a credential built by concatenation).
6. **Nothing new may be logged.** No password, passphrase, token, parameter value or result value, at any level (I1, unchanged). Statement text only as today. Field values are formatted with control characters escaped (newlines, carriage returns, ANSI escape sequences), so a value cannot forge a log line or drive the terminal: either through a custom field formatter of our own, or by pinning a `tracing-subscriber` version whose escaping is known, with a test that fails if the behaviour changes. Code that logs a statement goes through `ninesql_driver_api::hygiene::may_log_statement_text`, as the core and the drivers already do.
7. **Tests.** The implementing PR adds tests that the release clamp holds, that the file is `0600` in a `0700` directory and refuses a symbolic link, that rotation keeps at most three files, that a full channel drops instead of blocking, that a field holding a newline or an ANSI escape sequence comes out escaped on both sinks, and an I1 test that runs a connect, a statement with a credential word and a production statement with the file log at `debug` and finds neither the password nor the statement text in the log.

## Consequences
- Step 1 gives regression tests of the UI against real engines in CI, cheap to run and with no display; it closes "the UI tested on the mock driver only" for PostgreSQL, MySQL, MariaDB and SQLite. `TestAppContext` runs a deterministic executor while the drivers do real I/O on Tokio, so these tests must poll with real time and parking allowed; they will be slower and may need care against flakiness.
- Step 2 makes the P6-F visual pass repeatable: the same scenarios on every commit the maintainer runs, screenshots named by checkpoint, results in JSON a cloud session can read. It adds a test-only code path to the binary crate and to `ninesql-core` (the endpoint filter and the file-target rule), which three guards keep out of packages; a mistake in the guards would ship a binary that accepts `--e2e-run`. The runner refuses user data, but it is still code that dispatches actions on a real session: it needs a `security-reviewer` review, like the driver API.
- The probe of view states is a second, test-only interface of the UI that has to follow UI changes; a renamed label breaks scenarios. Scenarios should wait on named states rather than on label text where possible.
- Screenshots depend on an external tool and on X11 / XWayland in the first version; native Wayland rendering is screenshotted only once open question 4 is settled. Screenshots of the NineSQL window only, raised before capture, replace the smoke test's opt-in screenshot and its whole-screen fallback.
- Users get logs: warnings on stderr by default, and a file log they can turn on to attach to a bug report. A file log is a new file with sensitive context (connection names, hosts, error messages); it is `0600`, bounded and off by default, and the [troubleshooting page](../user-guide/troubleshooting.md) of the user guide, which says today that NineSQL writes no log file, must say what the file holds and how to turn it on.
- The `make e2e-local` report gains `ninesql.log` and per-scenario results, and its tutorial changes (`NINESQL_LOG`, the `scenarios` stage, window-only screenshots).
- To document when implemented: [docs/05](../05-security.md) (logging rules, the test build), the [tutorial](../tutorials/local-e2e.md), [user guide troubleshooting](../user-guide/troubleshooting.md), [packaging/README.md](../../packaging/README.md) (the guards), the ROADMAP (P6-G, P6-F).

## Security notes per invariant
- **I1.** No password, parameter value or result value in logs (§3.6), in results (§2.8) or on screen (the UI never formats a password). The release `trace` clamp keeps statement text out of shipped logs. The file log is `0600` in a `0700` directory, bounded. Every scenario run scans its files for the dev passwords and the run's master password (§2.10). The runner forces the vault and refuses a build with `secret-service`, so the user's keyring is never touched (§2.5). Warnings on stderr carry an error kind, not an engine message (§3.2). Stderr defaults to `warn`, which addresses the journal concern of P6-E M2 for logs as the panic hook does for panics.
- **I2.** No listener, socket, D-Bus name or inbound channel in the runner (§2.9); connections only to loopback endpoints, enforced in the core after DNS resolution with SSH hops included (§2.5). The subscriber writes to stderr and a local file only; no log shipping.
- **I3.** Unchanged; read-only refusal and production confirmations become scenarios (§1.3). A scenario cannot skip a confirmation: it answers it through the dialog's own actions, as a user does.
- **I4.** A separate `HOME` and XDG directories keep the first-run detection away from the user's DBeaver workspaces; import scenarios use synthetic fixtures copied into the run directory, and in a test build exports, including "Export connections to DBeaver…", write only inside the run directory (§2.5).
- **I5.** Unchanged. Dev connections that use TLS use the throwaway CA of `dev/`; a scenario that turns a check off does it through the connection dialog's visible, per-connection setting.
- **I6.** The log writer runs on a background thread with a bounded, lossy channel; the runner's steps are a foreground task with timers, never a blocking wait.
- **I7.** `tracing-subscriber` is declared MIT on crates.io (the `tracing` crates are MIT; `tracing-core` 0.1.36 in `Cargo.lock` is MIT), and its dependencies for `fmt` and `env-filter` (such as `sharded-slab`, `thread_local`, `matchers`, `regex-automata`) are expected to be MIT or MIT / Apache-2.0. The implementing PR confirms it with `cargo deny check licenses`. No GPUI feature is added (`test-support` and `screen-capture` stay out of the binary).
- **I8.** Unchanged; step 1 asserts that undeclared capabilities are hidden or disabled.

## Open questions for the maintainer
1. **`trace` in release builds.** This ADR clamps release logs at `debug` (§3.5). The alternative is to allow `trace` in release behind `NINESQL_LOG` with a warning at startup, which helps diagnose a user's problem with statement text on non-production connections. Which one? **Decided (maintainer, 2026-11-19): clamp release logs at `debug`, as proposed.**
2. **Stderr default level.** `warn` (proposed) or `info`? `info` gives more context in a bug report but sends more to the journal.
3. **Filter variable.** `NINESQL_LOG` with `RUST_LOG` ignored (proposed), or honour `RUST_LOG` as the harness assumes today? **Decided (maintainer, 2026-11-19): `NINESQL_LOG` only, `RUST_LOG` ignored; the harness moves to `NINESQL_LOG`.**
4. **Native Wayland screenshots.** First version: X11 and XWayland only (proposed). For native Wayland, a nested compositor dedicated to the run (for example `cage` with `grim`, which captures only that compositor's output), or accept the desktop's own screenshot tool on the whole screen with the current warning? Which compositor and tool, if any, should the harness depend on? **Decided (maintainer, 2026-11-19): X11 and XWayland only in the first version; no nested compositor dependency.**
5. **Checkpoint handshake.** A fixed hold at each checkpoint (proposed, no inbound channel) can miss a slow capture. A one-line acknowledgement from the harness on the runner's stdin would be exact; it is an inherited pipe, not a listener, but it is an inbound channel. Is that acceptable?
6. **File log switch.** `[logging] file_level` in `settings.toml` with no preferences page yet (the user edits the file) is proposed; should the file log also get an action in the palette ("Open log folder", "Turn file log on for this session")?
7. **Where step 2 runs.** Only on the maintainer's desktop through `make e2e-local` (proposed), or also on a CI runner with a software renderer (llvmpipe under Xvfb), which proves no GPU but would catch broken scenarios earlier? **Decided (maintainer, 2026-11-19): only on the maintainer's desktop through `make e2e-local`.**

## Rejected alternatives
- **OS-level input injection** (`xdotool`, `ydotool`): coordinates break with layout, theme and scale; blocked on Wayland except through `/dev/uinput`, which needs root-level access.
- **AT-SPI automation**: depends on GPUI accessibility, which is not ready; reconsider after the Orca test.
- **A control socket or local HTTP endpoint in a test build** (WebDriver-like): a listener other local users or processes could reach, against I2 and the attack-surface rule, and a channel that could be left on by mistake; the file-based scenario runner needs none.
- **Scenarios started by an environment variable**: a stray variable in the user's session could start one; an argument accepted only by the test build is explicit.
- **The runner in every build, refused at run time**: the code would ship in packages; a compile-time feature keeps it out entirely.
- **Whole-screen screenshots**: capture other windows and notifications of the user's desktop; the window-only capture replaces the current smoke test's.
- **GPUI's `screen-capture` feature**: pulls `scap`, banned by `deny.toml` (ADR-0013), and is a screen-sharing API, not a frame capture.
- **Logging: stderr only, no file log.** Simplest, but a user launched from a desktop entry has only the journal, which this ADR wants to keep to warnings, and the e2e report needs a log file per run. Rejected in favour of an opt-in file log.
- **Logging: no subscriber at all (today).** Every event of the core and drivers is lost, so neither a user's bug report nor an e2e failure carries context.
- **`tracing-appender` rolling files**: rotates by time, not size, and creates files with the process umask, not `0600`; its non-blocking writer may still be used for §3.3.
- **A compile-time `trace` strip (`tracing` feature `release_max_level_debug`)**: removes `trace` call sites from every crate in release builds, a stronger guarantee than the runtime clamp of §3.5, but it also changes what the tests of `cargo test --release` see; it remains an option if the maintainer prefers it to the runtime clamp (open question 1).
