# ADR-0007: Production safety model

- **Status**: Accepted. Note (P1-D core, 2026-11-14): §3 is extended to init SQL, which is classified and confirmed when it would run at connect, not refused when saved ([docs/02](../02-architecture.md#confirmations-adr-0007-adr-0011)). Amended (classifier, accepted by the maintainer on 2026-11-15) in the [section at the end](#amendment-classifier-2026-11-15): two deliberate over-classifications of `EXPLAIN` / `DESCRIBE` and `ANALYZE`, and `CREATE OR REPLACE` as destructive. Amendment (phase 5, 2026-11-16, **Accepted** by the maintainer on 2026-11-17) in the [section at the end](#amendment-phase-5-2026-11-16): one confirmation for a bulk write (CSV import) and for a grid save, how their tokens are bound, the manual-commit save under a savepoint, and exports that run reads only.
- **Date**: 2026-11-14

## Context
DBeaver offers connection types (Development, Test, Production) with a color, an auto-commit default, "confirm SQL execution" and a read-only flag. The read-only flag is mostly enforced on the client side through JDBC `setReadOnly`, whose effect depends on the driver. Incidents with GUI clients often come from a statement run in the wrong tab.

## Decision
1. **Connection types**: Development, Test, Production built in (DBeaver-compatible names and default colors), user-defined types allowed. Each type sets: color, auto-commit default, confirm destructive statements, confirm every write, read-only default, and whether query text may be logged.
2. **Read-only is engine-side** (I3). When a session is read-only, the driver applies the engine's mechanism (e.g. `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY` on PostgreSQL, `SET SESSION TRANSACTION READ ONLY` on MySQL / MariaDB, `PRAGMA query_only = ON` on SQLite, a read-only open mode for file engines, the engine's read-only user or option where nothing else exists). An engine without any engine-side mechanism declares `read_only: ClientSideOnly` in its capabilities, and the UI says so in plain words.
3. **Destructive statement guard**: on connections whose type asks for confirmation, statements are classified by the dialect's parser before execution (`DROP`, `TRUNCATE`, `DELETE` / `UPDATE` without `WHERE`, `ALTER`, `GRANT` / `REVOKE`, and engine-specific equivalents such as `FLUSHALL` on Redis or `dropDatabase` on MongoDB). The dialog shows the exact statement and the connection name typed in color. Unparseable statements count as destructive.
4. **Visual identity**: the connection color frames the editor tab and the results; the type name is always visible in the status bar.
5. **Manual commit by default for Production**, with a pending-transaction indicator and a confirmation when closing a tab with an open transaction.
6. Production connections never log query text, even at `trace` level.

## Consequences
- Each dialect needs a statement classifier good enough to find destructive statements across comments, case, multiple statements and CTEs; it gets property tests and a corpus of tricky cases.
- The engine-side mechanism of each engine is listed in [docs/08-engine-capabilities.md](../08-engine-capabilities.md).
- Users with a wrongly typed connection are still at risk: the import from DBeaver keeps their existing types, and the connection dialog asks for the type explicitly when creating a connection.

## Rejected alternatives
- **Client-side read-only only**: bypassable by any statement the client fails to classify.
- **Regex-based detection**: misses comments, quoting and multi-statement scripts.

## Amendment (classifier, 2026-11-15)
**Status: Accepted** (maintainer, 2026-11-15). It adds to Decision §3 and changes none of its points. Raised by the P1-E review (M1). Behaviour as implemented by commit 3291ca0 (`fix(driver-api): classify running EXPLAIN forms and CREATE OR REPLACE`, branch `fix/p2-pre-classifier`, security-reviewed; merged into the pre-phase-2 integration branch on 2026-11-15, it reaches `dev` with that PR): the shared statement classifier of `ninesql-driver-api` and its conformance lists `POSTGRES_EXPLAIN_WRITES` and `MYSQL_EXPLAIN_WRITES`.

**Context.** §3 classifies statements before execution, and the same classes decide what a read-only session refuses client-side (I3, on top of the engine-side mechanism). Some `EXPLAIN` forms run the statement they explain: PostgreSQL `EXPLAIN ANALYZE`, with the option also written quoted or `U&`-escaped inside a parenthesised list (`EXPLAIN ("analyze") DELETE …`, `EXPLAIN (U&"analyze") DELETE …`), MySQL `EXPLAIN ANALYZE`, MariaDB `EXPLAIN ANALYZE` and `DESC ANALYZE`, and MariaDB `ANALYZE <statement>`. The classifier used to detect `ANALYZE` as a bare word only, so `EXPLAIN ("analyze") DELETE FROM t` was a read and skipped the production confirmation while PostgreSQL deleted the rows. Reading every option list exactly as each engine does would make the classifier depend on engine and version details it cannot see.

**Decision.** The classifier errs on the side of confirmation, in two deliberate over-classifications:
1. An `EXPLAIN` / `DESCRIBE` / `DESC` with a **parenthesised option list**, or with `ANALYZE` / `ANALYSE` **in any form** (bare, quoted, backquoted, `U&`-escaped), is classified as the statement it would run: the riskiest of the statements starting at any explainable keyword after it, never below `Read`, and `Unknown` when nothing explainable follows the options or the list is unbalanced. So `EXPLAIN (FORMAT JSON) DELETE FROM t` asks for confirmation on a production connection and is refused in a read-only session, although PostgreSQL does not run the `DELETE` for it.
2. **Every statement starting with `ANALYZE` / `ANALYSE` is `Unknown`**, whatever follows (MariaDB `ANALYZE <statement>` runs the statement; `ANALYZE [TABLE] t` writes statistics on PostgreSQL, MySQL and SQLite). So MariaDB `ANALYZE SELECT …` is refused in read-only sessions and confirmed on production, although it only reads.
3. A plain `EXPLAIN` (no option list, no `ANALYZE`), SQLite `EXPLAIN [QUERY PLAN]` and `DESCRIBE t` stay reads.
4. `CREATE OR REPLACE …` is `Destructive`, not `Ddl`: it silently overwrites an existing object, which the production rule (confirm destructive statements) would otherwise not confirm.

**Consequences.**
- No form of `EXPLAIN` or `ANALYZE` that runs a write can skip the production confirmation or pass the client-side read-only check.
- False positives, accepted: an `EXPLAIN` with options but without `ANALYZE` asks for a confirmation it does not need, and `ANALYZE SELECT` cannot be used in a read-only session on MariaDB. A user who needs a plan in a read-only session uses a plain `EXPLAIN`.
- The conformance lists `POSTGRES_EXPLAIN_WRITES` and `MYSQL_EXPLAIN_WRITES` are part of `writes_for(engine)`, so each driver's read-only tests also check that these forms are refused engine-side.
- Narrowing either rule later (for example, reading PostgreSQL option lists exactly) needs a new amendment or ADR and a security review.

**Rejected alternatives.**
- **Parse each engine's `EXPLAIN` options exactly**: depends on engine and version (option names, boolean spellings, quoting), and a single misread option hides a write from the confirmation.
- **Treat every `EXPLAIN` as a read**: lets `EXPLAIN ANALYZE DELETE` through without confirmation.
- **Treat every `EXPLAIN` as `Unknown`**: plain `EXPLAIN SELECT` and `DESCRIBE t`, which never run anything, would need confirmation and be refused in read-only sessions.

## Amendment (phase 5, 2026-11-16)
**Status: Accepted** (maintainer, 2026-11-17; proposed 2026-11-16). It adds to Decision §3 and §5 and changes none of their points. Raised by the phase 5 task reports and the security reviews of P5-C (import confirmation binding, read-only exports, session leases) and of the P5-A core (save confirmation key, savepoint, rollback reporting). Behaviour as implemented on the session branch at commit ccc7215: `crates/ninesql-core/src/transfer.rs` (`TransferService`, `ImportToken`, `ImportKey`, `ExportTask::begin_read_only`) and `crates/ninesql-core/src/edit/mod.rs` (`EditService::save`, `SaveToken`, `SaveKey`); their rustdoc is the reference.

**Context.** §3 confirms statements one by one: on a type that confirms every write, a CSV import of 100 000 rows (up to 1 000 rows per `INSERT`) or a grid save of many rows would ask once per statement, which trains users to click through, and the dialog would show statements the user did not write. Asking once instead needs a confirmation that cannot be reused for something else: another file, a file changed after it was shown, another table or mapping, other values. §5 gives production manual commit by default, so a save must not commit the user's transaction behind their back. And an export runs its statement again: if it ever ran a write, nobody would have confirmed it.

**Decision.**
1. **One confirmation per bulk write and per save.** On a connection typed production, or whose type confirms every write, a CSV import and a grid save ask **once**, before anything is sent: the first call ends with a confirmation request (`ImportEvent::NeedsConfirmation`, `SaveEvent::NeedsConfirmation`) and nothing is sent. The import confirmation shows the connection (and whether it is production), the table and the mapped columns as they will be sent, the statement shape (one row), the resolved file and its size. The save confirmation shows the connection, the table, the counts (updated, inserted, deleted), the columns left out of the concurrency check and the exact preview script of every statement. The user's answer is sent back as a token with the same request.
2. **Token binding.** Tokens are single-use (consumed on the first redeem, whether it matches or not), valid **10 minutes**, kept in memory only (at most 16 pending per service):
   - the **import token** is bound to the session, the canonical file, the file's identity read with `fstat` on the opened handle (device, inode, length, modification time with nanoseconds), the table, the target columns, the full source-to-target mapping in insert order, the transaction mode and the skip-invalid-rows choice;
   - the **save token** is bound to the session, the table and a SHA-256 digest of the table name parts, every statement text and every parameter value, in order (the service keeps the digest, not a copy).
   
   A token that does not match, has expired or was used already is refused (`InvalidConfirmation`), and the user confirms again.
3. **Per-statement confirmations after it.** Once a job is confirmed, the session still asks its own §3 confirmation for each statement (types that confirm every write). The service answers it only for the statement it just sent: same text, byte for byte, same number of parameters, classified `Write`; and only once per statement. Any other confirmation request fails the job (`UnexpectedConfirmation`): the save is undone, and the import stops with its open transaction rolled back (with "commit every N rows", batches committed before stay). Every generated statement is also self-checked before it is sent (one statement, classified as a filtered `Write`).
4. **Manual-commit save under a savepoint.** In manual-commit mode (production by default, §5) a save runs inside the session's transaction (opened with `BEGIN` when none is) under a savepoint with a random name (`ninesql_edit_save_<random>`). On success the savepoint is released and the transaction stays open: the changes are committed only by the user's own commit. On failure `ROLLBACK TO SAVEPOINT` undoes the save alone; if that fails, the whole transaction is rolled back and the save fails with an error that says earlier uncommitted work was lost too (`TransactionRolledBack`). A driver without savepoints refuses saves in manual-commit mode. In auto-commit mode the save runs in a transaction of its own and refuses a session with an open transaction.
5. **Exports run reads only.** An export's statement must classify as `Read` with the session's dialect; anything else is refused before it runs (`NotARead`), and a confirmation request during an export fails it. When the session is not read-only, has transactions and has none open, the export runs inside an engine-side read-only transaction (PostgreSQL family `BEGIN READ ONLY`, MySQL family `START TRANSACTION READ ONLY`; none on SQLite and engines without transactions), rolled back before the export reports its end. On a production or confirm-every-write connection the export is **refused** when a transaction is already open on the session, and fails when the read-only transaction cannot be opened; on other types it reads inside the open transaction, or without a read-only transaction, with a warning shown to the user.

**Consequences.**
- A bulk import on a confirm-every-write type asks once; the per-statement guard still runs on every statement and can only be answered for the exact statement the confirmed job sends.
- Changing the file (content, size, modification time, or a replacement under the same name), the mapping, the transaction mode or the skip-invalid choice after the confirmation, or any edited value or statement of a save, makes the token useless.
- A confirmation that expires while the user reads it must be given again; tokens do not survive a restart.
- A side-effect function the classifier reads as a read is still refused by the engine inside an export's read-only transaction; on SQLite and engines without transactions only the classifier and the session's read-only mode apply.
- Tests: the import and save confirmations and the per-statement answers on the mock driver (`csv_import_refusals_and_production_confirmation` in `crates/ninesql-core/tests/transfer.rs`; `production_confirms_the_whole_save_once`, `confirm_every_write_type_answers_only_the_confirmed_statements` in `edit.rs`); the export's read-only transaction on PostgreSQL (`transfer_engines.rs`); the manual-commit savepoint on PostgreSQL, MySQL, MariaDB and SQLite (`edit_engines.rs`).
- Widening a token's scope (one confirmation for several files, tables or saves) or answering per-statement confirmations for statements the job did not send needs a new amendment or ADR and a security review.

> **Note (2026-11-18, P5-E end-of-phase review).** Two decisions this amendment left implicit, recorded without changing its points:
> 1. **The import commits its own rows, also on a manual-commit session.** Unlike a grid save (Decision 4), a CSV import opens and commits its own transactions whatever the session's mode: at the end with "All or nothing", every N rows with "commit every N rows". A session in manual-commit mode (production by default, §5) therefore does not hold the import's rows for the user's own commit, and its "Roll back" cannot undo them. The import refuses a session with an open transaction, so it never commits earlier work of the user's. The confirmation carries the mode and this fact (`ImportConfirmation::transaction`, `session_manual_commit`, `non_transactional`) so the UI says "Rows are committed by the import; Roll back cannot undo them". The token also binds the CSV syntax and value options and whether the target table can roll back (P5-E L5, M1).
> 2. **TiDB exports have no engine-side read-only transaction.** TiDB treats `START TRANSACTION READ ONLY` as a no-op (refused with error 1235 unless `tidb_enable_noop_functions` is on, then accepted without effect), so Decision 5 cannot protect a TiDB export. NineSQL does not send it on TiDB: on a session that is not read-only, a TiDB export has the `Read` classifier check only, is **refused** on production and confirm-every-write connections (`TransferJobError::NoReadOnlyTransaction`), and runs with a warning on every other type (`ExportWarning::NoReadOnlyTransaction`). A read-only TiDB session (enforced engine-side by the driver, ADR-0026 §3.2) exports normally. Tests: `export_read_only_transaction_mysql_and_tidb` in `crates/ninesql-core/tests/transfer_engines.rs`.

**Rejected alternatives.**
- **Ask for every statement of an import or a save**: hundreds of dialogs for one action, which teaches users to confirm without reading; the statements are generated, so showing them one by one adds nothing.
- **Skip the per-statement guard once a job is confirmed**: a bug in the job could then send any write unconfirmed; answering only the byte-identical statement keeps the guard meaningful.
- **Bind the import token to the path only**: a file replaced or edited between the confirmation and the import would be imported without having been shown.
- **Commit a manual-commit save at once**: would also commit the user's earlier uncommitted statements, against §5.
- **Run exports as the user typed them, without the `Read` check**: re-running a write from "Export results…" would write again, unconfirmed.
