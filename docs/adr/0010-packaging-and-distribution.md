# ADR-0010: Packaging and distribution

- **Status**: Accepted. Note (P1-D wiring, 2026-11-15): the Flatpak permissions of §3 also include `--system-talk-name=org.freedesktop.login1` (logind on the system bus, to lock secrets on sleep and screen lock), and "network" is `--share=network`, which Flatpak grants all-or-nothing: NineSQL itself limits network use to the user's connections and their SSH / proxy hops (I2). See the [amendment of ADR-0005](0005-secrets-storage.md#amendment-p1-d-wiring-2026-11-15) and [docs/10](../10-supported-platforms.md#flatpak-permissions). [Amendment (P6-A packaging, 2026-11-19)](#amendment-p6-a-packaging-2026-11-19): Accepted (maintainer, 2026-11-19). A [dated note on that amendment](#note-on-the-p6-a-amendment-what-v010-ships-2026-11-19) (2026-11-19) records that v0.1.0 ships as a cosign-signed `.deb` on the GitHub release only; the APT repository (§2) and Flathub (§3) come later.
- **Date**: 2026-11-14

## Context
NineSQL targets Debian and Ubuntu desktops. Users of a security-minded database client should be able to verify what they install. A `curl … | bash` installer runs unverified code as the user, often with `sudo`.

## Decision
1. **`.deb`** built with `cargo-deb`, for `amd64` (and `arm64` when CI capacity allows): binary, `.desktop` file, hicolor SVG / PNG icons, AppStream metainfo, MIME type for `.sql`, man page, third-party license file. No maintainer script that touches the network.
2. **Signed APT repository** served from GitHub Pages (or equivalent static hosting): `Release` / `InRelease` signed with a dedicated OpenPGP key whose fingerprint is published in `SECURITY.md` and the README; installation uses a `signed-by=` keyring file in `/usr/share/keyrings/`, never `apt-key`.
3. **Flatpak** published on Flathub, with the narrowest permissions that work: network, Wayland / X11 fallback, GPU (`--device=dri`), Secret Service D-Bus name, file access through portals (no `--filesystem=home` by default). The SSH agent socket is opt-in and documented.
4. **Release assets** on GitHub Releases: `.deb`, `SHA256SUMS`, signatures (Sigstore / cosign keyless from the tag-push workflow), SBOM (CycloneDX).
5. **Reproducible builds**: pinned toolchain, `--locked`, `SOURCE_DATE_EPOCH`; CI checks that two builds of the same tag produce the same `.deb`.
6. **No `curl | bash` installer**, ever. A one-line command in the docs is allowed only when it downloads a signed key and adds the APT source, written out in full.
7. **Supported platforms** are listed in [docs/10-supported-platforms.md](../10-supported-platforms.md) and tested in CI with an install test in containers of each distribution (package installs, binary starts with `--version`, desktop file valid).

## Consequences
- Release work (keys, Flathub submission, Pages setup) is a maintainer task in P6 and cannot be delegated to agents.
- Flatpak sandboxing complicates SSH agent access and local socket connections (e.g. PostgreSQL over a Unix socket); the user guide documents the overrides.

## Rejected alternatives
- **Snap**: an option for later; Flatpak first because it is distribution-neutral and preferred on Debian.
- **AppImage only**: no sandbox, no update channel, weaker integration.
- **Upstream Debian packaging first**: the long-term goal, but Debian's Rust packaging policy (every crate packaged) makes it a post-1.0 effort.

## Amendment (P6-A packaging, 2026-11-19)
- **Status**: **Accepted (maintainer, 2026-11-19)**. It records the decisions the P6-A packaging work took ([packaging/README.md](../../packaging/README.md), `packaging/`, `.github/workflows/release.yml`) and the follow-ups of its security review. It adds to the decision above; where it departs from this ADR or from the [ADR-0005 P1-D amendment](0005-secrets-storage.md#amendment-p1-d-wiring-2026-11-15), it says so.

**Context.** The first `.deb`, Flatpak manifest and release workflow (P6-A) had to settle points this ADR leaves open (the application id, the Flatpak's file access, how far reproducibility goes, who can produce a release signature), and the security review of that work found that a file chosen through the Flatpak document portal escaped the DBeaver check (I4).

**Decision.**
1. **Application id** `io.github.yil00.NineSQL` (confirmed by the maintainer, 2026-11-19), the same for the desktop file, icons, AppStream id, Flatpak id and the window's Wayland app id / X11 `WM_CLASS`. It is settled before the first release because changing it moves the Flatpak's data directory.
2. **No Secret Service in the Flatpak while `secret-service` is off.** The manifest does not declare `--talk-name=org.freedesktop.secrets` as long as the build does not enable the `secret-service` feature (off by default, [ADR-0012](0012-secret-service-client-and-msrv.md)); the Flatpak keeps saved passwords in the encrypted vault. `packaging/flatpak/lint-manifest.py` requires both or neither (the feature on the `cargo build` line and the permission). This **deviates from point 6 of the [ADR-0005 P1-D amendment](0005-secrets-storage.md#amendment-p1-d-wiring-2026-11-15)** and from §3 above, which list the Secret Service name among the Flatpak's permissions: a permission for a backend the binary cannot use would widen the sandbox for nothing. It returns with the backend.
3. **Two static read-only file grants**, nothing else from home or the host: `--filesystem=~/.ssh/known_hosts:ro` (OpenSSH's host keys, the file only, never `~/.ssh`) and `--filesystem=~/.local/share/DBeaverData:ro` (the first-run import offer). The latter also exposes DBeaver's `credentials-config.json` (obfuscated, not encrypted) to the sandbox; the import reads it anyway when the user imports saved passwords, and the grant is read-only. Other files go through the file chooser portal. DBeaver's own Flatpak and Snap locations are reached with the folder picker.
4. **Document-portal files (I4, review M1).** The sandbox makes only the `DBeaverData` grant read-only; a portal grant is read-write on the host file. The core therefore treats a path under the document portal's mount (`$XDG_RUNTIME_DIR/doc`, `/run/user/<uid>/doc`, `/run/flatpak/doc`) as follows (`crates/ninesql-core/src/dbeaver_roots.rs`, feature `document-portal`, on by default): it asks `org.freedesktop.portal.Documents.GetHostPaths` (version 5, session bus, at most 2 s, on a thread of its own, at most 4 calls in flight; answers cached per document id, 256 ids at most, 10 min for a host path, 30 s for no answer) for the host path and runs the DBeaver checks on it, after the same checks on the portal path itself, which can only make the file inside (a workspace folder picked through the folder portal shows its markers through the mount); when the portal is unavailable, times out, fails or does not know the document, the file counts as inside; inside a sandbox, a marker walk that finds nothing proves nothing (the sandbox does not see the host's folders), so the file also counts as inside unless it lies directly in the home directory. Such an "unverified" result opens a SQLite database read-only; an export, which only creates a new file, may still write there but never replaces a file.
5. **No `MimeType`** in the desktop file until `ninesql` opens a file given on its command line: offering "Open with NineSQL" for `.sql` would do nothing (I8). `.sql` is already `application/sql` in shared-mime-info, so no MIME definition is shipped. §1's "MIME type for `.sql`" waits for that change.
6. **`ninesql` refuses unknown arguments** (exit status 2) and answers `--version` / `--help` before any window, display or GPU, so the install test can run it in a container.
7. **Hand-listed `Depends`** (`libc6 (>= 2.35)`, `libgcc-s1`, `libxcb1`, `libxkbcommon0`, `libxkbcommon-x11-0`, `libvulkan1`, `libwayland-client0`, `libfontconfig1`; recommends `mesa-vulkan-drivers | vulkan-icd`) rather than `dpkg-shlibdeps`: GPUI loads Vulkan, Wayland and fontconfig with `dlopen`, which `dpkg-shlibdeps` cannot see, and the list must not depend on the host that runs cargo-deb. The install test resolves it on the four targets; the `dlopen`'ed libraries are exercised only by the GUI run of P6-F.
8. **Builder floor: Ubuntu 22.04 (glibc 2.35).** The binary is linked in an Ubuntu 22.04 container pinned by digest, the oldest glibc of the release targets; `build.sh` fails if the binary needs a newer glibc symbol. Raising the floor drops a supported platform ([docs/10](../10-supported-platforms.md)).
9. **Toolchains.** Release builds use the Rust toolchain pinned in `release.yml` (`RUSTUP_TOOLCHAIN`, 1.100.0; bumped in its own PR), while `rust-toolchain.toml` stays on `stable` for development; reproducing a release locally needs `NINESQL_RUST_TOOLCHAIN=1.100.0`. The Flatpak uses the `rust-stable` SDK extension, which is not pinned, so the Flatpak build is not reproducible in §5's sense.
10. **Reproducibility is proven within one workflow run, not over time** (§5 as implemented). Two builds from two checkout paths on two runners must be byte-identical. The builder's apt packages (linker, C compiler, `-dev` libraries) are not pinned, so a rebuild months later may differ; pinning them through `snapshot.ubuntu.com` is a follow-up. The packaging tools are pinned to exact versions (cargo-deb 3.8.0, cargo-about 0.9.3, cargo-cyclonedx 0.5.10, cosign v3.1.4) and `build.sh` checks the first two.
11. **Release flow and who can sign** (§4 as implemented; [RELEASE.md](../../RELEASE.md) §4). The maintainer pushes the `vX.Y.Z` tag (a tag pushed with `GITHUB_TOKEN` does not start workflows). The workflow builds, compares, install-tests, then signs in a job with `id-token: write` only and creates a **draft** release in a separate job with `contents: write` only; both jobs run in the `release` environment. The maintainer configures a tag ruleset restricting `refs/tags/v*` to themselves and the `release` environment with themselves as required reviewer and a deployment policy limited to `v*` tags (P6-B; [packaging/README.md](../../packaging/README.md#who-can-sign-a-release)). The release notes print the commit, and verification pins the certificate identity (`…/.github/workflows/release.yml@refs/tags/vX.Y.Z`), the issuer (`https://token.actions.githubusercontent.com`) and `--certificate-github-workflow-sha <commit>` ([SECURITY.md](../../SECURITY.md#release-signing)). The maintainer publishes the draft.

**Consequences.**
- In the Flatpak, a SQLite file chosen through the portal opens read-only unless it lies directly in the home folder or a DBeaver check on its host path clears it, which inside the sandbox needs the folder to be visible (`flatpak override --filesystem=<folder>`, after which the file chooser returns the real path). Exports through the portal keep working.
- A Flatpak user who wants the Secret Service waits for the backend (ADR-0012); there is no override that enables it in a default build.
- A signature is only as strong as the repository settings of decision 11, which live outside the repository and are a P6-B task for the maintainer.
- A third party can rebuild a tag bit for bit only while the Ubuntu 22.04 archive serves the same packages.

**Rejected alternatives.**
- **Keep `--talk-name=org.freedesktop.secrets` as ADR-0005 lists it**: grants a D-Bus name the default binary never uses.
- **Treat every document-portal path as inside, with no portal call** (the interim rule the review allowed): simpler, but also refuses exports through the portal and gives the `.deb` build no host path to check.
- **`--filesystem=home:ro`** so the marker walk sees the host's folders: exposes the whole home directory (`~/.ssh` keys included) to the sandbox, against §3.
- **`dpkg-shlibdeps` (`$auto`) for `Depends`**: misses the `dlopen`'ed libraries and depends on the build host.
- **One signing-and-release job** with both `contents: write` and `id-token: write`: any step of it could sign and publish; the split keeps the OIDC token away from the job that writes to the repository and vice versa.

### Note on the P6-A amendment: what v0.1.0 ships (2026-11-19)
Decided by the maintainer on 2026-11-19; it changes the order of delivery, not the decisions above. **v0.1.0 is published as a cosign-signed `.deb` attached to the GitHub release**, with `SHA256SUMS`, the CycloneDX SBOM and their Sigstore bundles (§4 and decision 11 of the amendment). The signed APT repository of §2 and the Flatpak on Flathub of §3 are not part of v0.1.0 and come in a later release; §2 and §3 still describe their target design. Until the APT repository exists, users verify the `.deb` with `cosign verify-blob` and `SHA256SUMS` ([SECURITY.md](../../SECURITY.md#release-signing)), and no OpenPGP fingerprint is published. [docs/04](../04-mvp-scope.md#exit-criterion) exit criterion 2 and [RELEASE.md](../../RELEASE.md#3-artifacts-from-v010) §3 were amended to match.
