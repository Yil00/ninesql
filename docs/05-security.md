# Security

NineSQL holds credentials to production databases and displays their data. Its security model protects those credentials and data on the user's machine, on the network, and against the user's own mistakes.

## Assets
- Database passwords, tokens, SSH key passphrases, client certificate keys.
- Data displayed, copied, exported or kept in history.
- The integrity of production databases (accidental writes).
- The user's DBeaver workspace (must not be damaged by import).

## Threats and controls
| Threat | Control | Invariant / ADR |
|---|---|---|
| Another local process or a backup reads saved passwords | Secret Service or Argon2id + XChaCha20-Poly1305 vault ([notes below](#vault-format-v1)); workspace holds references only; `0600` / `0700`; no plaintext store at all | I1, ADR-0005, ADR-0008 |
| Secrets leak through logs, history, crash output or exports | No values or passwords in logs; history without parameters; query text logged at `trace` level only when the connection type's `log_query_text` allows it, and never for production ([below](#statement-text-in-logs)) | I1, ADR-0007 |
| Network attacker intercepts or impersonates a server | `verify-full` TLS by default, rustls; a per-connection CA file is the only trust anchor and `verify-ca` requires one ([ADR-0019](adr/0019-tls-ca-file-semantics.md)); SSH host keys checked, changed keys blocked; non-strict host-key policies only as explicit, flagged per-hop choices | I5, ADR-0011, ADR-0016, ADR-0019 |
| The client itself leaks data (telemetry, update checks) | No network traffic except declared connections | I2 |
| Accidental destructive statement in production | Connection types, engine-side read-only ([below](#read-only-sessions)), parser-based confirmation, manual commit default | I3, ADR-0007 |
| A secret store that never answers (an ignored unlock prompt) blocks connects | Secret reads bounded ([below](#bounded-secret-reads)) | ADR-0004, ADR-0005 |
| Secrets left in memory while the machine sleeps or the screen is locked | Vault and "ask every time" cache locked on logind sleep and session lock (default-on `desktop-lock` feature) and after an idle time ([below](#vault-format-v1)) | I1, ADR-0005 |
| Injection through generated SQL (edits, filters, DDL) | Values always bound in what runs; previews with typed literals that read the same in every lexical mode; names checked and quoted by the dialect; every generated statement self-checked (one statement, expected class); a raw `WHERE` must stay a read; tests with hostile identifiers and values ([below](#generated-sql-and-row-edits-p5-a-p5-b)) | ADR-0004, ADR-0007, ADR-0027 |
| An export or an import overwrites, plants or leaks a file (symbolic links, DBeaver files, NineSQL's own storage, `~/.ssh`) | New `0600` file, `O_EXCL` / `O_NOFOLLOW`, `RENAME_NOREPLACE` unless the overwrite was confirmed, protected directories refused; import files opened once and read through one handle ([below](#export-and-import-files-p5-c)) | I1, I4, ADR-0027 |
| An exported CSV runs as formulas in a spreadsheet ("CSV injection") | Formula guard on by default for CSV and TSV exports and for the grid's CSV and tab-separated copies, `Ctrl+C` included ([below](#export-and-import-files-p5-c)) | ADR-0027 |
| A bulk write or a grid save reaches production unnoticed, or an export runs a write | One confirmation for the whole import or save, bound to exactly what runs; exports run reads only, in an engine-side read-only transaction where possible ([below](#confirmations-of-bulk-writes-and-saves-p5)) | I3, ADR-0007 amendment |
| A DBeaver export leaks secrets or weakens a connection | No secret, no `credentials-config.json`; connections DBeaver could not reproduce safely skipped; read-only weaker in DBeaver, warned ([below](#export-to-dbeaver-p5-d)) | I1, I4, ADR-0006, ADR-0027 |
| Malicious or corrupted DBeaver files / server responses crash or exploit the parser | Total parsing, fuzzing, no panics on untrusted input | ADR-0006 |
| DBeaver workspace damaged by import or by a connection to a file inside it | Read-only access, byte-identical test after preview and apply ([below](#dbeaver-import-p2-c)); file drivers open files inside a DBeaver workspace read-only ([below](#files-inside-a-dbeaver-workspace)) | I4, ADR-0006 |
| Supply-chain compromise | `cargo deny` (licenses, bans, sources, advisories), exact pins for GPUI ([ADR-0013](adr/0013-gpui-source-and-supply-chain.md)), `--locked`, patched third-party crates checked against their crates.io archive by `scripts/verify-patches.sh` in CI ([audit log](audits/gpui-snapshot.md)), signed reproducible releases, SBOM | I7, ADR-0002, ADR-0010 |
| Out-of-memory on huge results | Fetch size and byte budget per result, streamed export; image previews only for single-frame PNG and JPEG within size and pixel limits (GIF and animated PNG shown as hex), decoded images evicted from GPUI's caches once no longer shown (from every window's sprite atlas too when the results view closes), and an image never shown not decoded; client-side sort bounded at 200 000 loaded rows ([ADR-0027](adr/0027-phase-5-editing-transfer-and-export-decisions.md) §6) | I6, ADR-0004, ADR-0027 |

## What NineSQL does not protect against
- A compromised user session (malware running as the user can read the unlocked keyring or memory).
- Database-side permissions: NineSQL can do what the database account can do; least-privilege accounts are the user's responsibility. Read-only mode reduces mistakes; it is not a privilege boundary when the account can turn it off.
- Data the user explicitly exports or copies to the clipboard.

## Vault format v1
The vault (`vault.bin`, ADR-0005 §2) is specified in the rustdoc of `ninesql_secrets::vault`. Bounds and properties:
- Key: Argon2id v0x13, 16-byte random salt, parameters in the header (default m = 64 MiB, t = 3, p = 1). New vaults and password changes accept m from 19 MiB to 1 GiB, t from 2 to 16, p from 1 to 8; reading accepts any valid parameters under the same ceilings, so a planted header cannot make NineSQL allocate more than 1 GiB.
- Sealing: XChaCha20-Poly1305 over the whole entry list, a new random 24-byte nonce on every write, the 112-byte header as associated data. A separate key-check tag tells a wrong master password from a damaged file. The payload is zero-padded to 256-byte steps, so the file size reveals little about the number and length of secrets.
- Limits: 10 000 entries, 64 KiB per secret, 16 MiB per file. Reading never writes: a wrong password, a damaged, truncated or newer file is reported and left untouched.
- Memory: the derived key and decrypted entries are zeroized on lock, idle timeout and drop. Two copies cannot be wiped from NineSQL's code: a short-lived cipher instance that Rust may move on the stack, and a 64-byte stack copy left by `argon2` 0.6 (`blake2b_long`); the Argon2 working memory is allocated and wiped by NineSQL because the crate does not wipe its own.
- Idle lock on `CLOCK_BOOTTIME` (suspended time counts).
- Lock on sleep and screen lock (`DesktopLockWatcher`, [docs/02](02-architecture.md)): the vault is locked and the "ask every time" cache cleared on logind `PrepareForSleep(true)`, on the session's `Lock` signal and when its `LockedHint` turns true. The watcher holds a logind sleep **delay inhibitor**, so the suspend waits (up to logind's `InhibitDelayMaxSec`) until the lock ran. Every signal is checked on receipt: a signal with a destination header is refused and the sender must be the current unique owner of `org.freedesktop.login1`, so another process cannot release the inhibitor or forge a lock. If the system-bus connection is lost, the watcher locks once at once (fail-closed), then reconnects with a bounded back-off (1 s doubling to 60 s, kept doubling while the bus flaps: it resets only after a connection that lasted 60 s; each attempt cut after 5 s) and subscribes again (keeping the session found before if the lookup fails until logind is back, then looking it up again, with two retries; a session not found again is reported as a problem); back on the bus it locks again if the session's `LockedHint` is true or cannot be read (fail-closed), or if the machine was suspended meanwhile (`CLOCK_BOOTTIME` ahead of `CLOCK_MONOTONIC` by more than 2 s beyond what it was, so its `PrepareForSleep` was missed; a shorter suspend is not seen). If logind leaves the bus, the watcher locks once and waits for it; when logind returns, the same `LockedHint` and suspend checks apply. Recorded in the [ADR-0005 amendment (lock watcher reconnect)](adr/0005-secrets-storage.md#amendment-lock-watcher-reconnect-2026-11-18), accepted (maintainer, 2026-11-18). The watcher is behind its own `desktop-lock` feature (zbus 6 only, no Secret Service client), **on by default**, and `CoreServices` starts it at startup; after a logind restart the owner change is handled before any signal of the new logind, and the delay inhibitor is taken again from it; a refused or unanswered `Inhibit` is retried with a back-off (1 s doubling to 60 s) while logind is on the bus and no sleep is under way. **Flatpak**: the sandbox must be allowed to talk to logind on the system bus, `--system-talk-name=org.freedesktop.login1` (in addition to `--talk-name=org.freedesktop.secrets` for the keyring); without it the watcher cannot start, `lock_watcher_status` reports it and only the idle lock applies. Limits: while the bus or logind is away, sleep and screen lock are not watched (the idle lock still applies), and a screen lock followed by an unlock in that window is not seen; a watcher that could not start at all (no system bus at startup) is not retried. `CoreServices::lock_watcher_status` tells the UI live whether sleep and screen lock are watched, so the UI's connection problems clear when the watcher is back; a screen lock watched before and lost (the session not found again) is reported as a problem too.
- Vault unlock: an open that needs a vault secret while the vault is locked answers `OpenOutcome::NeedsVaultUnlock` before anything is dialled, and before it asks for "ask every time" fields, so these are typed once, after the unlock. A lock (sleep, screen lock, "lock secrets") that arrives while an unlock is queued or deriving its key wins: `LockHooks` counts lock generations, `unlock_vault` / `create_vault_with` capture the count when called and, when it moved by the time the vault is open, lock it again and answer `VaultError::Locked`. The master password travels as a `SecretString` moved to the blocking pool and dropped (zeroized) right after the key derivation; a wrong password is reported without echoing it (tests check that neither the master password nor a saved database password reaches any file under the workspace directories).

- Master password: a new vault and a password change need at least 12 characters (`MIN_MASTER_PASSWORD_CHARS`, Unicode characters, not bytes); a shorter one is refused with `VaultError::PasswordTooShort` before any key derivation, and the vault prompt shows the rule (P1-E review, L4). A password made only of whitespace is refused as empty (`VaultError::EmptyPassword`). An existing vault created before the rule still unlocks with its password.

Known limits:
- **Offline guessing** of a copied `vault.bin` is slowed only by Argon2id: the master password must be strong. The 12-character minimum rules out the weakest choices; it does not measure strength. The back-off between failed unlocks (3 free attempts, then 1 s doubling up to 60 s) is **per process**: it slows guessing through a running NineSQL at an unattended desktop, not a restarted process or a copied file.
- **Rollback is not detected**: someone able to write `vault.bin` can put back an older copy (older secrets under an older master password). Detecting it needs state outside the file; it is an optional follow-up.
- For information: XChaCha20-Poly1305 is not key-committing, so a file crafted by someone who can write it could decrypt successfully under more than one key (the partitioning-oracle class of attacks, which also needs to observe many unlock outcomes). The vault does not claim to resist an attacker who can replace `vault.bin` (see rollback); this is recorded, not mitigated.

## Bounded secret reads
An unlock prompt of the Secret Service is not a D-Bus method call and can wait indefinitely. The core therefore bounds secret resolution itself ([docs/02](02-architecture.md)): the store calls of one connect share one deadline (`ManagerConfig::secret_timeout`, default 60 s), after which the field fails with `SecretError::Unavailable`, as does a panicking store task. A read already in flight for the same secret is joined instead of starting another store call, and at most 8 reads may run or hang on the blocking pool at once (further ones fail as `Unavailable`), so a store that stops answering cannot starve the runtime. A connect whose caller went away stops at once; a store call already running ends on the store's own limits and its value is dropped unused. Known limit: the Secret Service write path (`set` / `delete`) cannot dismiss a prompt yet; it is a follow-up due before that backend is on by default.

## Read-only sessions
A read-only connection is enforced by the driver at the session level, never only by the UI (I3, ADR-0007). Every driver that exists today (pgwire, mysqlwire, sqlite) refuses write-class statements client-side and lets the engine refuse the rest. Where the engine has a session read-only mode, the driver sets it before any init statement and checks it after **every** statement; where it has none (QuestDB, TiDB, since P4-C), a read-only session is accepted only when the server itself refuses writes, and refused otherwise, never faked:
- **pgwire** (PostgreSQL): `default_transaction_read_only` is checked after every statement and the session is closed if it was lifted. Inside a transaction block the driver then runs `SET TRANSACTION READ ONLY`, because the one-shot `SET TRANSACTION … READ WRITE` (including its comma form `SET TRANSACTION ISOLATION LEVEL …, READ WRITE`) makes the open transaction writable without changing the session default. Before this fix (wave 3a) a read-only session in manual-commit mode or in an explicit transaction could write through a writing function; regression tests cover autocommit, manual-commit and explicit transactions, savepoints and aborted transactions.
- **mysqlwire** (MySQL, MariaDB): `transaction_read_only` is read back after every statement (a lifted mode, or a failed read-back, closes the session), then `SET SESSION TRANSACTION READ ONLY` is re-asserted, which resets a pending one-shot `READ WRITE` for the next transaction.
- **pgwire** (TimescaleDB, YugabyteDB): as PostgreSQL.
- **pgwire** (QuestDB, `ServerSetting`, not liftable): only the server's read-only user or a read-only server; checked at connect from `SHOW PARAMETERS` **and** with a write probe that changes nothing and must be denied. Verified on open-source QuestDB only.
- **mysqlwire** (TiDB, `ServerSetting`, liftable): only an instance with `tidb_super_read_only` or `tidb_restricted_read_only` on, and only for an account that mode covers. At connect the driver also refuses an account whose `SHOW GRANTS` (active roles expanded) lists `RESTRICTED_REPLICA_WRITER_ADMIN` (exempt from both modes), `SUPER` or `ALL PRIVILEGES ON *.*` (so `root`), fail-closed, and requires a write probe that changes nothing (`DELETE FROM information_schema.CHARACTER_SETS WHERE FALSE`) to fail with error 1836 (phase 4 review M1). The instance's mode and `CURRENT_ROLE()` are read back after every statement; a lift or a role change closes the session at the next read-back. Windows: a statement that passed the classifier as a read can run before that read-back or while a lift propagates across TiDB servers, and a privilege granted to the account by another session after connect is not re-checked until the next connect ([docs/08](08-engine-capabilities.md#read-only-mechanism-adr-0007-i3), [ADR-0026](adr/0026-phase-4-metadata-navigator-and-wire-engine-decisions.md) §3.2).
- **sqlite**: read-only open, `query_only`, an authorizer that allows only reads and no attached databases, verified after every statement; the session is closed if anything changed.

Since the driver-API PR (2026-11-15) the shared classifier also refuses the comma form (`SET TRANSACTION ISOLATION LEVEL …, READ WRITE`) client-side as an access-mode change, and reads a `WITH` as a read only when its main statement is found outside every CTE; the engine-side re-asserts above remain as defence in depth, with tests that bypass the classifier.

Init SQL is classified before connecting with the engine's default lexical rules, not with the server's `sql_mode` or `standard_conforming_strings`; the gap and its mitigations (flagged lexical-mode changes and multi-statement entries, every entry after a session statement flagged, drivers splitting with the session's dialect, one statement per call, read-only re-asserted) are described in [docs/02](02-architecture.md#confirmations-adr-0007-adr-0011). Imported init SQL is confirmed once whatever the connection type (`init_sql_needs_confirmation`, same section).

Read-only mode is a guard against mistakes, not a privilege boundary (see above). Per-engine details: [docs/08](08-engine-capabilities.md#read-only-mechanism-adr-0007-i3).

## SCRAM-only authentication
`ConnectParams::password_exchange = ScramOnly` asks the driver to accept only a SCRAM exchange in which the server proves it knows the password verifier, as libpq's `require_auth=scram-sha-256` ([docs/08](08-engine-capabilities.md#pgwire-postgresql-p1-b)). pgwire enforces it whatever the transport: a request for md5 or a cleartext password, and a server that accepts the login without a verified SCRAM exchange (trust), fail the connect before anything derived from the password is sent. mysqlwire refuses the setting at connect, because no MySQL authentication exchange gives that proof.

Limit: there is no channel binding yet (`SCRAM-SHA-256-PLUS` with `tls-server-end-point` is a follow-up). `ScramOnly` stops method downgrades; it does not stop a man in the middle that relays the exchange to the real server when TLS is `require` or `disable`. Only `verify-full` (or `verify-ca` with a private CA) protects against that. The core connection model carries it as `password_exchange` (`connections.json` schema 3; a version 2 file is migrated and a `password_exchange` key found in it is dropped, so the policy only comes from a NineSQL that validated it), checked at save against the driver's declared policies; `Connection::scram_without_verified_tls` tells the UI to flag `scram-only` below `verify-ca`. The connections UI (P1-C) offers it as a "SCRAM only" toggle when the driver declares the policy and the authentication is a password, with that warning.

## Statement text in logs
Drivers log statement text at `trace` level only when `ConnectParams::log_statements` is set and the connection is not typed production. The core sets `log_statements` from the connection type's `log_query_text`, so a custom type with `log_query_text = false` is honoured, not only production (ADR-0007). Parameter and result values are never logged. A statement whose text holds a credential word (password, identified, secret, token, encrypt…, whole words in any case, literals and comments included) or a URI with credentials (`scheme://user:password@`) is never logged, by the drivers or the core (`ninesql_driver_api::hygiene`, since P3-D / P3-C); the rule is lexical, so a credential built at run time by concatenation is not detected. Driver errors never echo a property key raw: control characters are escaped and long keys cut.

**Query history** (P3-C, [docs/02](02-architecture.md#query-history-p3-c), [ADR-0024](adr/0024-phase-3-execution-history-and-preferences-decisions.md) §2, accepted): `history.sqlite` is created `0600`, never holds parameter values, holds nothing for production connections or types with `log_query_text = false`, and skips statements under the same credential rule; deletes are followed by a WAL checkpoint so deleted text does not stay in the write-ahead log. A secret typed as a literal in a statement without a credential word (an `INSERT` into an application table) is recorded: bind it through the parameters prompt instead.

## Application logging (ADR-0029 §3)
The `ninesql` binary installs the only `tracing` subscriber (`crates/ninesql-ui/src/logging.rs`); library crates emit events and never install one.
- **Stderr at `warn` by default**, one line per event, no ANSI colours, so a session started from a desktop entry sends only warnings and errors to the user journal. `info` and `debug` are opt-in.
- **A file log, off by default**: `[logging] file_level` in `settings.toml` (`off`, `error`, `warn`, `info`, `debug`; no `trace`), or `NINESQL_LOG` for one run. It writes `$XDG_STATE_HOME/ninesql/logs/ninesql.log`: the directory `0700`, the file `0600`, opened with `O_NOFOLLOW` and refused unless it is a regular file owned by the user; at most 8 MiB per file and three files (`ninesql.log`, `.1`, `.2`). One background thread writes it through a bounded channel; when the channel is full, events are dropped and counted, never waited on (I6).
- **Filter**: `NINESQL_LOG` takes the `RUST_LOG` syntax and applies to both sinks; `RUST_LOG` is ignored, so a value set for other tools does not change what NineSQL writes. In release builds every filter is capped at `debug` (statement text lives at `trace`, above), with one warning when a filter asked for more.
- **Escaping**: control characters, line and paragraph separators and bidirectional controls in the message and in every field are written escaped (`\n`, `\u{…}`) on both sinks, so a value cannot forge a log line or drive a terminal.
- **Error kinds, not messages**: events at `info` and above in the core, secrets, SSH, storage, transfer and DBeaver crates, and at `debug` and above in the driver API and the drivers, carry a stable error kind (and an engine's error code where there is one), never an engine's, SQLite's, D-Bus's or an SSH server's message, a statement, a host, a user name or a full path: an engine message can quote a value (a duplicate key, a failing cast). The message stays in the UI. Tests: `crates/ninesql-core/tests/log_hygiene.rs`, `conformance::assert_engine_messages_not_logged` and `conformance::assert_failed_connect_not_logged` in the driver tests, and an I1 test of the file log at `debug` (a connect, a statement with a credential word and a production statement leave neither the password nor the statement text in the file).
- What the file holds: connection names, host names and error kinds with their context. It is sensitive context, not secrets; read it before you attach it to a bug report ([troubleshooting](user-guide/troubleshooting.md)).

## Test build (`e2e-scenarios`, ADR-0029 §2)
The end-to-end scenario runner of P6-G step 2 exists only in a binary built with the `e2e-scenarios` feature of `ninesql-ui` (off by default, Linux only), which `make e2e-local` builds in `target/e2e-build/`, apart from `target/release/ninesql`. It accepts `--e2e-run <file> --e2e-out <dir>`; no environment variable starts a run.
- **Never packaged.** A compile-time refusal when `NINESQL_PACKAGE_BUILD` is set (`packaging/deb/build.sh` and the Flatpak manifest set it, and the Flatpak lint requires it); a marker string (`NINESQL-E2E-SCENARIOS-TEST-BUILD`) that `build.sh`, `release.yml` and the install test refuse; `make e2e-feature-guard` (in `make check` and the CI `deny` job), which fails when the feature is reachable from a default feature of `ninesql-ui` or `ninesql-core` or turned on by another crate, build dependencies included. `ninesql --version` of a test build says `(e2e-scenarios test build, not for distribution)` and its window title ends with `[E2E TEST BUILD]` ([packaging](../packaging/README.md)).
- **Isolated from the user's data.** Before anything is read or written, the runner checks that `HOME` and the four XDG variables lie in one fresh `0700` run directory of the user, under the system temporary directory or a `target` directory, not the account's home or a default XDG directory, with empty NineSQL directories; otherwise it stops with status 2.
- **Guards in the core** ([docs/02](02-architecture.md#test-build-guards-feature-e2e-scenarios-adr-0029-25)): connections only to loopback addresses, checked after DNS resolution with SSH hops and the tunnel target included (the address checked is the one connected to); export, import and database files only inside the run directory; the encrypted vault in the run directory with a random master password per run, never the keyring (a build with `secret-service` is refused at run time).
- **No inbound channel.** The runner opens no port, socket, D-Bus name or pipe and reads no input during a run; it writes checkpoint lines to its standard output, which the harness reads to take a screenshot of the test window alone (X11 or XWayland).
- **I1 check of every run.** At the end of a run the runner scans every file of the run directory (the vault excepted) for the passwords of `dev/engines.json` and the run's master password; a hit is exit status 3, and `make e2e-local` then writes no archive. Screenshots cannot be scanned; they show what the UI shows, and the UI never formats a password.
- The lock watcher stays on in scenario runs, as in the application: a screen lock or a suspend during a run locks the run's vault, so a later step that needs a saved password can fail. Leave the desktop unlocked while the scenarios run.

## Files inside a DBeaver workspace
`ConnectParams::inside_dbeaver_workspace` marks a file endpoint inside a DBeaver workspace (I4). File drivers then open the file read-only whatever the connection's read-only setting says, never create it and never create or modify a file next to it; network drivers ignore the flag. sqlite opens such a file immutable, so it creates no journal, `-wal` or `-shm` file. The cost is freshness: pages committed only in a `-wal` file (a writer that crashed or is still running) or in a hot journal are not visible in that session, and its first notice says so. `ninesql-core` computes the flag for every file endpoint ([docs/02](02-architecture.md#connection-lifecycle)): after resolving symbolic links, a file under the `DBeaverData` directory of a known install location, under a folder picked for an import, under any directory named `DBeaverData`, or under a folder holding a DBeaver workspace marker (`.metadata/dbeaver-workspace.properties`) or a `.dbeaver` directory with a project file (`data-sources*.json`, `project-settings.json`, `credentials-config.json`), is flagged. The marker walk stops before the home directory: `$HOME`, its ancestors and `/` are never taken for a workspace or project. A stray `.dbeaver` in a shared directory such as `/tmp` is ignored only while it holds no project file: another local user can create one and get files below it opened read-only, which fails safe and shows through the flag. A dangling symbolic link is checked at its target (followed at most 40 links deep), where a creating open would write. The checks are read-only and fail closed: a path that cannot be resolved (any error but "not found") or a marker that cannot be checked counts as inside. The driver is given the canonical path that was checked, so the check and the open name the same file, and `SessionInfo::inside_dbeaver_workspace` lets the UI say why the file was opened read-only. Defence in depth (P1-E review, L2): the core also sets `read_only` for such a file and refuses the session (`ReadOnlyNotEnforced`) when the driver does not report it read-only, so a future file driver that ignores the flag cannot write to it. Limit: a DBeaver workspace in a custom location, without its markers and never picked for an import, is not recognised. **Document portal** (P6-A review M1, [ADR-0010 amendment](adr/0010-packaging-and-distribution.md#amendment-p6-a-packaging-2026-11-19)): a file chosen through the Flatpak file chooser has a path under the document portal's mount (`/run/user/<uid>/doc/…`, `/run/flatpak/doc/…`), which the portal writes through to the host; the core asks the Documents portal for its host path (`GetHostPaths`, at most 2 s) and runs the checks above on it. No answer, a failure or an unknown document counts as inside, and so does, inside the sandbox, a file whose host folders the sandbox cannot see (a missing marker proves nothing there), unless it lies directly in the home directory. Such an unverified file opens read-only; an export, which only creates a new file, may still write there but never replaces a file.

## DBeaver import (P2-C)
The core side of the import ([docs/02](02-architecture.md#dbeaver-import-p2-c)) adds these controls to the parser's ([docs/06](06-dbeaver-interop.md#import-rules-enforced-by-the-parser-p2-a)):
- **I1**: the preview holds no secret value (slots and kinds only). At apply, each decrypted value goes straight from the parser's zeroizing buffer to the chosen store (keyring or vault; with no store the field stays "ask every time" and the value is dropped) and is dropped right after; `connections.json` gets a reference only. The import report (`imports/dbeaver-<timestamp>.json` in the project) holds statuses, reasons, counts and report entries, never a value. Tests check that no imported secret (fixtures, crafted plaintext passwords, re-imported values) reaches any file under the NineSQL directories or the captured logs.
- **I3**: imported init SQL always gets `init_sql_needs_confirmation`, set by NineSQL (never read from the file), again on every re-import, and kept by the UI write paths while the init SQL is unchanged; an end-to-end test opens a crafted "dev" connection and gets `InitSqlNeedsConfirmation` with `imported = true`, before the save (test-before-save), after it, and with a UI copy that lost the marker. Imported connection types only ever make an existing type stricter, built-in types included (reported, [ADR-0023](adr/0023-phase-2-import-decisions.md) §2); a re-import keeps the saved connection type unless the imported one is at least as strict on every rule, and a stricter read-only or manual-commit override. A per-connection `auto_commit` override cannot turn auto-commit on for a production type.
- **I2**: a connection the parser disabled because its route could not be reproduced (network profile, unknown handler such as a proxy, SSH forwarding target) keeps a persisted `DisabledReason` (`route`): the UI save paths refuse to drop it, and only `Workspace::enable_connection` with `route_fixed` (the user confirmed the route was set up again) and a passing driver validation enables it.
- **I4**: the core never opens a DBeaver file itself (it goes through `ninesql-dbeaver`'s read-only reader); a test checks every file of the repository's fixture workspace is byte-identical, with the same modification time, after preview and apply, and the same for each P0-E fixture copy. The source workspace is added to the session's DBeaver roots at preview time, so a database file inside it opens read-only, and an imported file endpoint inside a DBeaver workspace is saved with `read_only = true`.
- Driver properties the engine's driver reserves or does not accept are dropped with a report entry; they never reach a driver.
- **Re-import and saved secrets** (P2-C review, H1): a re-import updates a connection only when the DBeaver id, project and canonical source workspace all match; another workspace reusing an id gets a new connection. A secret saved in NineSQL survives a re-import only while everything it authenticates against is unchanged (engine, host, port, user, TLS mode and CA file, SSH route; or the SSH hop's host, port, user, key file and the hops in front of it; a non-strict host-key policy is not carried across a route change), so a crafted or edited workspace cannot redirect a saved password to another host or downgrade TLS under it. A weaker TLS mode or another CA file is not taken without the user's per-connection acceptance, and accepting it drops the database password. The test-before-save of a preview asks for every credential.
- **Secret writes**: imported values are written under fresh references; the old references are deleted only after `connections.json` points at the new ones, so a failed import loses no saved secret.
- **Connection types**: types defined in several projects are folded tighten-only; built-in types are made stricter (never weaker) to keep DBeaver's confirmation and manual-commit rules, with a report entry, since this applies to every connection of the type.

## Generated SQL and row edits (P5-A, P5-B)
- **What runs is bound.** Row edits, the CSV import and the server-side filters send every value as a bind parameter; the preview, the copy as SQL `INSERT` and the SQL export use typed literals that read back as exactly the bound value in every lexical mode of the engine (PostgreSQL `standard_conforming_strings` on or off: `E''` when needed; MySQL family `NO_BACKSLASH_ESCAPES`, `ANSI_QUOTES` and multi-byte client character sets: `CONCAT(_utf8mb4 X'…')` for a string holding a backslash, a NUL or a hidden character), so a preview replayed in another session changes the same row ([docs/08](08-engine-capabilities.md#dml-generation-p5-b)). Names are checked (`dml_check_identifier`: empty, NUL, names the engine would truncate) and quoted by the dialect. Each generated statement must split as one statement and classify as the expected class (`Write` for edits and the import, `Read` for filters and exports), or it is not run.
- **Which rows.** `UPDATE` and `DELETE` always carry a `WHERE` on a key taken from the metadata (never from the result's column names), with the original values of the edited columns; each must change exactly one row inside a transaction, otherwise the whole save is undone. Only a result of the core's own table query is editable (`QuerySource`), so an alias in a typed statement cannot point an edit at other rows. Tables whose storage engine has no transactions (or, on the MySQL family, an unknown one) are not editable, since a failed save could not be rolled back.
- **Raw `WHERE`.** A user-typed filter is accepted only when it stays a read inside its parentheses (lexical checks plus the classifier). The checks are lexical: a function with side effects outside the classifier's lists (a user function that writes) passes; read-only sessions stop its writes engine-side (I3). Bidirectional control characters in it are shown with visible markers, not refused ([Phase 5 follow-ups](ROADMAP.md#phase-5-follow-ups)).
- **Logs and history.** Nothing logs a value; the filter history is in memory only and, on production and non-logging types, keeps only the shape of a filter.

## Confirmations of bulk writes and saves (P5)
[ADR-0007 amendment](adr/0007-production-safety-model.md#amendment-phase-5-2026-11-16) (accepted, maintainer, 2026-11-17):
- A CSV import and a grid save each ask **once**, before anything is sent, on production and confirm-every-write connection types: the import shows the connection, table, columns, statement shape, file and size; the save shows the counts, the unchecked columns and the exact preview script.
- The token is single-use and valid 10 minutes. The import token is bound to the session, the canonical file and its identity (device, inode, length, modification time), the table, the columns, the mapping, the transaction mode, the skip-invalid choice, the CSV syntax and value options (header, delimiter, quote, NULL text, empty fields, trimming) and whether the table can roll back; the save token to the session, the table and a SHA-256 digest of the exact statements and values. Anything different is refused and asks again.
- **The script is shown whole.** The save confirmation, the DML preview and the CSV import confirmation show their script in a read-only, virtualized view that never cuts text (P5 UI review M1): a long line wraps onto continuation rows marked `↪`, at the width measured from the box and its mono font at every frame (72 columns until the first measurement; wide characters such as CJK, emoji, flags, arrows and symbols counted conservatively; one spare column), with horizontal scrolling to the widest row as a backstop, so a narrow dialog wraps sooner rather than clipping the end of a row (second re-review M-A); invisible, line-breaking and bidirectional characters are shown as visible markers, and the line and byte counts and an "Ends with:" line are shown, so a clause at the end of a long `UPDATE` cannot be pushed out of sight or reordered. Names in the dialogs (connection, table, columns, foreign keys, the import file path) follow the same marker rules. "Revert row changes" is refused while a save, its confirmation, a run or a lease holds the pending changes, so the confirmed script stays the one shown.
- After that, the service answers the session's per-statement confirmations only for the byte-identical `Write` statement it just sent; any other confirmation request fails the job.
- In manual-commit mode a save runs under a savepoint and leaves the transaction open: the changes are committed only by the user's own "Commit transaction".
- **Exports run reads only.** The exported statement must classify as `Read` (a write is never run by an export), and runs inside an engine-side read-only transaction when the session is not read-only and has transactions (PostgreSQL family `BEGIN READ ONLY`, MySQL and MariaDB `START TRANSACTION READ ONLY`), so a side-effect function the classifier reads as a read is refused by the engine. On production and confirm-every-write connections an export is refused when that transaction cannot be opened or a transaction is already open; elsewhere it goes on with a warning. **TiDB has no read-only transaction**: its `START TRANSACTION READ ONLY` is a no-op (refused with error 1235 by default, accepted without effect when `tidb_enable_noop_functions` is on), so NineSQL does not send it; a TiDB export on a session that is not read-only relies on the classifier only, is refused on production and confirm-every-write connections, and is warned about on every other type ("no read-only transaction"). A read-only TiDB session is enforced engine-side by the driver, so its exports are not affected.
- **An import commits its own rows.** Unlike a grid save, a CSV import commits what it writes even on a session in manual-commit mode (at the end with "All or nothing", every N rows otherwise), so the session's "Roll back" cannot undo it; the confirmation says so ([ADR-0007 amendment](adr/0007-production-safety-model.md#amendment-phase-5-2026-11-16), note of 2026-11-18).
- **Non-transactional tables.** A table whose storage engine cannot roll back (MyISAM, MEMORY, ARCHIVE, Aria…, `TableInfo::transactional == Some(false)`; on the MySQL family also an unknown engine) is never editable in the grid, and an import into it is refused in "All or nothing" mode: only "commit every N rows" runs, and the confirmation and the summary say rows cannot be rolled back (every row the database accepted stays, whatever the end) ([ADR-0027](adr/0027-phase-5-editing-transfer-and-export-decisions.md) §1.6).
- **A save that cannot be undone closes the session.** When a failed save can be undone neither by `ROLLBACK TO SAVEPOINT` nor by a full `ROLLBACK`, the session is closed, which rolls its transaction back on the server, so part of a save is never left for a later commit (`EditError::UndoFailed`). The same holds for a failed import whose `ROLLBACK` also fails: the session is closed.

## Export and import files (P5-C)
- **New files only (I4).** An export goes to a temporary file in the target directory (`O_CREAT | O_EXCL | O_NOFOLLOW | O_CLOEXEC`, mode `0600`), synced, then moved into place with `renameat2(RENAME_NOREPLACE)`, so a file that appeared meanwhile is never replaced; replacing an existing file needs its own explicit step in the dialog ("Replace"), and the move then replaces a symbolic link itself, never the file it points to. Where `RENAME_NOREPLACE` is unsupported: a hard link, then, on file systems without hard links, a check followed by `rename` (a narrow race). On error or cancel the partial file is removed. The final file stays `0600`: exports may hold sensitive data.
- **Protected directories.** The target directory is resolved (symbolic links included) and refused when it is, or lies inside, a DBeaver workspace (`DbeaverRoots`, fail-closed), NineSQL's configuration, data or state directories (vault, `connections.json`, history) or `~/.ssh`; compared by resolved path prefix and by `(device, inode)` of the directory and each ancestor, resolved at every check (bind mounts and renames covered). An import file inside NineSQL's own storage is refused too.
- **Import files.** Opened once with `O_NOFOLLOW | O_NONBLOCK` only if it is a regular file (a FIFO or a device has side effects), checked with `fstat` and read through that handle, never the path again; at most 8 GiB, 1 MiB per record and 4 096 fields per record; issues carry a line, a column and a reason, never a value.
- **Formula guard.** CSV and TSV exports, "Copy selected cells as CSV" and the tab-separated copies ("Copy selected cells", "Copy selected cells with column names"), prefix with `'` a text cell or header that starts with a tab or a CR, or whose first character after leading Unicode whitespace and format characters is `=`, `+`, `-`, `@`, `|` or a full-width `＝ ＋ － ＠`, so a spreadsheet opens it as text. On by default ("Formula guard: on" in the export dialog; always on for copies); numbers are never prefixed. Other formats escape their own syntax (JSON per RFC 8259, Markdown punctuation, HTML entities with a Content-Security-Policy that forbids scripts).
- No secret is written by an export: only result values (I1). Data the user exports is theirs to protect ([above](#what-ninesql-does-not-protect-against)).

## Export to DBeaver (P5-D)
- **No secrets (I1)**: the export never writes a password, passphrase or token, nor `credentials-config.json` (not even encrypted); the core passes only a "saved" flag. Descriptions, properties, folder names and type ids that look like they hold a secret are dropped or the connection is skipped, with a report entry; a test checks that no saved secret reaches the written files.
- **New files only, never in DBeaver locations (I4)**: a new `data-sources.json` (temporary file, hard link that fails if the name exists, device and inode checked) or a new project folder; targets inside a DBeaver location are refused. Residual: the directory is checked, then used by path (no directory-relative calls), so another process of the same user swapping a directory in between could redirect the new file; it still never overwrites one ([docs/06](06-dbeaver-interop.md#file-safety-i4)).
- **Weaker in DBeaver**: DBeaver enforces read-only in its JDBC driver (`setReadOnly`) and its UI, not with an engine-side read-only transaction re-checked after every statement; every read-only connection gets a warning, `readOnlyMode=always` on pgjdbc, and its init SQL keeps only statements that read and call no function. DBeaver applies its own SSH host-key checks, not NineSQL's per-hop policies (warned), and before 24.3 reads only the first jump host (route-change warning). Connections DBeaver would connect to differently are skipped: URL syntax in hosts, databases or file paths (it would override TLS and read-only), IPv6 address hosts, routes NineSQL disabled, Unix sockets. TLS is written so that the worst case is `verify-ca`, never plaintext (MySQL-family `verify-full`), and the importer keeps the stricter mode when a handler and a property disagree.
- Details: [docs/06](06-dbeaver-interop.md#export-to-dbeaver-p5-d).

## Accepted risks
- **`secret-service` 6.0.0-rc.1 key handling** (P0-D review item L5). The crate does not zeroize the Diffie-Hellman key pair, the shared secret or the AES session key of the Secret Service transport session, and its modular exponentiation is not constant time. Leftovers only decrypt the D-Bus traffic of one short-lived session; reading them needs access to NineSQL's memory, a core dump or swap, which already exposes the secrets themselves (see above). NineSQL wraps returned secrets in zeroizing buffers at once and always asks for an encrypted session. Accepted as a residual risk; the Secret Service feature stays **off by default** until the desktop round trip of ADR-0012 passes (including the KWallet wizard that the probe may trigger through D-Bus activation) and the crate moves to a stable 6.x. Items 1–3 are to be reported upstream. Review details: rustdoc of `crates/ninesql-secrets/src/secret_service.rs`.
- **md5 password authentication on PostgreSQL** over a transport that is not protected (no `verify-ca` / `verify-full` TLS and no fully verified loopback SSH tunnel) is allowed with a logged warning, because servers still configured for md5 exist: an observer can capture the digest and crack it offline. A cleartext password is refused over such a transport. The per-connection "SCRAM only" setting ([below](#scram-only-authentication)) refuses md5; it is in the connection model and offered by the connection dialog (P1-C).
- **Local SSH tunnel port.** While an SSH tunnel is open, its local end listens on `127.0.0.1` on an ephemeral port (ADR-0011 §5). Other local users on the same host can connect to that port and reach the database through the tunnel. Database authentication still applies; on a multi-user host, the tunnel gives other users the network path, not the credentials.
